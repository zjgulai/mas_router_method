## 发生了什么

给 wiki 文档增量续写五章时，我用了

```
POST /docx/v1/documents/{doc}/blocks/{block_id}/descendant
  { children_id: [...], index: 0, descendants: [...] }
```

以为语义是「在这些块**之后**插入」。实际语义是「把这些块插成这个块的**子块**」。

于是 487 个块（05 到 09 五章）全部嵌进了 04 章最后一段的下方，并且因为我每一批都把
`last` 更新成上一批的最后一个块，批次之间又互相嵌套，形成 9 层深的树。

**读全文时顺序完全正确**，因为按文档顺序展开一棵深度优先树，结果和扁平序列一样。
所以 06、07、08 三章各核对过一次「写进去了 101/79/86 块」，每一次都对，而结构是坏的。

## 怎么发现的

写 09 章时接口开始返回 `1770041 open schema mismatch`，连一个普通段落都在报错。排查时
才发现：`root.children` 只有 545 个，而总块数是 1033。

## 影响

- 文档表面可读、可搜索、顺序正确，但**任何依赖层级的操作都会错**：折叠、目录、导出
  markdown 时的缩进、以及「这一段属于哪一节」。
- 更糟的是它不会报错。三次核对全部通过，因为它们核对的都是「块数对不对」。

## 正确写法

```js
// 追加到文档末尾，平级
POST /docx/v1/documents/{doc}/blocks/{doc}/children
  { children: [...], index: -1 }
```

`blocks/{doc}/children` 的 `index: -1` 才是「追加到末尾」，追加的块 parent 是文档根。

## 处置

1. 按深度优先顺序把 487 块的内容读出来（`walk(anchor)`），逐块重建，用
   `blocks/{doc}/children` + `index: -1` 平级追加。
2. 核对新的 `root.children` 长度和 H1 位置，确认 05..09 都在根下且顺序正确。
3. 删除原嵌套树（删锚点连同其子树）。
4. 补回被连带删掉的那一段（锚点本身是 04 章的正文）。

修复后：1072 个根子块，0 个嵌套块，8 个 H1 位置正确。

## 教训

**「写进去了」和「写对了」是两件事，而我只验证了前者。** 三次核对都在数块数，没有一次
去查 `parent_id`。这和仓库里 INC-002 是同一族：读到的内容是对的，但它不在你以为的位置上。

一个更具体的判据：对树形结构做增量写入后，第一条断言应当是「新块的 parent 等于预期的
父节点」，而不是「块数增加了 N」。
