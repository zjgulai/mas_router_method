at: 2026-10-25

related: [INC-001]

## 发生了什么

测试出现偶发失败，且失败方式自相矛盾：同一条断言，单独跑绿、全量跑有时红，
两次运行失败的条数还不一样（4 条、2 条、0 条）。先后排除了：

- 并发：实验证明 `--test-concurrency=1` 确实串行化（A 写探针、B 读目录，B 不再看到 A 的探针）
- 可见性：写一个文件后立刻让新进程 `readdir`，40 次全部命中，文件是「存在」的

真正的原因是**内容**。

## 证据

同一段代码，写入 78 字节再让新进程读回并逐字节比对：

```
/sessions/.../mnt/mas_router_method/docs/site    bad 19/60
/sessions/.../mnt/outputs/fsprobe                bad 18/60
/tmp/fsprobe                                     bad  0/60
```

失败时读到的是 **4157–4167 字节**的别的内容（4096 对齐），不是写入的 78 字节。
约每三次写入出现一次。

复现脚本留在 `/tmp/content.mjs`：

```bash
node /tmp/content.mjs <目录>
```

## 影响

1. **所有「写文件 → 立刻起一个进程读它」的测试都会偶发失败**，而且失败原因与
   断言要测的东西无关。`links.mjs` 的探针测试因此以约三成概率拿到「无断链」的结论。
2. **本机验证的可靠性低于我一直假设的水平。** 我长期把本机门禁当作完成标准，
   但在这个挂载目录上，`node scripts/site/build.mjs && git diff --exit-code`
   这类「先写再让别的进程读」的验证同样会得到假结论。
3. **CI 不受影响**：GitHub runner 是普通文件系统。所以 CI 绿而本机红（或反之）
   都不是矛盾，两者测的不是同一件事。
4. 与 INC-001（`git status` 报假 M、`git add` short read）以及早先 `tar` 给短文件
   补 NUL 是同一族：**这个挂载的写后读不保证一致。**

## 处置

- 测试侧：新增 `scripts/test-fs.mjs` 的 `writeAndConfirm()`，写完用新进程复核内容，
  不对就重试，直到环境真的就绪。这是**建立前置条件，不是放松断言**。
- 记录本事故，因为「本机绿」在这个仓库里不是充分证据。

## 未解释的部分

4096 对齐的具体来源、以及被读到的究竟是谁的数据，没有查明。
已查明的是：读写都正确，中间那一步不保证。

## 追加证据（同一天，第二次撞上）

修完审查发现后，我用 `cp` 覆盖了 `scripts/markdown.mjs`（把注入的 bug 恢复成正确版本），
然后立刻跑测试。同一个磁盘内容、同一个命令，连跑两次都报 1 条失败，第三次 26/26 全过。

中间执行过 `sync` 并 `sleep 1`，没有用。

这次的意义在于：**它不是测试的抖动，是文件的抖动。** 磁盘上的内容是对的，进程读到的是旧的。
因此本仓库里「刚才跑还是红的、现在绿了」不能当作「改好了」的证据——
必须换一个目录（`/tmp` 是 VM 本地文件系统，实测 0/60）或换一次 CI 才作数。

## 什么时候可以关闭

当挂载行为改变、或所有会写后跨进程读的验证都改在 `/tmp` 或 CI 上做时。
