# 实测一：用这套方法做一个真实产品

**状态**：进行中
**目的不是做出产品，是找出方法在哪里不够用。**

---

## 为什么要有这份文件

方法是用来「让不写代码的人能做出产品」的。七阶段的每一段都有自己的 exit test，
但**方法整体的 exit test 从来没跑过**：找一个真人、从零走一遍。

这份文件就是那一次。判断它成败的标准不是产品做出来了没有，而是
**最后那张缺口清单有多长、多具体**。

## 测量工具：什么算一个「洞」

只记下面六类。当场记，不事后回忆——事后回忆会把「我顺手补上的」记成「方法写了」。

1. **我不得不发明一个方法没描述的步骤**
2. **我不得不跳过方法描述的某一步**，因为它在这里做不到
3. **两份文档说法不同**，我必须自己选一个
4. **我判断不出这一步做完没有**——exit test 没有区分度
5. **我去用了方法没提到的工具或 skill**
6. **我问了用户一个方法本该回答的问题**

**不算洞的**：方法明确留给我判断的设计决定、我自己不够谨慎犯的错
（后者记成事故，另算）。

## 一条规矩：不许圆场

我在跑的过程中会很想替方法补台阶——「这里它大概是这个意思」。那就是在破坏测量。
每当有这种念头，就停一下，记一行。**圆场的地方就是洞。**

## 环境观察（不计入六类，但影响可用性）

**E1. 这个界面上无法按名字调用 skill。** 方法在多个地方写「用 `/anb`」「用
`anb-design`」，那是 Claude Code 的调用方式；当前环境里 repo 的 skill 不在可调用列表里，
只能读文件再照做。对这轮试跑影响不大（我读得懂文件），但它意味着
**「方法的入口」和「用户手上的界面」不总是同一个东西**。真实交付时要面对这个问题。

**E2. 这一轮测不了「陌生人的困惑」。** 用户是方法的作者，知道七个阶段长什么样。
所以下面记录的是「方法在真实工作里够不够用」，不是「一个没听过的人能不能跟上」。
后者需要真人，是这次刻意没做的那条路。

| — | 需求 | 让用户给出一个想法 | 用户让我提供选题。**非洞**：方法有处方（「给几个具体选项，让他挑」），照做即可 | — |

| 2 | 需求 | 问第 3 问「现在怎么办、为什么更糟」 | 方法同时要求 **「一次问一个问题」** 和 **第 3 问含两件事**。我按方法作为一问提出，用户只答了前半，得再问一次 | 3 |
| 3 | 需求 | 走 exit test（用 agent 扮演陌生人） | 陌生人准确复述出「做什么用」和「给谁用」——**exit test 按字面是通过的**。但它同时说「不知道打开之后它给我的是什么」。方法规定产出是「一页五句话」，**这五句里没有「产出什么」的槽位**；第 4 句问的是能力，不是产物 | 1 |

| 4 exit test 分辨不出 | 0 | 见下方说明 |
| 5 用了方法没提到的工具 | 0 | — |
| 6 问了方法本该回答的问题 | 0 | — |

**值得注意的是：没有一条是「方法说错了」。** 七条全是「方法少了一块」或「方法自己前后不一致」。
它的推理没出问题，**它的产出模板有洞**。

**第 3 条算不算类型 4（exit test 分辨不出）**：我判不算。exit test 问的是「他能复述出用途和对象吗」，
陌生人做到了，测试按自己的标准是有效的。问题在于**它问的维度和实际缺口不是一个**——
通过了，而描述仍然不可执行。这是比「测试太松」更隐蔽的一种失效，值得单列一类，
但六类里没有它的位置。**这本身可能算第 9 个洞。**

## 方法说中的地方（正面结果）

方法的价值不只在缺口里，也在它预测对的地方。这一轮有四处：

1. **「第 5 句是你最想跳过的」——当场兑现。** 我问「你们的售后政策成文吗」，用户跳过它、
   转头回答了我顺手给的六条示例。
2. **「给具体选项，让他挑」这个处方是有效的。** 我在第 3 问猜错了（猜他在用通用大模型，
   实际是翻历史对话），用户直接纠正了我。**猜错能被纠正，说明处方按预想工作。**
3. **重议条件这个机制比它原本的用途更通用。** 判断点数谈不拢（第 5、6 笔）时，
   最后是靠设计阶段另一处的「什么情况说明这个设计错了」收场的。
4. **`design.mjs` 正确拒绝了草稿记录。** `constraints D-002` 报「no confirmed design record」——
   一个还在 `drafting` 的设计不会被下游当成规格读走。语义在没有人为干预的情况下生效了。

**格式也没卡手**：`work/requirements/`、`work/designs/`、`work/tickets/` 三个寄存器
在这一轮里第一次被真正使用，写入格式都不需要解释。

## 方法在试跑中途被改过

第 7 条缺口当场修了（`drafting` 允许缺块，但已写出的块仍受约束）。
**后续阶段的记录因此是针对一个打过补丁的方法**——这一点必须留着，
否则后面「方法没卡住」的结论会不准确。

修复本身也出了一次错：第一版豁免写成「草稿阶段整条跳过」，把草稿变成规则管不着的角落，
于是「拒绝清单写成价值观」在草稿阶段也能蒙过去。**被上一轮加的一条既有测试当场抓出。**

## 试跑停在哪里

| 阶段 | 状态 |
|---|---|
| 需求 | 六句话齐、已落盘。**exit test 未通过**（需要真人，这个对话里没有） |
| 设计 | 四块都写了，**但第 2 块被 T-005 阻塞**——拒绝清单需要那份拢好的政策 |
| 开发及以后 | 未开始。设计没到 `confirmed`，按方法就不该往下走 |

**这是一个真实的停顿，不是绕路。** 方法正确地识别出「政策散在几处」是个问题，
正确地把它变成了跨会话的票（T-005），然后就**停在了它的第一个硬门之前**——
因为设计记录到不了 `confirmed`，而 `confirmed` 是下游能读它的前提。

换句话说：**试跑没有失败，它撞上了真实世界，并且停下来等了。** 而不够用的地方是——
方法不知道该怎么「等」：`drafting` 表达不了「尽力了、在等一件外部的事」。
