# 实测一：用这套方法做一个真实产品

**状态**：已收尾。需求阶段走完（exit test 未通过）；设计阶段三轮未通过 exit test；**验收阶段未触及。**
**目的不是做出产品，是找出方法在哪里不够用。**

---

## 结论

**十二笔缺口，零笔是「方法对某事判断错了」。** 输的全是产出模板：少一格、多一个词、
或者两处话说不到一起。它的推理没输过。

### 还没修的三条，按「便宜 × 影响」排

**一、没有任何东西检查几块之间是否互相成立。（第 12 笔，影响最大）**

五块是各自独立回答的五个问题。唯一会比较它们的是 exit test，而它只给一个数字，
说不出「第 3 块和第 5 块打架」。三轮实测里，硬矛盾全部是跨块的：
政策行要求权限表里不存在的动作（C3）、逐句依据让某个状态永远不可达（C1）。

*改法*：exit test 的产出从「猜了几处」改成两样——**猜了几处，以及哪几块互相冲突**。
后者不是零，就等于没做完，不管前者多小。这是一句话的事，而它对应三轮证据。

**二、「拒绝清单」这个名字装不下它的内容。（第 11 笔）**

实测的十一行里，只有一行是真正的拒绝（不答），其余十行是「这种情况该怎么答」。
按名字实现，会把「3 个月不能用，且不要给建议」那一行做成升级——而它明写不升级。

*改法*：把第 2 问拆成两问——「**它必须拒绝什么**」（短，是禁令）和
「**每一种情况该怎么答**」（一张决策表）。它们确实是两样东西，而决策表需要的是表格形状，
不是清单形状。代价是块数从五变六。

**三、exit test 的隔离无法保证。（第 9 笔）**

方法要求「不给别的上下文」，但没有东西能保证这一点——第一轮那个 agent 有工具，
它自己去读了仓库，报告第一句就承认了。

*改法*：方法里已经有一个现成的机制——路由那处的「部分验证」，用于「exit test 需要
一个你手上没有的东西」。设计阶段的 exit test 也该用它：**拿不到隔离，就记成部分验证，
写清缺什么**，而不是当作完整证据。不需要新机制，只需要把已有规则接上去。

### 它说中的地方（这些同样是结论）

- **「第 5 句是你最想跳过的那一句」——当场兑现。** 问「售后政策成文吗」，用户跳过它去回答了示例。
- **「给具体选项让他挑」这个处方是有效的。** 我在第 3 问猜错了（猜他在用通用大模型，
  实际是翻历史），用户直接纠正了我——**猜错能被纠正，说明处方按预想工作。**
- **重议条件这个机制比它原本的用途更通用。** 一个跟设计无关的争论（判断点几处），
  最后是靠设计记录的「什么情况说明这个设计错了」收场的。
- **`design.mjs` 主动拒绝把草稿当规格读。** 没有人为干预。
- **状态机拒绝了 `open → awaiting-verification`**，逼我走 `in-progress`。它是对的。

### 试跑自己证明了方法的价值

**十二笔里，前三轮内部打磨一笔都没碰到。** 逐条核对两遍、一个独立审查员、九道门禁全绿——
全都发现不了「产出模板缺一格」，因为**你读不出没写的东西**。只有真跑一个产品才撞得到。

### 这次没测到的（不假装它不存在）

- **验收阶段完全没碰到。** 那是方法唯一的硬门，也是它宣称自己最有价值的地方。
  它需要一个能通过 exit test 的设计才谈得上，而试跑三轮都没做出来。
- **测不了「一个陌生人能不能跟上」。** 用户是方法的作者。要测那个，需要一个没听过这套东西的人。
- **三行政策是「用户确认、未经实例验证」** —— 即无法判断，不是通过。
- **试跑中途改过方法**（第 7 笔当场修）。后续阶段跑的是打过补丁的方法。

## 为什么要有这份文件

方法是用来「让不写代码的人能做出产品」的。七阶段的每一段都有自己的 exit test，
但**方法整体的 exit test 从来没跑过**：找一个真人、从零走一遍。

这份文件就是那一次。判断它成败的标准不是产品做出来了没有，而是
**最后那张缺口清单有多长、多具体**。

## 测量工具：什么算一个「洞」

只记下面六类。当场记，不事后回忆——事后回忆会把「我顺手补上的」记成「方法写了」。

1. **我不得不发明一个方法没描述的步骤**
2. **我不得不跳过方法描述的某一步**，因为它在这里做不到
3. **两份文档说法不同**，我必须自己选一个
4. **我判断不出这一步做完没有**——exit test 没有区分度
5. **我去用了方法没提到的工具或 skill**
6. **我问了用户一个方法本该回答的问题**

**不算洞的**：方法明确留给我判断的设计决定、我自己不够谨慎犯的错
（后者记成事故，另算）。

## 一条规矩：不许圆场

我在跑的过程中会很想替方法补台阶——「这里它大概是这个意思」。那就是在破坏测量。
每当有这种念头，就停一下，记一行。**圆场的地方就是洞。**

## 环境观察（不计入六类，但影响可用性）

**E1. 这个界面上无法按名字调用 skill。** 方法在多个地方写「用 `/anb`」「用
`anb-design`」，那是 Claude Code 的调用方式；当前环境里 repo 的 skill 不在可调用列表里，
只能读文件再照做。对这轮试跑影响不大（我读得懂文件），但它意味着
**「方法的入口」和「用户手上的界面」不总是同一个东西**。真实交付时要面对这个问题。

**E2. 这一轮测不了「陌生人的困惑」。** 用户是方法的作者，知道七个阶段长什么样。
所以下面记录的是「方法在真实工作里够不够用」，不是「一个没听过的人能不能跟上」。
后者需要真人，是这次刻意没做的那条路。

## 设计阶段 exit test 的三轮结果

方法规定：把四块交给一个 agent、数它猜了几处、**零处才算做完**；「两轮正常，
超过三轮说明缺的是整整一块」。

| 轮次 | 猜测 | 矛盾 | 材料 | 变量 |
|---|---|---|---|---|
| 1 | 12 | 6 | 四块 | **读了仓库，污染**——方法要求「不给别的上下文」，但没有东西能保证这一点（第 9 笔） |
| 2 | 8 | 9 | 五块（补产出形态） | 无工具，隔离成功 |
| 3 | 7 | 7（3 硬 + 4 软） | 五块 + 统一词汇 + 补六处 | 无工具。**只修我写错的地方，方法一个字没动** |

第 3 轮是对照实验，用来分开两个假设：矛盾高是因为「方法形状不对」，还是因为「我写得烂」。
答案是**两者都有，而后者只解释了一部分**——统一词汇和补上缺口把 9 降到 7，但三处硬矛盾
是结构性的，写得多细都不会消失。

**第 3 轮之后仍然存在的三处硬矛盾：**

- **C1**：第 4 块要求「每句都标依据」，第 5 块要求「可发候选」这个状态存在。字面执行，
  任何含问候语的草稿都必然有无依据句 → **可发候选永远不可达**。材料没有裁决。
- **C2**：第 2 块开头我说「唯一一行真正的拒绝是医疗安全类」，而表里第 6、10 行也是硬升级
  （草稿不出）——它们也没有「答」。我的概括和我的表打架。
- **C3**：政策条款要求的动作超出动作权限表（见上）。

**值得注意的是：没有一条是「方法说错了」。** 七条全是「方法少了一块」或「方法自己前后不一致」。

**第 3 条算不算类型 4（exit test 分辨不出）**：我判不算。exit test 问的是「他能复述出用途和对象吗」，
陌生人做到了，测试按自己的标准是有效的。问题在于**它问的维度和实际缺口不是一个**——
通过了，而描述仍然不可执行。这是比「测试太松」更隐蔽的一种失效，值得单列一类，
但六类里没有它的位置。**这本身可能算第 9 个洞。**

## 方法说中的地方（正面结果）

方法的价值不只在缺口里，也在它预测对的地方。这一轮有四处：

1. **「第 5 句是你最想跳过的」——当场兑现。** 我问「你们的售后政策成文吗」，用户跳过它、
   转头回答了我顺手给的六条示例。
2. **「给具体选项，让他挑」这个处方是有效的。** 我在第 3 问猜错了（猜他在用通用大模型，
   实际是翻历史对话），用户直接纠正了我。**猜错能被纠正，说明处方按预想工作。**
3. **重议条件这个机制比它原本的用途更通用。** 判断点数谈不拢（第 5、6 笔）时，
   最后是靠设计阶段另一处的「什么情况说明这个设计错了」收场的。
4. **`design.mjs` 正确拒绝了草稿记录。** `constraints D-002` 报「no confirmed design record」——
   一个还在 `drafting` 的设计不会被下游当成规格读走。语义在没有人为干预的情况下生效了。

**格式也没卡手**：`work/requirements/`、`work/designs/`、`work/tickets/` 三个寄存器
在这一轮里第一次被真正使用，写入格式都不需要解释。

## 修复情况（试跑结束后一次性处理）

八条缺口全部修了。改动落在 skill 的产出模板、需求寄存器、和站点上。

| # | 修法 |
|---|---|
| 1 | `anb-idea` 的「会出错的地方」加了一节：**全部同意是一个信号，不是成功**。做法是追问一个只有他能给的具体事实——上个月哪一次、那个人是谁、数字是多少。「经得起一个具体实例的建议答案，本来就是他的；经不起的，是你的。」 |
| 2 | `anb-idea` 的「怎么跑」写明：**第 3 句是两个问题，要问两遍**。并且第二遍必须问到「上个月具体哪一次」——「很慢」对什么都成立，什么都决定不了。 |
| 3 | 产出模板加了一句：**它给你什么**（产物，不是能力）。要求写成一个**能用手的名词**。exit test 也从两维改成三维：用途、对象、**以及它会还给他什么**。 |
| 4 | 需求寄存器加 `awaiting-verification`，位置在 drafting 与 confirmed 之间，用词与票据完全一致。验收没过就打回 drafting 重写——和票据的 `awaiting-verification → in-progress` 同形。R-001 已经移进去了。 |

| 7 | 代码已当场修（`drafting` 允许缺块，但已写出的块仍受约束）。skill 里补上了这条说明，否则下一个人还会以为「四块齐备」是从一开始就要求的。 |
| 8 | `anb-design` 第 2 问加了一问：**这份清单从哪来**。三种答案——在一处、完全不存在、**存在但散在几处**。第三种情况明确：拢成一份是跨会话的工作，它是一张票，而这一块在票做完之前**是阻塞的**；并写明不要凭记忆写拒绝清单。 |

**还有一个我自己加的、不算在那八条里的观察**：exit test 通过了、而产出仍然不可执行——
它问的维度和实际缺口不是一个。第 3 条的修法顺带处理了它（exit test 加了第三维）。
但「测试做对了它声称做的事，却问错了维度」这一类比「测试太松」更隐蔽，
方法自己的六类误判里没有它的位置。**这一条我没有动**，留着。

## 方法在试跑中途被改过

第 7 条缺口当场修了（`drafting` 允许缺块，但已写出的块仍受约束）。
**后续阶段的记录因此是针对一个打过补丁的方法**——这一点必须留着，
否则后面「方法没卡住」的结论会不准确。

修复本身也出了一次错：第一版豁免写成「草稿阶段整条跳过」，把草稿变成规则管不着的角落，
于是「拒绝清单写成价值观」在草稿阶段也能蒙过去。**被上一轮加的一条既有测试当场抓出。**

## 试跑停在哪里

| 阶段 | 状态 |
|---|---|
| 需求 | 六句话齐、已落盘。**exit test 未通过**（需要真人，这个对话里没有） |
| 设计 | 四块都写了，**但第 2 块被 T-005 阻塞**——拒绝清单需要那份拢好的政策 |
| 开发及以后 | 未开始。设计没到 `confirmed`，按方法就不该往下走 |

**这是一个真实的停顿，不是绕路。** 方法正确地识别出「政策散在几处」是个问题，
正确地把它变成了跨会话的票（T-005），然后就**停在了它的第一个硬门之前**——
因为设计记录到不了 `confirmed`，而 `confirmed` 是下游能读它的前提。

换句话说：**试跑没有失败，它撞上了真实世界，并且停下来等了。** 而不够用的地方是——
方法不知道该怎么「等」：`drafting` 表达不了「尽力了、在等一件外部的事」。
