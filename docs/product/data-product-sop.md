# 8+3 实现 SOP：49 格「三件事」

**状态**：骨架。每格只写三件事，不写完整 SOP。
**为什么只写三件**：完整 SOP 里有相当一部分**现在写不出来**——跨源去重阈值要真实数据标定，
情感打标准确率要金标准集才知道。而这三件在没有真实数据时就能写，跑起来后补细节。

---

## 零、8+3 的产物分三类，不是统一写成 SKILL

7+1 能做成 SKILL，是因为它每个板块都是**同一类东西**：一次会话能完成、产出落进一个寄存器。

8+3 的八层不是。照搬会出现两个无用的 skill（采集、存储），因为它们描述的是「写一个幂等抓取器」。

| 类别 | 哪些格 | 产物形态 | 为什么 |
|---|---|---|---|
| **决策类** | 标签体系、指标口径、模型设定、结论卡、证伪条件 | **skill + 提示词**，同 7+1 | 是人做的判断，需要会话引导 |
| **工程类** | 抓取、存储、指标计算、下钻 UI | **检查器 + 接口契约**，不写 skill | 是代码，需要可执行的验收 |
| **运行类** | 三柱监控、证伪检查、漂移告警 | **定时脚本 + 告警定义** | 长期跑，需要无人值守 |

**这张分类表是后面所有格子的写作模板**：格子属于哪一类，就按那一类的形态交付。

---

## 一、每格必须写的三件事

```
输入契约   它需要什么，格式是什么，谁保证
输出契约   它产出什么，带哪些版本字段
失败模式   什么情况说明它错了，怎么测出来
```

**三件事都必须是可判定的**。「输出质量要高」不是契约，「输出带 schema_version + 口径版本」是。

## 二、49 格（由 `docs/product/matrix.json` 生成）

**这一节不手写。** 它由 `node scripts/sop-render.mjs` 从 `matrix.json` 生成，
`node scripts/sop-render.mjs --check` 会核对两者一致。理由是这个仓库已经犯过一次：
同一个事实写在四处，改了一处其余三处没跟上，于是出现了一条反向指令。

格子数是 **49**：采集 6 格、存储 6 格、打标 6 格、指标 7 格、分析 6 格、呈现 5 格、结论 7 格、报告 6 格。

### 2.1 采集层（6 格）

**设计 · 采集**｜决策类
- **输入**：需求阶段的「声量由哪些源合成」
- **输出**：源清单（源 × 用途 × 可回溯深度 × 成本）、抓取节奏表、去重指纹方案、首次见到字段定义
- **失败**：源清单里出现「为了以后可能有用」的源；或某源的可回溯深度写不出来

**开发 · 采集**｜工程类
- **输入**：需求阶段定下的源清单，每源带可回溯深度与成本上限
- **输出**：每个源一个 adapter，统一输出 {raw, first_seen_at, fetched_at, source_task_id}；原始载荷原样存
- **失败**：同一批数据跑两次得到不同 `first_seen_at`；或抓到的东西缺 `fetched_at`

**验收 · 采集**｜工程类
- **输入**：两天同批抓取的数据
- **输出**：时滞检查报告（同一帖子两次抓取的互动量差）、去重率、缺抓率
- **失败**：去重率异常低（说明跨源重复没处理）或时滞方差大（说明抓取节奏不稳）
- **检查器**：`node scripts/collect-audit.mjs <ledger.jsonl>`
  - 退出码：0 通过 / 1 失败 / 2 无法判断
  - 时滞跨区域离散、指纹召回率、按源四态计数

**运营 · 采集**｜运行类
- **输入**：每日抓取结果
- **输出**：三态计数（抓到了 / 抓错了 / 无法判断）+ 今天各源成功率
- **失败**：连续两天某源成功率 0 而无告警

**迭代 · 采集**｜决策类
- **输入**：运营期的源表现（成本、覆盖率、可回溯深度）
- **输出**：新增/停用源的 ADR
- **失败**：加了源但没写「它替代了谁的什么职责」

**管理 · 采集**｜运行类
- **输入**：源故障
- **输出**：INC- 记录（严重性、影响哪些结论、恢复时间）
- **失败**：事故记成票（票是打算做的事，事故是发生了的事）

### 2.2 存储层（6 格）

**设计 · 存储**｜决策类
- **输入**：四类归属命名空间决定（见 design §三·五）
- **输出**：schema（含 schema_version / taxonomy_version / 口径版本 三列）、增量/全量分区策略、保留原始载荷的存储位置
- **失败**：schema 里有一列解释不出它属于哪一类命名空间

**开发 · 存储**｜工程类
- **输入**：adapter 输出的观察记录流，含 raw 与两个时点
- **输出**：建表 + 迁移脚本；原始载荷压缩存；**重跑不重写历史**
- **失败**：重跑一次把 `first_seen_at` 覆盖了

**验收 · 存储**｜工程类
- **输入**：两次全量重跑
- **输出**：一致性报告（第二次是否改写了历史记录）
- **失败**：任何历史字段被改写 → 直接不通过
- **检查器**：`node scripts/collect-store.mjs verify <ledger.jsonl>`
  - 退出码：0 不变量成立 / 1 有结构性错误
  - first_seen_at 不被重写、空抓留记录、迁移是读侧透镜

**运营 · 存储**｜运行类
- **输入**：库的实际状态
- **输出**：增长速率、存储成本、重复率
- **失败**：增长速率异常（说明去重失效或重复抓取）

**迭代 · 存储**｜决策类
- **输入**：schema 变更需求
- **输出**：迁移 ADR + 旧数据保留策略
- **失败**：迁移 ADR 没写「旧版本数据还能不能查」

**管理 · 存储**｜决策类
- **输入**：迁移
- **输出**：ADR（永久记录）
- **失败**：迁移写进票而不是 ADR（ADR 是历史，票是工作）

### 2.3 打标层（6 格）

**设计 · 打标**｜决策类
- **输入**：指标层要求的标签清单
- **输出**：标签体系（层级 + 定义 + 版本策略）、置信度口径、金标准集抽样方案、Kappa 阈值
- **失败**：某个标签写不出「什么情况算不适用」

**开发 · 打标**｜工程类 + 决策类
- **输入**：标签体系
- **输出**：标注流水线（打标 + 置信度 + 版本写入）、金标准集 runner
- **失败**：标注结果没有 `taxonomy_version`

**验收 · 打标**｜决策类
- **输入**：金标准集（人工标）
- **输出**：准确率、Kappa、按置信度分层的准确率
- **失败**：准确率 < 0.7 → 该维度不可用，A2+/A2− 退化为 A1；Kappa < 0.6 → 标签定义有歧义

**运营 · 打标**｜运行类
- **输入**：持续标注结果
- **输出**：准确率漂移监控（按周）、置信度分布
- **失败**：准确率连续两周下降而无告警

**迭代 · 打标**｜决策类
- **输入**：标签需要改版
- **输出**：新版本 + 显式映射表（不静默合并）+ ADR
- **失败**：旧数据被重写，或跨版本查询没有分组

**管理 · 打标**｜决策类
- **输入**：标签改版
- **输出**：ADR + 设计记录更新
- **失败**：改版只改了代码，没留下为什么

### 2.4 指标层（7 格）

**需求 · 指标**｜决策类
- **输入**：决策者要做的决定（从结论层 C1–C4 来）
- **输出**：这个决定需要哪几个数字，各自容许的误差量级；不需要的数字明确列出
- **失败**：把「能算的所有数字」当成需求清单；或某个数字写不出「错了会怎样」

**设计 · 指标**｜决策类
- **输入**：需求阶段的「决策需要哪些数字」
- **输出**：指标卡（八项必有字段），三族清单，**A2+/A2− 拆分**
- **失败**：任一指标卡缺「已知偏差」或「什么时候不可用」

**开发 · 指标**｜工程类
- **输入**：指标卡
- **输出**：计算逻辑，每个数字带 口径版本
- **失败**：同一个指标在两处实现有不同定义

**验收 · 指标**｜工程类
- **输入**：两处独立实现的同一指标
- **输出**：对账报告
- **失败**：两处数字不一致 → 直接不通过。另：分母异常检测（某周分母骤降）
- **检查器**：`node scripts/metric-card.mjs check`
  - 退出码：0 八项齐 / 1 有缺项或空话
  - 模板本身会被判失败——八个小标题什么也没证明

**运营 · 指标**｜运行类
- **输入**：每日计算
- **输出**：三态（算出来了 / 算错了 / 无法判断）+ 分母规模监控
- **失败**：某天指标缺失而无告警

**迭代 · 指标**｜决策类
- **输入**：口径需要变更
- **输出**：新版本号 + 新旧对应说明；**旧数据不重算**
- **失败**：变更后跨期比较没有标注版本差异

**管理 · 指标**｜决策类
- **输入**：口径变更
- **输出**：ADR + 设计记录
- **失败**：变更没留下为什么

### 2.5 分析层（6 格）

**设计 · 分析**｜决策类
- **输入**：C1–C4 要证伪什么
- **输出**：模型设定（面板、固定效应、控制变量清单、滞后范围）+ **§七 kill switch**
- **失败**：控制变量清单里没有缺货率

**开发 · 分析**｜工程类
- **输入**：模型设定
- **输出**：最小版（2 区域 × 12 周）→ 加控制变量版
- **失败**：跑出来没有区间，只有点估计

**验收 · 分析**｜工程类
- **输入**：真实数据
- **输出**：§七 相关性报告、区间是否跨 0、稳健性（分置信度分层）
- **失败**：相关性 > 0.8 → 停；区间跨 0 → 标「无结论」而不是「效应弱」
- **检查器**：`node scripts/region-corr.mjs <data.csv>; node scripts/panel-fit.mjs <panel.csv>`
  - 退出码：0 成立 / 1 识别不成立 / 2 无法判断 / 3 无结论
  - §七 是前置门禁；区间跨 0 是「无结论」不是「效应弱」

**运营 · 分析**｜运行类
- **输入**：每周重估
- **输出**：收敛性、系数稳定性
- **失败**：系数符号在两周之间翻转而无告警

**迭代 · 分析**｜决策类
- **输入**：新一年数据 / 新源
- **输出**：重估 + 与旧结论对比
- **失败**：重估后没说明旧结论是维持、修正还是推翻

**管理 · 分析**｜决策类
- **输入**：模型设定变更
- **输出**：设计记录（不是 ADR——它会变，会被 superseded）
- **失败**：写进 ADR（ADR 不该再改）

### 2.6 呈现层（5 格）

**设计 · 呈现**｜决策类
- **输入**：分析输出的形状
- **输出**：下钻路径、口径版本显示位置、三态可见性方案
- **失败**：某个聚合数找不到下钻路径

**开发 · 呈现**｜工程类
- **输入**：带区间的分析结果，每个数字附口径版本
- **输出**：下钻 UI
- **失败**：数字旁边不显示口径版本

**验收 · 呈现**｜工程类
- **输入**：上线后的界面
- **输出**：逐个数点一遍，确认每个能下钻到明细
- **失败**：任何一个数字点不下去 → 不通过

**交付 · 呈现**｜工程类
- **输入**：可运行的界面
- **输出**：别人能打开的地址
- **失败**：只有本机能开

**运营 · 呈现**｜运行类
- **输入**：访问日志
- **输出**：有人看吗（访问量、下钻深度）
- **失败**：上线两月零访问而无告警

### 2.7 结论层（7 格）

**需求 · 结论**｜决策类
- **输入**：一句话想改变的动作
- **输出**：★C1–C4 四条结论的骨架 + 决策 + 停止信号（什么情况下不投）
- **失败**：只有「想了解」没有「会改变哪个动作」；停止信号写不出来

**设计 · 结论**｜决策类
- **输入**：C1–C4 + 决策 + 停止信号
- **输出**：结论卡六项模板 + 证伪条件**可执行化**
- **失败**：证伪条件写成「如果结论错了」

**开发 · 结论**｜工程类
- **输入**：卡模板
- **输出**：结论卡存储（含状态：active / superseded）
- **失败**：状态只有「已发布」，没有「被推翻」

**验收 · 结论**｜决策类
- **输入**：每条结论卡
- **输出**：逐条确认证伪条件能被一条命令执行
- **失败**：任一条执行不了
- **检查器**：`node scripts/verify-conclusion.mjs <conclusions.json>`
  - 退出码：0 全成立 / 1 有结论被证伪 / 2 有检查无法判断
  - 每条证伪条件是一个纯函数，能被触发

**运营 · 结论**｜运行类
- **输入**：决策者的实际使用
- **输出**：被使用次数、被反驳次数、被推翻次数
- **失败**：只统计「看了」，不统计「据此做了什么」

**迭代 · 结论**｜决策类
- **输入**：被推翻的结论
- **输出**：superseded + 新结论 + 为什么推翻
- **失败**：直接删掉旧结论（那就失去了「我们错过什么」的记录）

**管理 · 结论**｜决策类
- **输入**：结论卡
- **输出**：设计记录；被推翻走 superseded 状态迁移
- **失败**：改写原件而不是新增

### 2.8 报告层（6 格）

**设计 · 报告**｜决策类
- **输入**：证伪条件清单
- **输出**：证伪检查的跑批频率 + 失败通知路径 + 报告节奏
- **失败**：证伪检查只在「有人想看」时跑

**开发 · 报告**｜工程类
- **输入**：结论卡：主张、范围、区间、依据、证伪条件、决策含义
- **输出**：证伪检查脚本 + 推送通道
- **失败**：检查失败时不通知

**验收 · 报告**｜工程类
- **输入**：人为造一次证伪触发
- **输出**：看它报不报
- **失败**：造了触发不报 → 不通过。这是整个报告层的唯一实质验收
- **检查器**：`node scripts/verify-conclusion.mjs <conclusions.json>`
  - 退出码：0 全成立 / 1 有结论被证伪 / 2 有检查无法判断
  - 报告层唯一的实质验收：造一次触发，看它报不报

**交付 · 报告**｜工程类
- **输入**：推送通道
- **输出**：飞书 / 邮件可达
- **失败**：需要人手动转发

**运营 · 报告**｜运行类
- **输入**：发送记录
- **输出**：发了多少、有没有回应、有没有人因为某条报告改了做法
- **失败**：只统计发送量

**管理 · 报告**｜决策类
- **输入**：证伪检查的触发
- **输出**：INC 记录（触发了哪一条、影响哪些结论、谁被通知）
- **失败**：证伪触发记成票（票是打算做的事，事故是发生了的事）

## 三、三条纵向链优先做

不按格子做，按链做。选出三条，每条打穿。

| 链 | 层 | 走了几跳 | 现在的状态 | 为什么选它 |
|---|---|---|---|---|
| **链 A：采集 → 存储** | 采集 + 存储 | 2 跳 | 4 格有检查器 | 地基。**时滞与历史改写是静默错误**，最晚发现代价最大 |
| **链 B：指标 → 分析** | 指标 + 分析 | 3 跳 | 2 格有检查器 | **§七 与 区间跨 0 是产品的生死线**，越早知道越好 |
| **链 C：结论 → 报告** | 结论 + 报告 | 2 跳 | 2 格有检查器 | 决定产品是「dashboard」还是「报告」 |

栏里的数字由 `matrix-check --json` 算出来，不手填——手填就会过时，而过时的数字和新鲜的
数字长得一模一样。

**不选呈现**。它最简单，测不出方法。

## 四、顺序（与 design §8.4 一致）

1. **§七 相关性检查**（1 天，不过就停）
2. **链 B 最小版**（2 区域 × 12 周，只产出一个带区间的数）
3. **链 A**（补采集与存储的契约与检查器）
4. **链 C**（证伪条件可执行化）
5. 补呈现

**每一步都产出一个可被证伪的数，而不是一个「已经搭好的层」。**
