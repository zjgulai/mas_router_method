# 过程与交付的管理：一张多维表格怎么承载 7+1 × 8+3

**状态**：方案。**未改任何代码**，本文是这一轮的交付物。
**适用**：`work/` 里已落盘的事实，投影到飞书多维表格，供人和 AI 同时读写。

---

## 零、为什么现在管不清

三个坐标系被当成同一个用：

| 维度 | 唯一来源 | 数量 |
|---|---|---|
| 阶段（7+1） | `work/schema.yml` | 8 |
| 层（8+3） | `docs/product/matrix.json` | 8 |
| 状态 | 同上 | **5 类实体、17 个状态词** |

17 个词里，`awaiting-verification` 在需求和票据里都出现、含义不同；`confirmed` 在设计里
是定稿、在需求里是验收完毕。一张表只能有一个主轴，其余退成字段或视图。三个轴都想当主轴，
结果是一个都排不出序。

**更危险的一处**：矩阵里的「验」不是「检查通过」，是**「有检查器且脚本存在」**。
49 格里 6 格标着它，而其中没有任何一次真实的运行结果被记下来。

所以这套方案的第 1 步不是建表，是**给「检查结果」造一个来源**。

## 一、HITL 分类：一条轴，四类

分 HITL 有几种常见切法（谁决策、能否撤销、有无证据），但叠在一起就不可排序。
只用一条，因为它是唯一可判定的：

> **这一格要靠什么，才能从「未完成」推到「已完成」？**

| 类别 | 关门条件 | 谁关门 | 格数 | 判据 |
|---|---|---|---|---|
| **命令关门** | 一条命令 exit 0 | **AI 自行** | **6** | 这一格有检查器 |
| **人关门** | 人看产物后说通过 | **AI 推进，人验收** | **32** | 无检查器，且不在需求阶段、不是运行类 |
| **人开门** | 人的回答本身就是输入 | **人必须先答** | **2** | 需求阶段的两格 |
| **无人关门** | 持续跑，只有告警 | **无人，AI 自主** | **9** | 运行类 |

**推导规则必须写成这样，不能按「类别」推：**

```
运行类                        → 无人关门
有检查器                      → 命令关门
否则 阶段 = 需求               → 人开门
否则                          → 人关门
```

第一版按类别推（工程类 → 命令关门），把「开发·采集」判成了命令关门——而**写 adapter
这件事没有任何命令能关它**。它没有检查器。所以判据是有没有检查器，不是类别。

### 四类分别意味着什么

**命令关门（6 格）**：只有验收行的六格。AI 跑命令、读退出码、自己关门，不需要人。
这是唯一可以完全无人值守的一类。

**人关门（32 格）**：AI 可以自己工作很久，但最后一下必须人点头。这是绝大多数格子的形态，
也是「AI 自行决断」与「HITL」的分界最容易搞错的地方——**AI 自行决断的是过程，人决断的是关闭。**

**人开门（2 格）**：需求·指标、需求·结论。AI **连启动都不行**，因为答案是人的输入。
这两格和「人关门」的区别是：人可以让人关门的格子挂着，AI 照样在动；这两格挂着，AI 一步都动不了。

**无人关门（9 格）**：运营八层 + 管理·采集。它们永远没有「完成」，只有「在跑」和「告警」。
把它们标成待办是错的——它们会永远待办。

### 为什么「哪些需要补充」不是第四类

「需要补充」不是一个关门方式，是一个**缺口状态**。它属于字段，不属于分类：

- `缺口 = 缺口`：这个阶段正在进行，却没有票认领（现在 3 格）
- `缺口 = 未到`：产品没上线，运营/迭代/管理的票要等前面走完（现在 18 格）

把它们混进关门方式，会让「无人关门」和「没人做」看起来一样。

## 二、「检查结果」的六个值

| 值 | 含义 | 出现范围 |
|---|---|---|
| **无检查器** | 这一格没有可执行的验收，永远不会有结果 | 43 格，长期 |
| **未运行** | 有检查器，一次都没跑 | 6 格，可能 |
| **通过** | exit 0 | 6 格 |
| **不通过** | exit 1 | 6 格 |
| **无法判断** | exit 2 | 6 格 |
| **无结论** | exit 3 | 6 格 |
| **已确认无法判断** | 人看过，接受这次查不了，**带到期日** | 6 格 |

**「无检查器」和「未运行」必须分开。** 前者是一个决定（这一格不设自动验收），后者是一个待办（去跑一次）。合并成「43+6 格未运行」会让 43 个决定变成 43 个永远做不完的待办。

### 「已确认无法判断」的硬约束

它存在的理由：`collect-audit` 报 exit 2 时，人可能知道原因（刚上线只有一批数据），判它暂时不适用。

**但豁免必须有期限。没有到期日的豁免等于永久豁免**，而永久豁免会让整个「无法判断」机制失效。

三条必填，缺一不可：

1. `等什么`：一句具体的话
2. `豁免到期日`：具体日期
3. `豁免人`：谁批的

到期后自动落回 `无法判断`。这条在同步脚本里实现，不靠人记得。

## 三、`checks.jsonl`：检查结果的唯一来源

**没有它，表格的「检查结果」只能是假的。** 现在磁盘上没有任何地方记录「某个检查器跑过、结果是什么」。

一行一次运行，只追加：

```json
{"cell":"验收·指标","cmd":"metric-card check","at":"2026-10-28T09:12:00Z",
 "trigger":"scheduled","exit":0,"verdict":"passed","evidence":"E-013","note":""}
```

| 字段 | 取值 | 谁写 |
|---|---|---|
| `cell` | `阶段·层`，必须是矩阵里存在的格子 | 脚本 |
| `trigger` | `scheduled`（周频 CI）/ `manual`（人跑） | 脚本 |
| `exit` | 0–3 | 脚本，原样记录 |
| `verdict` | 见下表 | **脚本，不许手填** |
| `evidence` | `E-0NN` 或空 | 手动跑时人写 |

退出码映射固定一处，不许各脚本各写一套：

```
0 → passed          1 → failed
2 → inconclusive    3 → no-conclusion
```

**实测现状**：14 个脚本里 4 个只用 0/1，8 个用 0/1/2，`panel-fit` 多一个 3，`work.mjs` 只有 1。
表格里不能有四种编码方式，所以归一化只在同步层做一次，脚本不改。

## 四、四张表

### 表一：节点（49 行，主表）

字段分三组，**组间用底色区分**，否则人会去改机器字段。

**机器组**（磁盘 → 表，人不可编辑）

| 字段 | 类型 | 取值 |
|---|---|---|
| 节点ID | 文本（主键） | `设计·打标` |
| 阶段 | 单选 | 需求/设计/开发/验收/交付/运营/迭代/管理 |
| 层 | 单选 | 采集/存储/打标/指标/分析/呈现/结论/报告 |
| 类别 | 单选 | 决策类/工程类/运行类/工程类+决策类 |
| 关门方式 | 单选 | 命令关门/人关门/人开门/无人关门 |
| 进度 | 单选 | 无票/未开始/进行中/待验收/已完成/已停用 |
| 缺口 | 单选 | 缺口/未到/— |
| 检查结果 | 单选 | 七个值，见 §二 |
| 触发方式 | 单选 | 定时/手动/— |
| 最近检查 | 日期 | |
| 检查年龄 | 公式 | 见 §五 |
| 检查器命令 | 文本 | |
| 关联票 | 关联 → 表二 | 多对多 |
| 关联证据 | 查找引用 | 经票汇总，见 §六 |

**人组**（表 → 磁盘，反向只回写这四个）

| 字段 | 类型 | 取值 |
|---|---|---|
| 在等谁 | 单选 | 等人/等AI/等外部/不等 |
| 等什么 | 文本 | |
| 负责人 | 人员 | 可多选 |
| 备注 | 文本 | |

`在等谁 = 等AI` 的意思是**在等一条命令的结果**，不是「AI 在干活」。它通常落在 6 个命令关门的格子上。

**进度与检查结果不能合并。** 一格可以 `进度 = 待验收`（票说做完了等人看）而 `检查结果 = 通过`（命令过了）；也可以命令过了但还没人看过。合起来就分不清「东西做完没有」和「命令验过没有」。

### 表二：票

票ID、标题、状态（5 值）、**关联节点**（多对多）、**需要什么**、关联证据、负责人、在等谁、等什么。

`需要什么` 现在只是票正文里的一句话。**必须提出来变字段**——否则 AI 读不出「这张票卡在等一个决定」，而那是它唯一需要知道的事。

### 表三：证据（只增不改）

证据ID、关联票、命令、结果（4 值）、触发方式、原始输出（截断）、时间。

### 表四：事故与决策（合表）

编号（`INC-001` / `ADR-0007`）、类型（事故/决策）、状态、关联节点、摘要、日期。

两者都是计划外或不可逆的东西，看的人相同。分两张表会让两张都没人看。

## 五、五个视图（写死，直接可填）

**① 该我做的** — 每天唯一必开
```
AND( 负责人 包含 当前用户, 进度 ∈ {未开始, 进行中} )
排序：检查年龄 降序, 阶段
```

**② 在等我的**
```
AND( 在等谁 = 等人, 进度 ≠ 已完成 )
排序：检查年龄 降序
```

**③ 红色**
```
OR( 检查结果 ∈ {不通过, 无法判断, 无结论}, 缺口 = 缺口 )
排序：阶段, 层
```
`无法判断` 与 `不通过` 同视图但**不同色**：前者是「查不了」，后者是「查了不通过」。

**④ 待验收队列**
```
进度 = 待验收
排序：最近检查 升序
```

**⑤ 陈旧的绿**
```
AND( 检查结果 = 通过, 检查年龄 > 8 )
排序：检查年龄 降序
```

**阈值定 8 天，不是 7。** 周频 CI 每周一跑，但触发时间会漂几小时；设 7 天会让每次调度擦着阈值，出现「周一早上全变红」的假警报。

**「从未运行」不走天数。** 它没有日期，`TODAY() - 空` 会算成巨大天数，看起来和「过期」一样——而这两件事的动作完全不同：一个是「去跑一次」，一个是「这个东西可能已经坏了」。公式：

```
IF( 最近检查 = 空, "从未", TODAY() - 最近检查 )
```

视图 ⑤ 最容易被忘，也最值钱——**不主动筛，三周前的「通过」和今天的「通过」长得一模一样。**

## 六、CI 的现状与边界（这一条必须先说清）

现有 15 步 CI 里，5 步与检查器有关，但**其中 4 步跑的是 `--demo`**：

```
region-corr --demo ; test $? -eq 1     ← 断言 demo 仍然会失败
panel-fit --demo
collect-audit --demo ; test $? -eq 1
verify-conclusion --demo ; test $? -eq 1
metric-card check                       ← 唯一跑真实数据的一步
```

**`--demo` 的结果不能写进 `checks.jsonl`。** 它验的是「检查器还能抓到已知的错」，是对检查器的测试；而且它规定了必须失败，写进去就是一条假的「不通过」。

所以 CI 分两类：

| 类别 | 现在有几条 | 写 jsonl |
|---|---|---|
| 自检（验检查器还能变红） | 4 | **不写** |
| 真检查（验这一格的状态） | **1**（`metric-card`） | 写，`trigger = scheduled` |

**验收行的其余五格现在没有可跑的真实数据**——它们需要 `<ledger.jsonl>`、`<panel.csv>`，
仓库里没有。所以周频 CI 目前只能产出**一条**真实结果。

这个不能靠改 CI 解决，只能等真实数据。**表格必须能显示这个事实**：显示「6 格有检查器，其中 5 格从未运行」，而不是让它们看起来运行过。

## 七、同步：磁盘为源，表格为投影

### 三条数据流向

| 方向 | 内容 | 触发 |
|---|---|---|
| **正向（自动）** | 磁盘 → 表：格子、票、证据 | 同步脚本 |
| **反向（极窄）** | 表 → 磁盘：`在等谁`、`等什么`、`负责人`、`备注` | 同步先 pull |
| **禁止** | 其余一切从表改磁盘 | 无 |

**为什么必须有反向**：`在等谁` 这个字段在磁盘上没有家，而它恰恰是协作最需要的一列。
只存表格，磁盘就不是唯一来源了；那时一个脚本读磁盘、人看表格，两边对不上，谁对谁错说不清。

所以：**这四个字段写进 frontmatter，反向只读回这四列。** 这是被点名的例外，不是双向同步。
（`work.mjs` 的解析器**已经读 `owner` 字段**，只是票据上没人填——所以加负责人是数据改动。）

### 接口

```
node scripts/bitable-sync.mjs            # pull → 断言 → push
node scripts/bitable-sync.mjs --pull     # 只把人字段拉回磁盘
node scripts/bitable-sync.mjs --push     # 只把机器字段推上表
node scripts/bitable-sync.mjs --dry-run  # 打印将改什么，不写
```

退出码沿用：0 成功 / 1 冲突或行数不符 / 2 无法判断（API 不通、表结构漂移）。

**顺序必须先 pull 再 push。** 反过来的话，push 会用磁盘上过时的人字段覆盖人刚在表里填的东西，
而且不报错——那人只会觉得「我填的怎么没了」。

### 两个白名单，启动时断言不相交

```
MACHINE = [进度, 缺口, 检查结果, 触发方式, 最近检查, 检查器命令, 关门方式]
HUMAN   = [在等谁, 等什么, 负责人, 备注]

assert MACHINE ∩ HUMAN === ∅     // 不成立就拒绝运行
```

`--push` 只写 MACHINE，`--pull` 只读 HUMAN。没有这个断言，某天两边都加了字段，冲突就变成
「谁后写谁赢」——而那种错不会立刻出，会等改了一边忘了另一边才炸。

### 三条硬规则

**一、孤儿不删，标记。** 磁盘上没有的节点，表里标 `缺口 = 孤儿`，不删行。删了之后没人知道它消失过。

**二、行数自报。** 每次同步打印 `磁盘 49 格 → 表内 49 行 → 孤儿 0`。
**一个跑通了但写了零行的同步，和一个成功的同步输出一模一样。**

**三、字段名漂移要报错。** 有人改列名，push 会写到不存在的字段上然后报成功。
同步前比对表结构，字段集合不符就 exit 2。

## 八、17 个状态词 → 5 个

原状态留在磁盘里，表格只显示 5 个：

| 表格值 | 来自 |
|---|---|
| 未开始 | `open` |
| 进行中 | `drafting`、`in-progress`、`active`、`contained` |
| 待验收 | `awaiting-verification` |
| 已完成 | `confirmed`、`done`、`closed` |
| 已停用 | `dropped`、`abandoned`、`expired`、`superseded` |

**`contained` 归「进行中」不归「已完成」**：事故只是控住了，没关闭。这两者的动作不同——
一个是继续盯，一个是复盘。

## 九、实施顺序

**不一次建完，会建出一个没人填的表。**

| 步 | 做什么 | 为什么这个顺序 |
|---|---|---|
| 1 | `work/checks.jsonl` + `scripts/check-run.mjs <cell>` | 没有它，「检查结果」永远只能是假的 |
| 2 | CI 增加真检查步骤（现在只有 `metric-card` 一条） | 周频的第一条真实数据 |
| 3 | `在等谁`/`等什么` 两个 frontmatter 字段 + 票据 `owner` | 三个字段，人工填，无代码 |
| 4 | `work.mjs --json` | 结构化的唯一出口；现在它没有 JSON 输出 |
| 5 | 建表 + 手动导入一次，用两三天 | **先别写同步**，字段一定会改 |
| 6 | `bitable-sync.mjs` | 依赖 4、5 |
| 7 | 通知与提醒 | 最后 |

## 十一、这份方案没解决的问题

1. **`关联证据` 用不用两跳。** 证据只指向票，票才指向节点。飞书的「查找引用」能不能跨两跳（证据 → 票 → 节点）
   我没有你的表可以试。**建表时先试一跳；通不过就由同步脚本算好一个 `关联证据id` 文本字段直接写。**
2. **`验收·指标` 之外的五格没有真实数据。** 表格会显示「5 格未运行」，这不是配置问题，是数据问题。
3. **会议前的临时绿。** `触发方式 = 手动` 能标出来，但挡不住有人只在会前跑一次。这个靠流程，不靠字段。
4. **豁免到期后的自动回落。** 逻辑定了（到期落回 `无法判断`），但依赖同步脚本每天跑一次。
