## 一、四条客观建议（先说，因为它影响怎么读这张图）

### 建议 1：矩阵会把注意力引向横向，而真正的工作在纵向

64 个位置里 **49 格有内容**，真正的交接**落在「开发」这一行内部**：
采集 → 存储 → 打标 → 指标 → 分析 → 结论 → 报告。

跨阶段的横向流转很少，而且大多是「约束」而不是「工作」（设计约束开发、验收检查开发）。
**所以这张图用来分配责任可以，用来排期会出事**——按阶段推进就是瀑布，而瀑布在数据产品上必死。

### 建议 2：空格是信息，而且分两种

64 减 49，空 15 格。但空法不同：

- **不该有**（需求阶段不选数据源；呈现层没有交付就没有运营）→ 正常
- **该有但没人** → **这是漏洞**，见 §四

**只填有内容的格子，等于把漏洞藏起来。**

### 建议 3：三根柱子不是第三个维度，是横切义务

把口径/质量/血缘放进 X 轴，它们看起来就像层。但它们和八层不同类——
**八层是流水线上的工序，三柱是每一层都必须回答的三个问题**。

它们单独在 §三，写「这一层对这根柱子的义务」，不写任务。

### 建议 4：跨层一致性原来没有格子负责——现在有了八跳契约

每一格单独看都对，但**格子之间的一致性没人管**：分析层用的指标，是哪个口径版本的？

这一条原来是「建议加一列」。现在 §五 的八跳衔接把「交的是什么、带哪些版本、下游怎么校验」
写成了数据，`matrix-check` 会检查每一跳都写了版本字段和下游校验，缺一条就报错。
**「建议」变成了「它空着会失败」。**

### 附一条更根本的：运营不是第七个阶段

七阶段流程假设有终点（产品做出来了）。**数据产品没有终点**——它上线之后要跑几年。
所以矩阵里「运营」那一行覆盖的生命周期比其余七行加起来还长，且它在 8 层里
**每一层都有格子（8/8）**，是唯一满行的一行。

**这不是措辞问题。** 它意味着资源分配必须按这个事实来：一次性的建造成本，
对比永久的运行成本（采集额度、标注复核、模型漂移监控）。

## 二、图例

每一格的状态**由脚本算出**，从不手填——手填必然过时，而过时的绿点和真的绿点长得一模一样。

| 符号 | 状态 | 判据 | 含义 |
|---|---|---|---|
| **●** | verified | 有检查器，且命令指向的脚本存在 | 这一格能被证明 |
| **○** | contract | 三件事齐，没有检查器 | **契约在，执行不在**——这个区别必须显示出来 |
| **✕** | hole | 三件事有缺，或写了「同上」 | 这一格是洞 |
| **·** | — | 位置本来就不该有格子 | 正常，见建议 2 |

阶段本身说明了动作，不必在格子里重复：设计=定、开发=建、验收=验、交付=建、运营=跑、
迭代=定、管理=记。

### 三·二、三根柱子（横切义务，不是层）

| 阶段 \ 柱 | 口径 | 质量 | 血缘 |
|---|---|---|---|
| **需求** | · | · | · |
| **设计** | 每个指标一个定义 + 版本策略 | 三态定义；每层各管什么 | 链到哪一跳；每跳带版本 |
| **开发** | 定义进存储，随指标卡走 | 三态采集点 | 记录每个产物的上游版本 |
| **验收** | 同一个数字在两个报表口径一致 | 造故障，看它报「无法判断」还是「正常」 | 从任一结论能点到原始载荷 |
| **交付** | 数字旁显示版本 | 三态对用户可见 | 用户可下钻 |
| **运营** | 版本漂移监控 | 三态计数；第三态 >0 要报警 | 断链检测 |
| **迭代** | 变更 = 新版本，旧数据不重算 | · | 跨版本血缘要接得上 |
| **管理** | 口径变更 → ADR | 质量事故 → INC | · |

**血缘那一列现在被 §五 覆盖了一半**：八跳契约写明了每一跳带什么版本。
剩下没被覆盖的是「从任一结论能点到原始载荷」——那需要一个真正的血缘遍历器，
目前只有 `collect-store view` 能从条目追到原始载荷。

## 五、衔接点：八跳，每跳带版本

| 从 | 到 | 交的是什么 | 带哪些版本 | 下游怎么校验 | 断了会怎样 |
|---|---|---|---|---|---|
| 开发·采集 | 开发·存储 | 观察记录：raw + first_seen_at + fetched_at + source_task_id | schema_version + fetched_at | source_task_id 在账本里有对应的 run；first_seen_at ≤ fetched_at | 没有 first_seen_at → 时间序列锚在抓取时刻，「抓得晚」被读成「更热」 |
| 开发·存储 | 开发·打标 | 去重后的条目 + 四类归属命名空间 + 原始载荷 | schema_version + taxonomy_version | region 落在四值命名空间内；unattributable 至少两个冲突依据 | 归属摊派给 unknown → 分母完整但错，且看起来没有任何问题 |
| 开发·打标 | 开发·指标 | 标签 + 置信度 + taxonomy_version | taxonomy_version + metric_version | 读到的 taxonomy_version 不等于指标卡声明的版本时报警，不许猜 | 标签改版后静默合并 → 去年的数和今年的数不是一个体系，而台阶看不见 |
| 开发·指标 | 开发·分析 | 数值 + 口径版本 + 分母规模 | metric_version + produced_at | 分母骤降时拒绝出结论；口径版本不同的两期不许直接相减 | 口径变更被读成业务变化——最贵的一种错误 |
| 开发·分析 | 开发·呈现 | β + 95% 区间 + 吸收了什么的说明 | 模型设定版本 + produced_at | 区间跨 0 的数字不进聚合视图；「关联不是因果」的标签必须跟着数走 | 交付一个识别不成立的看板，而它看起来完全正常 |
| 开发·分析 | 开发·结论 | C1–C4 + 区间 + 有效样本量 | 模型设定版本 + upstream_versions | 区间跨 0 → 该条结论不许落卡；样本不足 → 降级为描述性 | 结论卡带着一个什么都没有的区间发布 |
| 开发·结论 | 开发·报告 | 结论卡 + 证伪条件（可执行）+ status | 口径版本 + taxonomy_version | 证伪条件必须是已注册的函数名；未注册的名字算「无法判断」不算通过 | 证伪条件写成「如果结论错了」→ 无法被触发，报告退化成 dashboard |
| 开发·报告 | 迭代·结论 | 证伪触发 → 旧结论转 superseded + 新结论 + 为什么推翻 | produced_at | 旧结论原件保留不删；新结论指回旧结论；superseded 不被再次告警 | 直接删掉旧结论 → 失去「我们错过什么」的记录 |

**每一跳都要带版本四元组**：`schema_version` + `produced_at` + `upstream_versions` + `口径版本`。
下游读到陌生的上游版本时**必须报警，不许猜**。

这一条原来是散文。现在它是 `matrix.json` 里的八条 `transitions`，`matrix-check` 会检查：
两端的格子存在、`carries` 非空、`versioned` 非空、`downstreamChecks` 非空、`breaks` 非空。
**缺任何一项就报错**——所以「下游怎么校验」这一列不会退化成「同上」。

## 六、这次改动修了什么（留档，因为数字会再变）

这份文档原来有三处自相矛盾，是把它结构化的时候暴露出来的：

1. **「88 个格子」**：64 加 24。而它自己在建议 3 里说三柱「不是第三个维度」——
   把两样不同类的东西加在一起。现在 64 = 8 × 8，三柱单列。
2. **「48 格」**（SOP 标题）：实际 46，补上三格缺口后是 49。呈现 5 格、报告 5 格，不是 6。
3. **三格在矩阵里有、SOP 里没有**：需求·指标、需求·结论、管理·报告。现在都补了。

**这三处都是同一个病**：同一个事实写在几处，改一处其余没跟上。所以现在只有一个来源，
其余两处靠生成或校验。
