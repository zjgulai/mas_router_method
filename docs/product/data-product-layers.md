# 8+3 的层契约与检查器

**用途**：每层的输入契约、输出契约、失败模式，以及**执行它的那个命令**。
**不用于**：排期。排期在 `data-product-design.md` §8.4。

---

## 一、为什么这份文档必须带命令名

`data-product-sop.md` 写了 48 格的「三件事」，但它有一条自己承认的边界：那三件事
「在没有真实数据时就能写」。写下来之后，怎么知道它跑起来了？

答案只能是：**每一格要么有一个能变红的命令，要么它是一句愿望。**

这不是修辞。这套方法自己的历史里，最贵的三个缺陷形态全都长这样：

- 一条**永远不会失败的检查**（跨块约束写了但没校验）
- 一个**静默停止的断言**（`facts` 里文件读不到就 `continue`）
- 一次**计数变 0 却报绿**（`work status` 数出了 0 张票）

三者的共同点是：**它们看起来和成功一模一样**。所以这份文档每写一条契约，就必须写
出它在哪儿被执行。没有命令的那一行，标 `—`，并且它落在 §五 的未覆盖清单里，不许
安静地留在表格中间。

## 二、三层的契约（链 A：采集 → 存储）

| | 采集 | 存储 |
|---|---|---|
| **输入** | Apify actor 的原始返回 | 适配器输出的观察记录 |
| **输出** | `{raw, first_seen_at, fetched_at, source_task_id, schema_version, taxonomy_version, metric_version}`，加 `run` 记录 | 每个条目一条可查的行：`first_seen_at` 为最早一次，`raw` 为最新一次 |
| **失败模式** | 时滞跨区域不一致；抓取时点缺失；空抓不记录 | `first_seen_at` 被重跑覆盖；迁移后旧记录不可读 |
| **命令** | `collect-audit` | `collect-store verify` |
| **退出码** | 0 通过 / 1 失败 / 2 无法判断 | 0 不变量成立 / 1 有结构性错误 |

### 2.1 三条不变量，和它们各自的理由

**一、`first_seen_at` 不是列，是 `min()`。**

设计写的是「重跑不重写历史」。最省事的保证方式是**根本不存在更新路径**：账本只追加，
`first_seen_at` 在读的时候取最小值。一个**能够**覆盖 `first_seen_at` 的存储，早晚会被
覆盖——一次回补、一次迁移、一次「顺手修一下」。

这条的理由在统计上更硬：互动量随帖子年龄增长。如果时间序列锚在「最后一次抓取」，
那么「抓得晚」会被读成「更热」。而**区域正是要比较的单位**，这个错误不会报任何错。

**二、空抓必须留记录。**

「这周这个源什么都没抓到」和「这周这个源根本没跑」在文件里是同一种缺席，而它们对应的
动作相反。前者是结果，后者是故障。

`collect-audit` 因此把 `ok / partial / error / empty` 四个计数分开列，并把 `empty`
在输出里明确标成「是结果」。**唯一没被覆盖的是「压根没有 run 记录」**——那需要
「本该跑什么」作为独立输入，账本自己推不出来，所以它被写成已知缺口而不是猜成 0。

**三、迁移是读侧的。**

迁移不改写磁盘上的任何一行，它是在文件里追加的一条 `migration` 记录，读的时候套上去。
于是同一批旧记录**带着透镜和不带透镜都读得出来**——而「旧数据还能不能查」正是每个迁移
ADR 都会承诺、几乎没有一个会检查的那句话。

`collect-store migrate` 在写入前先试读一遍：试读丢记录就拒绝迁移。这条不是断言，是检查。

### 2.2 区域命名空间写进了校验，不是写进了注释

`region` 只接受 ISO alpha-2 或 `unattributable` / `insufficient` / `not_applicable`。
`unknown` 会被拒绝——因为设计说得很清楚：`unknown` 永不摊派，而一个能被写进字段的
`unknown`，下一步就会有人按人口比例摊派它。

`region_basis` 的要求是**按值的含义分别给的**，这是第一版写错的地方：

- `US`、`unattributable`、`not_applicable` → 必须有，因为这些都声明了一个判断
- `insufficient` → **不要求**，因为它的全部含义就是「没找到依据」

第一版对这一条一视同仁，于是要求 `insufficient` 提供依据。一条与定义矛盾的检查会教人
**编造一个依据来通过检查**，那比没有检查更糟。这个问题是拿真实载荷跑第一次时撞出来的。

## 三、三层的契约（链 B：指标 → 分析）

| | 指标 | 分析 |
|---|---|---|
| **输入** | 标注记录 + ERP | 指标序列 + 控制变量 |
| **输出** | 数值 + `metric_version`；指标卡八项 | `β` + 95% 区间 + 吸收了什么 |
| **失败模式** | 同一指标两处定义不一致；分母骤降 | 相关性过高识别不成立；区间跨 0 被说成「效应弱」 |
| **命令** | — （见 §五） | `region-corr` / `panel-fit` |
| **退出码** | — | 0 成立 / 1 识别不成立 / 2 无法判断 / 3 无结论 |

### 3.1 §七 是前置门禁，而且它有三个答案

三个区域声量若同步变动，**周固定效应吸收掉的正是信号本身**。所以 `region-corr` 在
动手前跑，并且能说「不行」。

它的第三种答案（exit 2）覆盖这些情况，每一种都会让相关系数变成 `NaN`，而 `NaN` 打印
出来是一个数字的样子：

- 区域少于 2 个、共同周数少于 8
- **一次以上的抓取批次混在一起**（互动量随年龄增长，批次不同等于时滞混入）
- **某个区域序列是平的**——平序列的相关系数是 `NaN`，若按 0 处理，它看起来会像那个
  「变异独立、救了整个设计」的区域

0.5–0.8 落在边界带：**通过，但每条结论必须带着「有效变异有限」这句话**。这是设计
自己给的判定，脚本只是执行它。

### 3.2 面板最小版：一个带区间的数，或者什么都没有

`ln(GMV)_rt = β·ln(声量)_rt + α_r + λ_t + X·γ + ε`

两条纪律是这个脚本存在的理由：

**一、区间跨 0 是「无结论」，不是「效应弱」。** 用 exit 3 表达这个区别，下游管线才
能拒绝发布它。一个跨过 0 的区间看起来像「有这个效应」，实际上什么都没说——而它会以
「弱效应」的名义进一次预算会。

**二、零变异的控制变量会被剔除，并且说出来。** 它与截距共线，矩阵奇异。但奇异只是
症状，真正的发现是「你以为你控制了它，其实没有」。设计 §8.5 第 7 条已经写了这个案例
（预算一年只调一两次），所以脚本打印 `dropped "promo"` 而不是静默忽略。

## 四、三层的契约（链 C：结论 → 报告）

| | 结论 | 报告 |
|---|---|---|
| **输入** | 分析输出 + 血缘 | 结论卡 + 证伪条件 |
| **输出** | 结论卡六项，含 `status: active / superseded` | 每周跑一次证伪检查，触发即通知 |
| **失败模式** | 证伪条件写成「如果结论错了」 | 造了触发不报；只统计发送量 |
| **命令** | `verify-conclusion` | `verify-conclusion --notify` |
| **退出码** | 0 全成立 / 1 有结论被证伪 / 2 有检查无法判断 | — |

### 4.1 证伪条件是函数，不是句子

`conclusion-conditions.mjs` 里七条条件，每条是一个纯函数，输入是一小块固定形状的数据。
这样做唯一的目的：**它能被触发**。「如果结论错了」触发不了；`区间是否跨 0` 能。

三条实现上的取舍：

**一、`triggered: true` 表示结论**死了**，不是检查通过。** 一个名叫 `isWrong()` 的函数
在健康结论上返回 true，早晚有人用反。

**二、无法测量不是成立。** 输入缺字段时返回 `unmeasurable`，而不是 `false`。这是整个
仓库反复在治的同一种病：一个没人看过的绿灯。

**三、`falsified` 压过 `unmeasurable`。** 一条已经知道错的结论，不会因为另一项检查缺
数据而变成「也许」。

### 4.2 报告层唯一的实质验收

设计原话：**造了触发不报 → 不通过。** 所以 `--demo` 这个 fixture 里同时有三条状态不同的
结论（成立 / 被证伪 / 无法判断），测试断言三者同时出现。一个只会全绿的 fixture 测不出
告警。

推送通道**故意没有接**。一个假装送达的通道会让这条验收通过而产品失败——`--dry-run`
打印将要发送的内容，真实发送在没配置时返回错误而不是成功。

## 五、还没被任何命令覆盖的格子

诚实清单。这些格子在 `data-product-sop.md` 里有内容，但没有可执行的东西：

| 格子 | 缺什么 | 为什么现在补不了 |
|---|---|---|
| ~~指标层全部~~ | **已补**：`metric-card.mjs` 判八项齐、空话、占位符、版本号 | 它判不了「定义可不可执行」——实测：一个跨层复合指标八项全填、全绿 |
| ~~打标层校验器~~ | **已补**：`label-audit.mjs` 判准确率、Kappa、置信度反转、金标准集规模 | 它判不了「定义有没有歧义」——只能事后从 Kappa 反推 |
| **`work/labels/` 没有 `work check` 校验** | 标签体系落盘后没有任何检查 | 需要先有一份真实体系才知道校验什么形状 |
| 打标·运营 | 准确率漂移监控（按周） | 需要连续多周的金标准集复测 |
| 呈现层 | 下钻可达性检查 | 需要界面 |
| 采集·迭代/管理 | 源清单的「替代了谁的什么职责」 | 是 ADR 的写作规则，不是数据 |
| 存储·运营 | 增长速率告警 | 需要长期运行 |
| 跨层一致性 | 下游读到陌生上游版本要报警 | **契约写了，没有检查**——这是下一个应该补的 |

最后一条值得单独说：`data-product-matrix.md` §五 要求「每一跳都要带版本四元组，下游
读到陌生的上游版本时必须报警」。这句话现在只有文档在说。按这个仓库自己的判据，它和
一条永远不会失败的检查是同一种东西。
