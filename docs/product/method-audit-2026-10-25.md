# 方法审计：七阶段 + 管理，从局部到体系

**日期**：2026-10-25
**审计对象**：ANB 七阶段 + 管理模块（8 个模块、16 个 skill、21 个站点页、work/ 记录层）
**结论**：结构成立，但**内部不一致**且**交接有断裂**。必修 3 项、应修 6 项。

---

## 口径（影响后面每一个判断）

**这套东西没有任何一个真人用过。** 本文中「已覆盖」只表示产物存在，
永远不表示它有效。这个前提对 8 个模块一视同仁。

---

## 一、逐模块

| 模块 | skill | 提示词 | 验收动作 | 机器校验 | 判定 |
|---|---|---|---|---|---|
| 需求 | 7 | 5 | 3 | 无 | 方法齐，产物不落盘 |
| 设计 | 11 | 9 | 4 | 有 | 方法最完整 |
| 开发 | 9 | 4 | 3 | 无 | 覆盖好，读不到上游 |
| 验收 | 12 | 6 | 3 | 无 | 最厚，接不住设计 |
| 交付 | 6 | 3 | 3 | 无 | 方法在，太薄 |
| 运营 | 8 | 3 | 3 | 无 | 半覆盖（自认） |
| 迭代 | 6 | 3 | 3 | 无 | 站点说覆盖，skill 半覆盖 |
| 管理 | 1 | 4 | 3 命令 | 有 | 结构最扎实，可达性最差 |

### 需求
- **卡点**：把功能清单当需求说；答不出「什么情况说明不该做」。
- **覆盖**：`anb-idea` 正面处理，含第六句「该不该用 agent」。
- **洞**：`work/requirements/` 空，0 条。需求阶段产物不落盘 → 跨会话会丢，
  而「回去改需求」正是最后一环要做的事。

### 设计
- **卡点**：不会设计的人不知从哪下手；容易写成规格；拒绝清单写成价值观。
- **覆盖**：四问 + `work/designs` 机器校验 + exit test（数问题）。目前最完整。
- **洞**：正文交叉引用仍用旧阶段编号；产出**无人消费**。

### 开发
- **卡点**：假数据；特判；提前搭架子。
- **覆盖**：`anb-runnable` 一条最窄的路 + 换一个没预想的输入的 exit test。
- **洞**：**0 次提及设计阶段**，读不到判断点与动作权限。

### 验收
- **卡点**：检查从没红过；跳过算通过；崩溃当通过。
- **覆盖**：唯一硬门 + 7 个检查 skill，最厚。
- **洞**：**0 次提及任何上游产物**，不引用设计记录与拒绝清单。

### 交付
- **卡点**：本机能开≠别人能开；配额撞墙。
- **覆盖**：方法有（密钥/数据/权限/地址四件事）。
- **洞**：提示词仅 3 条，全表最少。对不写代码的人，部署是最硬的墙。

### 运营
- **卡点**：只有技术数字，没有产品数字。
- **覆盖**：技术侧三数字；产品侧明确声明「答不了」。唯一的自觉半覆盖。

### 迭代
- **卡点**：加功能靠猜；模板抽取判据错。
- **覆盖**：**站点与 skill 分歧**——站点 07-iterate 有 4 条分支（含「回到需求」），
  而 `anb-reusable` **0 次提及观测数字**，只讲模板抽取。
- **洞**：自进化闭环在 skill 层未实现。

### 管理
- **覆盖**：状态即目录、只增不改寄存器、三条命令，结构最扎实。
- **洞**：① 从入口不可达 ② 8 个寄存器中 3 个从未使用（requirements/artifacts/receipts）
  ③ `anb-manage` 的「东西放哪」清单里没有 `work/designs/`。

## 二、连接关系（九条逐条测）

| 连接 | 状态 | 证据 |
|---|---|---|
| 需求 → 设计 | 通 | anb-idea 明说 design 阶段会重数判断点 |
| 设计 → 开发 | 断 | anb-runnable 提设计 0 次 |
| 设计 → 验收 | 断 | 见下 |
| 开发 → 验收 | 隐式 | 靠 exit test 承接，无显式引用 |
| 验收 → 交付 | 通 | shipable 引用上游质量标准 |
| 交付 → 运营 | 弱 | observable 未从 shipable 接手 |
| 运营 → 迭代 | 断 | anb-reusable 提观测数字 0 次 |
| 迭代 → 需求 | 断 | skill 层无回环 |
| 任意 → 管理 | 断 | 路由表与决策树都到不了 |

### 最要紧的断裂：设计 → 验收

`anb-design` 在 exit test 承诺「拒绝清单每一行都能写成一条会变红的检查」，
正文说「design 阶段写清单，verify 阶段变成检查」。但接收端 `anb-judgeable`
提及设计 / 拒绝清单 / `D-` 的次数**全为 0**，站点 04-verify 也是 0。

后果：设计阶段最有价值的产出**写完没有任何东西读它**。`work check` 只校验格式。
它退化成文档，不是规格——正是这套方法自己警告过的事。

### 第二要紧：管理不可达

`anb/SKILL.md` 提 `anb-manage` 0 次；`decision-tree.html` 提管理 0 次。
而站点导航里有「管理」。**两个入口互相矛盾。**

## 三、编号：我自己造的 bug

**现状**：阶段编号有两套并存。
站点用「1需求 2设计 3开发 4验收 5交付 6运营 7迭代」；
五个 skill 仍写旧编号（开发 Stage 2 / 验收 Stage 3 / 交付 Stage 4 / 运营 Stage 5 / 迭代 Stage 6）；
站点页正文也混用（「03开发」写着「ANB 阶段 2 覆盖这一步」）。

**危害**：不是读起来怪。`anb` 有一句「Stage 3 是唯一的门，do not build stage 4」。
按站点编号，stage 3 是开发、stage 4 是验收 → 变成**不要做验收**，而验收是唯一的门。
对不写代码的人，自信的错误指令比没有指令更坏。

**根因**：阶段编号存在至少四处——站点 `STAGES`、站点 gapnote、skill 标题、skill 正文交叉引用，
没有单一来源。这套方法的铁律是「每一类信息只有一个家」，它自己的实现违反了。

---

## 四、比编号更靠下的一层：站点的源码不在仓库里

- 7 个生成器（`build_*.py` + `map.py`）只存在于会话临时目录，**不在仓库**
- 无 CI 步骤重建站点；`work/artifacts/` 登记数为 **0**
- `docs/site/` 的 21 个 html 中，**8 个是手写原件**（失败图鉴、决策树、术语表、能力图谱、
  anb-proposal、atlas-test-report、anb2-report、anb2-full），而 LAYOUT.md 称其为
  「生成物，不手改」
- `out/docs/` 是废弃的暂存副本（docs.html 实际链接的是扁平路径）

**后果**：站点实际上无法重建，只能手改 HTML——正是 LAYOUT.md 禁止的事。
这条不修，「单一来源」到不了站点，下一次改编号还会再错一次。

## 五、对照三个目标

1. **不会写代码的人会做产品** —— 大体成立。最薄的是交付。
2. **不会做设计的人会用提示词做设计** —— 结构对了，闭环没接上。设计 9 条提示词最厚，
   但覆盖的是「问什么」，没覆盖「答不上来怎么办」；产出无人消费。
3. **不会项目管理的人能轻松管理、自进化** —— **差距最大**。管理从入口不可达，
   7 个单阶段技能无一提及，3 个寄存器从未使用，运营→迭代→需求回环在 skill 层断开。

---

## 六、修复次序（已确认）

**必修**（会产生错误指令）：站点源码收回 → 阶段单一来源 → 站点与 skill 编号清零 → 管理可达
**应修**（断开的交接）：设计 → 验收、设计 → 开发、运营 → 迭代、迭代 → 需求
**应修**（薄处）：交付提示词、`anb-manage` 清单
**可选**：三个空寄存器——要么真用，要么承认是理论

---

## 七、计划中作出的三个决定（用户未答，实现时按此执行，可推翻）

1. **编号怎么统一**：**取消编号**。skill 里不再出现 `Stage N`，改用阶段名；
   站点显示用的编号由**位置在构建时派生**，永不手写。理由：编号是唯一必然过时的东西，
   名字不会。站点阶段页文件名同时去掉数字前缀（`design.html` 而非 `02-design.html`），
   使重排阶段不会产生死链。
2. **设计记录怎么被消费**：**由 `anb-judgeable` 主动读**。提供 `scripts/design.mjs`
   把已确认设计记录输出成下游可用的形式；读不到已确认记录时必须明说并继续，
   不得静默跳过（那正是失败图鉴第三类）。
3. **管理怎么可达**：**加进活的导航面，不动冻结原件**。
   原先写的是「加进路由表与决策树」，写计划时发现 `decision-tree.html` 属于
   站点明示「未改一字」的八份原始文档之一——改它会把「原文」变成「改编」。
   所以改为：router 表 + `branches.html`（生成物）+ 首页入口卡，
   并给 7 个阶段技能各加一句「这一步要记什么」（真正的横跨，
   也对应用户先前选择的「横跨七阶段的基础层」）。

   注：站点同时把 decision-tree 描述为「原始文档（未改一字）」和「导航：不知道下一步时用」，
   这两句本身有张力。本次不改它，但这个张力留着。

4. **站点手写原件与生成物分家**：`docs/site/originals/` 放手写原件，
   根目录只放生成物。理由：LAYOUT.md 称整个 `docs/site/` 是「生成物，不手改」，
   而其中 8 份是手写且被明令不得修改的——目录结构必须反映这个区别，
   否则孤儿检测无法区分「残留」与「原件」。
