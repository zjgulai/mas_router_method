第二次实测2026-10-24产品：repo-vitals · 955 行（源码 511 / 测试 444）

修正后的方法，
补上缺口了吗

上一次实测发现七个问句漏了一整类：它们管「机制可不可信」，不管「结果对不对」。 于是我加了四条质量问句，然后用修正后的方法做一个新产品——看那四条是不是真的补上了。 答案是补上了，而且它以我没预料到的方式咬了我一口。

结论

四条质量问句确实补上了缺口。第一步就见效：阶段 2 刚跑通，它们就抓到一个「看起来没问题、实际是坏的」结论——工具给一个已被作者废弃的库打了满分。

但更重要的是第二件事：修好之后，检查通过了，而通过的原因是错的。这一层，四条问句也拦不住。

3次「检查通过但理由错」
2个真实的误报，被真实数据抓到
22条检查，全部可失败
1次产品否定条件提前显形

做了什么

一个仓库名进去，一句可审计的结论出来——这个该不该用。选它是因为它天生带一个可量化的质量维度：结论对不对，可以拿真实仓库验证。

1

想法

验收未完成

五句话写完了。但验收动作是「念给一个不懂技术的人听，他能复述出用途」——这一步我做不了，需要另一个人。我先往下走了，这是一个真实的卡点，不是演示。

写的过程中修了一个自己的错误：第一版的「什么情况说明不该做」写的是「如果没人用」。那是废话，任何产品没人用都不该做。真正的否定条件是「这些指标不承载判断」——它可以被测量，所以它才是可证伪的假设。

2

能跑

验收通过

一条真实输入走通。验收动作是「用我自己随手找的输入，再换一个说不上来的」——两个都跑了。

而这一跑就把产品打穿了：

$ node src/index.js --repo moment/moment
moment/moment: looks solid. No red flags in the five signals checked.

moment 是作者自己宣布进入维护模式、建议新项目不要用的库。工具给了它满分。产品的否定条件在阶段 2 就显形了——如果修不好，这个产品就该停。

3

能判断

硬门通过

七条标准，先写检查，再改产品。关键是把检查分成两组：

A 组测机制——来源可追溯、失败不出结论、结论与表格一致、可重复。B 组测结果对不对——已知坏样本必须判坏、已知好样本不能误杀、每条信号必须说明盲区。

B 组就是上一次缺的那一类。它一上来就把 moment 抓了出来。

三次「通过但理由错」

这是这次实测最有价值的发现。三次都是我自己写的检查，三次都是绿的，三次都绿得不对。

第一次：B4 通过了，但抓的是错的东西

我把「moment 不能被判成 looks solid」写成检查，它通过了。我差一点就收工。

查了一下才知道：它通过是因为 moment 已经 496 天没提交，被「维护活跃度」判为 bad。而我写这条检查的本意是「作者说别用」。

这意味着：一个仍在活跃维护、但作者已宣布废弃的库，会拿到满分。我用一个假想样本验证了——确实满分。检查通过了，但它守的根本不是我以为的那扇门。

做法：把这个空洞显式写成一条断言错误行为的检查，锁住它。它会在空洞被填上时失败，提醒人「这里变了，想一想」。

第二次：检测器写好了，但认不出真实世界的措辞

我按自己想到的措辞写了废弃检测：「this package is no longer supported」「DEPRECATED: use X」。八种措辞，全部正确识别，零误报。

接到真实仓库上一跑——moment 认不出来。

因为它的 README 写的是：Moment.js is a legacy project, now in maintenance mode. New features are not being accepted.

这三句里没有一个词在我的模式库里。我是按「我想象一份废弃声明怎么写」来写的，不是按「真实世界怎么写」。

第三次：误报。而误报比漏报更贵

补上真实措辞后再跑：moment 认出来了，但 jquery 也被判成废弃了。

原因：jquery 的 README 里有一句「The 2.x and 1.x branches are no longer supported.」——说的是两个分支，不是项目本身。而我新加的「no longer supported」匹配到了它。

这一步让我意识到一件事：漏报只是少一个信号，误报会教人忽略所有信号。所以这个模块的取舍是明确偏向沉默的——宁可漏，不可错。

这些说明手册还缺什么

四条质量问句补上了原来的缺口，但它们还有一层漏。它们能发现「检查通过了但结果是坏的」，发现不了「检查通过了但通过的理由是错的」。

后者比前者更隐蔽，因为结果看起来是对的。B4 那次就是：结论正确（moment 被判为有风险），理由错误（因为陈旧，不是因为废弃）。如果样本换成一个活跃但已废弃的库，结论就会跟着错。

要加的不是第五条问句，而是一个动作：每次检查通过之后，问一句——「它是靠哪一条通过的？如果那一条不成立，它还会通过吗？」

具体做法：把那个「不成立」的情况造出来跑一遍。这一招在事后验证过两次（把贡献者数改成 unknown、把 readme 去掉），两次都发现了新的洞。

真实数据抓到的两个误判

这是「用真实输入」这条纪律的直接回报。两个都是我自己写出来、自己没看出来的问题。

样本第一次跑的结果说明什么
moment/momentlooks solid元数据全绿（4.8 万星、未归档、近期有提交）。真相只写在 README 里，而 GitHub 的字段表达不了它
jquery/jqueryusable with caveats（误报）README 里「2.x 和 1.x 分支不再支持」被当成「项目废弃」。版本范围的主语被我漏掉了

修完之后，六个真实仓库全部判对：moment 判为有风险，jquery、request、node、express、lodash 都没误报。

这次实测改变了什么

方法从三块变成四块，新增的一块是「检查通过之后要问它靠什么通过」。但更值得记的是另一件事：

  • 四次实测，四次都是「我以为的」被真实数据推翻。第一次是评测台自坏，第二次是七个问句漏类，第三次是「42 个不存在」的误判，这次是「通过但理由错」。
  • 每一次推翻都发生在第一次接触真实输入的时候，没有一次发生在我的推演里。
  • 所以「用真实输入跑一遍」不是流程的最后一步，它是最便宜的一次验证。我这次花在真实仓库上的时间不到十分钟，抓到的两个问题，靠推理一个都发现不了。

还有一点关于这套方法本身：它不能防住所有错误，但它让错误留下名字。这次三次「通过但理由错」，我每次都能发现，是因为手册里已经有「检查通过但结果是坏的」这个概念——它给了我一个方向去找。没有这个名字，我会直接收工。
