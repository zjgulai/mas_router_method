总览 / Agent 图谱

Main Agent 能力图谱

从「方法文档」到「飞书群里可用的咨询 Agent」。这个项目最值钱的不是写代码，而是把数据产品 / Agent 产品从想法推到可验收的判断与证据体系。Main Agent 将这套体系变为可路由、可引用、可拒绝的能力网络。

核心原则。 Main Agent 不是通用闲聊机器人。它以仓库中的已验证事实（代码、ADR、设计记录、评测用例、检查器）为唯一依据。 回答结构固定：【结论】一句话可执行 + 【定位】四条轴坐标 + 【依据】2–3 条短引文与路径 + 【下一步动作】。

一、四条核心坐标轴

定位一个问题时，先确定它落在哪个坐标系中。混淆四者是项目失控的最常见原因。

坐标轴取值范围回答的核心问题
生命周期 (7+1)需求 → 设计 → 开发 → 验收 → 交付 → 运营 → 迭代 → 管理现在处在哪一步？这一步的关门条件是什么？
数据产品层 (8)采集 → 存储 → 打标 → 指标 → 分析 → 呈现 → 结论 → 报告问题卡在哪一层？这一层的输入/输出/失败模式是什么？
横切三柱 (3)口径 / 质量 / 血缘这个数字的定义、可信度、来路能不能说清？
Agent 交付车道Incident / Exploration / Capability / Fast (G1–G5)这是能力问题还是确定性问题？最少要过哪几道门？

二、十七个能力节点

Main Agent 咨询引擎内部维护的 17 个能力节点与主责范围。

能力导航 navigate-capabilities

先判断问题属于哪条轴，避免把工程问题当模型问题解决。

意图与决策 intent-and-decision

先写「要改变哪个动作」和停止信号，通不过不进入设计。

结论卡规范 data-conclusion-card

结论卡六项必填，证伪条件必须可执行、可检验。

指标契约 metric-contract

一个指标一个明确定义，口径变更升级版本号、不重算历史。

采集时点 collection-time

first_seen_at 是锚点，抓得晚会被错误读成「更热」。

存储与血缘 storage-lineage

只追加、读侧迁移、版本四元组，保证旧记录始终可读。

打标体系 labeling-taxonomy

标签带版本、标注带置信度、维护金标准集与 Kappa 门槛。

分析与识别 analysis-identification

先跑相关性门禁，再做区域固定效应估计，避免伪相关。

呈现与下钻 presentation-drilldown

聚合数必须可逐级下钻，明确区分空值与异常状态。

报告与证伪 reporting-falsification

主动报告「哪条旧结论失效了」，结论具备时效性。

Agent 行为边界 agent-playbook

Playbook 锁目标与边界，工具层做硬护栏，不靠提示词兜底。

评测质量 eval-quality

Eval set 就是 spec；严格区分确定性检查与模型主观评分。

失败诊断 agent-failure-diagnosis

修复顺序铁律：eval → 数据 → 工具 → prompt，绝不反向。

交付车道 delivery-lanes

按四车道分流，严格守住 G1~G5 五道交付硬门。

方法治理 method-governance

没有能变红的命令就是愿望；单一来源与机器门禁。

飞书网关 feishu-surface

事件验签、3秒异步应答、幂等去重、长连接与 Webhook。

长任务处理 long-running-tasks

超长任务回执确认、异步队列调度与任务进度通知。

四、咨询引擎的执行链路

用户提问
  │
  ├─ 1. 分类：匹配 17 个能力节点与意图范围（低于阈值则追问或礼貌拒绝）
  ├─ 2. 路由：根据 14 条症状路线确定最经济的首检建议
  ├─ 3. 检索：BM25 检索知识库 chunk（优先匹配规范定义与事实依据）
  ├─ 4. 成文：按照【结论 / 定位 / 依据 / 下一步 / 边界】五段式严格输出
  └─ 5. 校验：禁止大模型生成无依据的路径与指令
