03开发

一条真实输入从头走到尾，出一个真实结果。不做功能，只做一条最窄的路。开工前跑 node scripts/design.mjs constraints：判断点要保持为判断，动作权限要实现成边界。

方法论已覆盖　这一步由 anb-runnable 覆盖，核心纪律是"不许有任何假数据"。

为什么这一步重要：这是最容易假装成功的阶段：界面有、按钮有反应、看起来通了，但背后是样例数据。

什么情况走哪条路

按代价排序，不按发生概率。先做便宜且能推翻结论的。点击跳到对应处理。

如果去为什么
跑通了，但结果来自样例/固定数据结果来自样例数据这是第一类假信号的温床。换一个你自己随手找的真实输入再试。
跑通了，但只对一种输入有效只对一种输入有效那不是跑通，是特判。换第二个说不上来的输入。
跑不通，报错看不懂错误看不懂错误必须是句子，不是堆栈。这是产品问题，不是调试问题。
真实输入跑通两次，结果都能给人看这一步过了进入验收。

结果来自样例数据

这是最危险的一种"跑通"：界面完整、按钮有反应、输出看起来合理，但背后是写死的。

怎么发现：给它一个你自己随手找的真实输入（真的链接、真的文件、真的需求），看它给出什么。再用一个你说不上来的输入试第二次，因为第一次可能是被特判过的。

只对一种输入有效

那不叫跑通，叫特判。

怎么发现：换一个你没预想过的输入。如果它崩了或者给出荒谬结果，说明这条路径只为一个案例存在。

这不是要你做通用产品，是要你知道自己现在的东西能覆盖多大的范围。

错误看不懂

用户看到一段英文堆栈，等于什么都没看到。

正确标准：错误信息要说清三件事：哪一步失败了、为什么、用户能做什么。"出错了"不是错误信息。

这一步过了

进入下一步。如果这是一个大产品，建议在这里停下来，把这一步的产出写成文件，因为三个月后你会需要它。

谁来验，怎么验

每一行都是一个你能亲手做的动作。做不了就记成未通过，写明缺什么，不要用近似动作代替。

动作通过标准
你自己用随手找的输入跑了一次不是它准备好的样例
换一个你没预想过的输入，也跑通了两个都能跑，才算跑通
失败时报的是一句人话，且退出码非零不是静默通过，也不是堆栈

从 2,794 个真实工程会话里挑出来的。案例已去掉业务细节，只用来说明这些误判真的会发生。

对应误判真实案例说明
结果来自样例数据拿准备好的样例数据跑，64 项检查全过；换成真实数据时，只做到"把数据找齐"，还没真正跑过。全绿和能用之间，隔着一整个真实数据。

实战避坑守则 (Battle Tips)

归属于开发阶段的实战守则摘要。完整复制口令见 作战手卡全表。

守则与手卡入口典型痛点验收判定
01-05 让 Agent 先看地图再改代码一口气动十几个文件，依赖和影响面不可见，合并后才发现牵连别处。变更说明必须能回答：改了哪里、为什么、可能影响谁、如何回滚。
02-02 AGENTS.md 太重 / 规则要分层把代码规范、API 格式、业务逻辑和所有例子全塞根目录，Agent 反而变慢。每条规则都要有触发场景、适用范围、验证方式和删除条件。
03-04 Bug 反复改 / 设调试止损线改一次、又引出新问题，第三轮已经忘了最初错误，Token 和时间一起烧掉。没有新的证据时，不继续堆 patch。
05-04 自动化 / 先拆链路再接工具把多个平台和 Agent 串起来很容易，但错误会被自动化放大。没有权限、幂等和回滚设计时，不做全自动发布。
06-03 数据工程 / 用状态机和 Provenance 管住链路数据产生、摄取、存储、处理、发布混在一起，失败后无法定位。任何结果都能回到源头、变换和版本。

这一步的实战用法

来自实战项目的做法，按它和本阶段的关系收录。完整案例、方法和提示词见 实战用法。

项目一句话来源
The Fable Method：把判断问题转成证据问题的 7 步循环分类、定义完成、取证、决策、最小改动、观察验证、结论先行；每一步都有硬边界。Sahir619/fable-method
Fable Mode：把编排做成结构，而不是提示词里的请求stage map、命名委派、可失败的检查、冷验证；orchestrator 没有写权限，worker 才有。mrtooher/fable-mode
fablize：只搬运被实验证明可搬运的程序不提升模型天花板，只让模型走到自己的天花板；只发布验证过效果的程序。fivetaku/fablize
Fable Advisor：架构师不下场打字，按能力分 lane 路由会话当架构师，GPT-6 lane 打字，Fable 在承诺边界和终局做审查。DannyMac180/fable-advisor
Fusion-Fable：独立 panel 加固定 judge，把多个模型合成一个答案同一 prompt 盲跑多个模型，Opus 固定做 judge，输出共识、矛盾、遗漏、盲点。duolahypercho/fusion-fable
Fable Foreman：路由卡是单一事实源，贵的模型要二次批准先证明能用，再按成本/能力选座；lead 亲自验收，贵模型要用户两次确认。olsenbrands/fable-foreman
System Prompts Leaks：把系统提示词当成可对照的工程材料18 个厂商、约 1900 份提示词，按产品和版本归档，能看到行为契约的结构和演变。asgeirtj/system_prompts_leaks
claude-directory：用 prompt、成品和录屏证明一个案例真的能跑541 个项目，每个都带 prompt.md、可运行代码、demo.mp4 和 poster.jpg。pulkitxm/claude-directory

这一步用到哪些 skill

  • anb-runnable：一条真实输入走通，不含假数据。
  • implement：读票 → tdd → typecheck → code-review → commit。
  • implement-spec：一个 spec 下多张票按 frontier 落地。
  • tdd：红绿重构。
  • ponytail：最小完整改动，不加没人要的抽象。
  • karpathy-guidelines：先声明假设，只改必须改的。
  • reuse-first：写工具前先搜仓库、标准库、GitHub。
  • prototype：一次性原型回答一个设计问题；多套并排，用截图/时序/状态面板作为证据，产出对比而非菜单。
  • using-git-worktrees：独立工作区，基线先绿。
  • swarm：并行 N 个 worker，排干后汇一份报告：覆盖、竞速、遍历分区。
  • principle-build-the-lever：批量活先造工具（codemod/脚本/生成器），别用手敲。
  • principle-laziness-protocol：偏向删除与最小改动；想加抽象时先读这条。
  • principle-subtract-before-you-add：先删死代码与冗余校验，再在更简单的底座上加东西。
  • deslop：删掉 AI 生成的代码泔水，统一风格。
