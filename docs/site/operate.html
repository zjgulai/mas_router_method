06运营

看得出它有没有被用、有没有变好、钱花在哪、出事时能不能查。

半个覆盖　这一步由 anb-observable 覆盖技术侧观测（跑几次、花多少、为什么失败）。产品侧观测（有没有人用、用了之后有没有变好）需要结合业务埋点完成。

为什么这一步重要：没有这一步，你无法回答"这个产品到底成不成立"。而技术上的"全部正常"和产品上的"没人用"可以同时成立。

什么情况走哪条路

按代价排序，不按发生概率。先做便宜且能推翻结论的。点击跳到对应处理。

如果去为什么
你不知道它跑了多少次、失败多少次不知道它跑了多少次先补三个数字，再谈别的。没有观测就加功能，等于在黑暗里挪。
有记录，但总数和分项对不上总数和分项对不上记录有洞。每一条其它结论都建立在这上面。
数字正常，但不知道有没有人真的在用不知道有没有人真的在用这是产品侧观测，需要埋点而不是日志。
能回答"谁在用、用了多少次、哪里失败"这一步过了进入迭代。

不知道它跑了多少次

你缺三个数字：跑了多少次、失败多少次、为什么失败。

先有这三个，再谈别的。没有观测就加功能，等于在黑暗里往前挪，你会一直走到撞墙才知道方向错了。

总数和分项对不上

这说明记录有洞：有请求开了头没结尾，或者被算了两次。

一个更隐蔽的版本：你去看仪表盘的那次请求，自己也被计入了仪表盘。于是每看一次，数字就涨一次，而且只涨不跌。

动作：把总数拆开加一遍。然后什么都不做，刷新五次，看数字会不会自己动。

不知道有没有人真的在用

技术观测答不了这个。日志能告诉你"程序跑了"，不能告诉你"有人需要它"。

这是这套方法的边界：它能让你不骗自己，不能让你不骗市场。要做产品侧观测，得埋点：谁在用、用了几次、在哪一步放弃。

这一步过了

进入下一步。如果这是一个大产品，建议在这里停下来，把这一步的产出写成文件，因为三个月后你会需要它。

谁来验，怎么验

每一行都是一个你能亲手做的动作。做不了就记成未通过，写明缺什么，不要用近似动作代替。

动作通过标准
做三次，历史里有三条做 N 次数 N 条
故意弄坏一次，能在记录里找到它和原因找不到就是记录有洞
知道花了多少这个产品花的是 API 配额与 token，两个都要能看清

来自实战项目的做法，按它和本阶段的关系收录。完整案例、方法和提示词见 实战用法。

项目一句话来源
Fable Mode：把编排做成结构，而不是提示词里的请求stage map、命名委派、可失败的检查、冷验证；orchestrator 没有写权限，worker 才有。mrtooher/fable-mode
fablize：只搬运被实验证明可搬运的程序不提升模型天花板，只让模型走到自己的天花板；只发布验证过效果的程序。fivetaku/fablize
Fable Advisor：架构师不下场打字，按能力分 lane 路由会话当架构师，GPT-6 lane 打字，Fable 在承诺边界和终局做审查。DannyMac180/fable-advisor
Fusion-Fable：独立 panel 加固定 judge，把多个模型合成一个答案同一 prompt 盲跑多个模型，Opus 固定做 judge，输出共识、矛盾、遗漏、盲点。duolahypercho/fusion-fable
Fable Foreman：路由卡是单一事实源，贵的模型要二次批准先证明能用，再按成本/能力选座；lead 亲自验收，贵模型要用户两次确认。olsenbrands/fable-foreman
claude-directory：用 prompt、成品和录屏证明一个案例真的能跑541 个项目，每个都带 prompt.md、可运行代码、demo.mp4 和 poster.jpg。pulkitxm/claude-directory

这一步用到哪些 skill

  • anb-observable：三个数字：跑几次、花多少、为什么失败。
  • observability-and-instrumentation：从 on-call 问题倒推日志、指标、追踪、告警。
  • instrument-product-analytics：事件表、漏斗、留存、身份策略。
  • artifact-registry：每个有持续成本的东西登记 owner 与过期。
  • tech-debt：打分排序的债务登记表。
  • deprecation-and-migration：弃用策略与 expand/contract 迁移。
  • repo-gc：E1–E4 分级的删除计划。
  • ponytail-audit：全仓审计：什么可以删。
  • show-me-your-work：长跑无人值守的工作留一份可审计决策轨迹：每行一条 what/why/evidence/result。
  • ketchup：用大白话和小图把"你上次说话之后发生了什么"讲清楚，并列出等你决定的事。
  • reflect：三个并行 reviewer 读本次会话，把学到的东西落到某个已有 skill 的具体改动上。
  • what-did-i-get-done：按时间段汇总自己提交的 commit。
