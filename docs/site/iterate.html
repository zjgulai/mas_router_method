07迭代

只留下真的用过的，改掉真的错的。先由运营给到的三个数字决定改什么，把结论落成 R- 或 T-；再决定留下什么做下个产品的起点。

方法论已覆盖　这一步由 anb-reusable 覆盖，并且推翻了它自己的一条规则（"用过三次才抽"太严）。

为什么这一步重要：迭代不是加功能，是去掉不该留的。判断标准是"上个产品用过吗"，不是"这个可能有用"。

什么情况走哪条路

按代价排序，不按发生概率。先做便宜且能推翻结论的。点击跳到对应处理。

如果去为什么
你要加一个新功能要加新功能先问：它解决的是观测到的哪个问题？答不出来就是猜。
你想抽一个通用模板想抽通用模板判据不是"用了几次"，是"它的形状会不会随产品变"。
一个东西你想保留，但说不清为什么想保留但说不清理由删掉。想不清理由的东西会成为下个项目的负担。
有了真实使用数据，知道该改什么这一步过了回到需求，开始下一轮。

要加新功能

先问：它解决的是你在观测里看到的哪个问题？

答不出来，那就是猜。猜的功能不会被用，而且会挤占维护别人在用的功能的精力。

答出来了，就把它落成记录：需求本身变了就写 work/requirements/ 里的 R-，是新认领的工作就写 work/tickets/ 里的 T-。这一步不是仪式：不落记录，结论就只活在这轮对话里，下一轮又从记忆开始，于是每隔几个月把同一件事重新学一遍。

想抽通用模板

判据不是"用了几次"。

真正的判据是：这东西的形状会不会随产品变。测试运行器的形状不变，抽出来两次就够；仓库骨架的形状每次都变，抽出来就是负担。

第二个判据：它要不要在每个产品里都重新验证一次"它可靠"。如果要，那抽取省的不是行数，是验证次数。

想保留但说不清理由

删掉。

没有理由的保留物会成为下个项目的负担，因为每个未来的决定都要塞进它的形状里。而且你会在三个月后忘记它为什么在那儿，于是没人敢删。

这一步过了

进入下一步。如果这是一个大产品，建议在这里停下来，把这一步的产出写成文件，因为三个月后你会需要它。

谁来验，怎么验

每一行都是一个你能亲手做的动作。做不了就记成未通过，写明缺什么，不要用近似动作代替。

动作通过标准
每一项保留物都能说出"在哪个产品用过、用了几次"答不出来的删掉
用模板开第二个产品，计时比第一个快更慢说明模板是负担
复盘产出的每一项有 owner 和复查日期没有归属的改进项等于没有

实战避坑守则 (Battle Tips)

归属于迭代阶段的实战守则摘要。完整复制口令见 作战手卡全表。

守则与手卡入口典型痛点验收判定
01-06 让环境和 Agent 一起变强静态环境只给结果，不给足够的反馈；Agent 很难知道什么算好。下次执行应能复用上一轮的证据，而不是重新猜。
02-01 新对话失忆 / 先做记忆分层需求、决策、坑和偏好散在聊天里，换会话就要重新交代。交接文档脱离原对话仍能让另一个 Agent 继续。
02-04 创建 Skill / 先抽取 定方法把一次对话复制成 Skill，容易把偶然措辞和无效步骤固化。Skill 必须能被另一个人读懂、运行和验证。
05-03 内容增长 / 把一次实践沉淀成方法内容靠灵感重复生产，经验无法复用，热点也难以转变成长期资产。内容必须留下下次可以直接执行的动作。

这一步的实战用法

来自实战项目的做法，按它和本阶段的关系收录。完整案例、方法和提示词见 实战用法。

项目一句话来源
Value-for-Fable：用诊断结构而不是压缩去接近 Opus压缩省下的是 token，削掉的是诊断质量；v2 删掉压缩强制，保留诊断结构。itsinseong/value-for-fable
fablize：只搬运被实验证明可搬运的程序不提升模型天花板，只让模型走到自己的天花板；只发布验证过效果的程序。fivetaku/fablize

这一步用到哪些 skill

  • anb-reusable：只用过三次以上的才抽；形状会变的别抽。
  • retro：按严重度排序的环境改进项。
  • improve-codebase-architecture：找架构里的深化机会。
  • triage：issue 状态机、分类、agent brief。
  • setup-matt-pocock-skills：新仓库首次接入工程 skill。
  • consolidate-memory：合并重复记忆，修剪索引。
