总览 / 设计

02设计

把"以后改起来很痛"的六件事先定下来：流程里哪些步骤固定、哪些要临场判断；它必须拒绝什么；每一种情况该怎么答；它能不打招呼就做什么；模型动手时看到什么；每种结局下人拿到手的是什么。

方法论已覆盖　这里曾经是空的：ANB 从"想法"直接跳到"能跑"。现在补上了六问方法论（anb-design），答案落成 work/designs/D-xxx，可以被 work check 校验。

最后两块是实测加上的：把前四块交给一个 agent 去实现最窄的路，它的猜测集中在"产出到底长什么样"，而四块里没有一块回答它；而原来的"拒绝清单"一块装了两样东西——实测十一行里只有三行是禁令，其余八行是"这种情况该怎么答"。

为什么这一步重要：设计阶段的错误不会当场报错。它会以"后面每改一次都很痛"的形式慢慢出现，而那时已经没人记得当初为什么这么定。四问的作用不是把设计做全，是把最贵的四个决定逼出来。

实战避坑与作战原则 (Battle Tips)

来自 6 大作战面板中归属于设计阶段的实战守则。详见 作战手卡全表 →

01-02 模型只是乘数，Harness 才是系统

痛点：模型会更换；真正累积的是工具、技能、上下文、循环和审批。

  • 把 system prompt、tools、agent loop、translation layer 视为最小 Harness。
  • 把高频流程沉淀成 Skill，把长期知识放到可检索的外层。
  • 不要用角色数量替代调度设计：先看上下文、工具边界、任务停止、结果验证。
如果模型明年强 10 倍，这个功能还应该留在 Harness 里吗？请按必要性、可替代性、验证成本回答。
验收判定：每个长期机制都要能说清保留理由和删除条件。

01-04 先路由，再执行

痛点：工具很多，Agent 选错方法时会把时间浪费在无效探索上。

  • 先判断任务类型：代码库、浏览器、数据、研究、视觉内容。
  • 按 scenario skill / tool index 选最短路径，保留 timeline 与证据。
  • 模型负责推理，专用执行器负责高频、低熵动作。
Route first, execute second: 先写任务类型、授权 scope、可用工具和退出条件，再开始 ACT。
验收判定：没有授权、scope 或工具前置条件时，不进入执行阶段。

02-05 上下文窗口 / 先做价值排序

痛点：低频 Skill、旧决定和中间噪声驻上下文中，挤掉真正有用的信息。

  • 按当前任务的决策价值排序：目标、约束、接口、失败样本优先。
  • 过期 Read、中间尝试和重复解释进入可丢弃区。
  • 用按需加载、摘要和状态文件维持长任务连续性。
请将当前上下文分成：必须保留、可按需加载、可丢弃三层，并说明每项的判断理由。
验收判定：压缩后不能丢失用户目标、关键报错、约束和可复现路径。

04-01 Prompt 不用专业 / 要写到自己读得懂

痛点：复杂术语堆在一起，自己都无法检查，模型也难以稳定复现。

  • 先写主体、风格、构图、媒介，再补镜头、光线、材质和约束。
  • 把目标拆成可观察的画面条件，而不是形容词堆叠。
  • 让 AI 帮你看改写，但最终 Prompt 必须能被自己读懂和验收。
【主体】x【风格】x【构图】x【媒介】；请把我的想法改写成我能读懂、能逐项检查的 Prompt。
验收判定：每个形容词都要对应可观察的画面证据。

04-03 抄参考 / 先提取设计系统

痛点：只看截图容易抄到表面，配色、字体、间距和组件关系仍靠猜。

  • 从真实网站提取颜色、字体、间距、阴影、圆角和状态。
  • 用 Design.md / design system 把审美决策写成可复用约束。
  • 把参考分成灵感、规范、组件和验收，不要混成一张收藏夹。
请从这个参考网站提取一份可执行设计系统：色板、字体层级、间距、组件、状态、无障碍和验收清单。
验收判定：输出必须能直接指导实现和 Review，而不是只说“高级、简洁”。

04-04 风格库 / 用编号减少描述成本

痛点：审美词汇不稳定，团队和模型对“手绘、电影感、高级”理解不一致。

  • 把风格做成编号画廊，选择时引用编号而不是重复形容。
  • 为每种风格保存中英描述、适用场景和反例。
  • 风格只是变量，仍要单独定义主体、构图、媒介和约束。
浏览风格画廊，选出最适合主题的 1 个风格编号，并说明它与主体、构图和媒介如何组合。
验收判定：风格选择必须能解释为什么适合当前任务。

04-05 复刻 / 先拆结构再换内容

痛点：看到结果就照抄，往往只能复制表面，无法迁移到新主题。

  • 拆出镜头、角色、服装、光影、动作、节奏和负面约束。
  • 先固定结构，再替换主体；每轮只改变一个变量。
  • 用对照图或片段回看判断是哪一层造成差异。
请把这个参考拆成结构变量与内容变量；先保持结构不变，只替换主体，并列出每轮对照检查项。
验收判定：复刻结果要能说明差异来自哪个变量。

04-06 UI 不是堆功能 / 是任务与层级

痛点：页面看起来完整，却没有清晰任务路径，AI 带来无意义装饰和默认组件。

  • 先写用户任务、信息层级和状态，再选组件和动作。
  • 用高内聚、低耦合组织页面；动效服务反馈，不服务炫技。
  • 把无障碍、响应式、性能和文案纳入设计验收。
请按用户任务重构这个页面：先列层级、关键状态和操作路径，再决定组件、动效和视觉风格。
验收判定：每个视觉元素都要服务理解、操作或反馈。

06-02 RAG / 先问检索结构是否适合任务

痛点：切块、向量和相似度搜索并非所有文档任务的最优解。

  • 对长文档先保留层级、章节、表格和引用关系。
  • 比较向量检索、关键词、树状索引和 Agent 导航。
  • 用代表性问题集测准确、召回、成本和可解释性。
请先分析文档结构和问题类型，再比较向量、关键词、树状索引等检索方案，给出基线与评测集。
验收判定：不要因为“大家常用 RAG”跳过任务结构分析。

什么情况走哪条路

按代价排序，不按发生概率。先做便宜且能推翻结论的。点击跳到对应处理。

如果去为什么
你要判断这东西到底该不该用 agent该不该用 agent，一个测试一个测试：能不能把决策树画出来。能画就是管线，画不出来才需要 agent。
你说的是功能和技术选型，说不清它必须拒绝什么拒绝清单写成了价值观拒绝清单写不出具体输入的，是价值观，不是设计。它在验收时会被悄悄丢掉。
它能发消息、删东西、付款或发布按重要性排权限，排错了按能不能撤销分三档，不按重要性。重要性你会排错，能不能撤销是事实。
模型要自己决定调哪个工具交接契约只写了"它做什么"每个工具三行，第二行「什么时候别用」是重点，也是最常被省掉的。

你的"拒绝清单"越写越长，而且大部分是"该怎么答"「拒绝清单」越写越长禁令是清单，应答规则是表格——形状不同。实测里有十一行，只有三行是真正的禁令。
拒绝清单要对照的政策，散在好几处输入存在，但散在好几处最常见也最麻烦的形态：既不是"有"，也不是"没有"。中间那件「拢成一份」的工作没人负责，而它跨会话。
只有一个用户、只跑一次、只读不写可以跳过，但要写下来可以跳过，但写下"我跳过了，因为…"。

该不该用 agent，一个测试

这个问题现在归需求阶段问（anb-idea），因为它是"你在做什么"的决定，不是"怎么实现"。

测试只有一个：你能不能把决策树画出来？能写出步骤顺序和分支条件，它就是固定流程，应该做成管线——顺序确定、一次模型调用嵌在脚本里，更便宜、更快、更好查。只有当下一步取决于上一步返回什么、你列不出分支时，才需要 agent。

设计阶段会把这个数重新数一遍：判断点零到一处，就该退回管线。两个阶段问同一个问题不是重复——一个是决定，一个是复核，而复核经常推翻决定。

拒绝清单写成了价值观

「要诚实」「不要有害」「保持品牌调性」——都对，但一条都测不了。

改法：每条按「一个具体输入 → 它必须改做什么」重写。写不出具体输入，就先问一句：这个产品最容易被误用成什么样？

为什么这一步值钱：拒绝清单是设计阶段唯一能直接变成验收检查的东西。写成价值观的那些，会在验收阶段写检查时被安静地删掉——因为没人知道怎么测，于是不测。

按重要性排权限，排错了

「付款重要，所以付款要确认；读文件不重要，所以放行。」结果是：一条读文件的动作把全部客户记录导了出去，而 2 美元的扣款被拦住了。

按能不能撤销排，只有这一个标准：
· 可撤销 → 放行
· 会被看见或花钱 → 放行，但记账并设额度
· 不可撤销 → 先问人

中间那档最容易被跳过，而真正的损失都在那：不是答错一次，是在有人看之前错了五十次。额度要写数字，「合理使用」不是额度。

交接契约只写了"它做什么"

只写"这个工具用来读品牌画像"，等于授权它在任何场景下用。

每个工具三行：做什么 / 什么时候别用 / 失败时返回什么。

第二行是重点。agent 产品最常见的失败不是工具坏了，是一个正确的工具被用在了不该用的地方——而日志里每一行都正常，没有报错，没有异常，只是结果微妙地错了。

第三行决定一次失败是一个回合还是整轮运行：说清"这个 id 不存在，不要用同一个 id 重试"的工具，能把循环自己结束掉。

四问答完，用数问题来验收

把四块交给一个 agent，不给任何别的上下文，让它实现最窄的那条路。然后数它不得不自己猜的有几处。

零处：设计完成。每一处：都是一个洞，补上，再交一次，再数。

两轮是正常的。超过三轮说明不是写得不细，是缺了一整块。

这个验收的好处是它不靠感觉——「设计得清不清楚」是个意见，「它问了三个问题」是个数。

「拒绝清单」越写越长

禁令是清单：短，每条是一个「不要做」。应答规则是表格：每个具体输入一行，写它该怎么答。

这两样东西形状不同，装进同一个标题里就会被名字带偏。实测过一次：十一行里只有三行是真正的禁令，其余八行是「这种情况该怎么答」——而按标题去实现，会把「3 个月不能用、且不要给建议」那一行做成升级，可它明写不升级。

怎么改：分两块。「拒绝清单」收尾时应该很短；如果它有十行，回去看一遍。

输入存在，但散在好几处

这是最常见的真实形态，而方法原本没有它的位置。

需求阶段只问「政策完全不存在吗」——不存在就停机；设计阶段这一问则默认输入已经可用。中间那种「存在、但散在平台后台模板 + 几封内部消息 + 主管的口头补充里」的形态，两边都不管。

怎么改：先承认它，别跳过。「把它们拢成一份可对照的清单」是一件跨会话的工作，所以它是一张票，而这一块在票做完之前是阻塞的。

不要凭记忆写拒绝清单。凭大家记得的东西拼出来的清单，是价值观画上了箭头——每一行都像真的，而且没人能指出哪一行是猜的。

可以跳过，但要写下来

一次性脚本、只给自己用的工具、只读不写的工具，不需要完整设计。

判据不是"东西小"，是两个事实：有没有不可撤销的动作、除你之外会不会有人用。两个都没有，可以跳过；有一个，第二问就不能跳。

但必须写下"我跳过了设计，因为 X"。因为三个月后你会把它当正式项目维护，那时候没人知道当初为什么没有这份记录——而沉默和"想过但决定不问"在记录里长得一模一样。

谁来验，怎么验

每一行都是一个你能亲手做的动作。做不了就记成未通过，写明缺什么，不要用近似动作代替。

动作通过标准
四块都写了，跳过的块写明理由「跳过：只读，没有动作」算写完；空白不算
判断点写下来并命名了，不是只有一个数"三处"必须能指出是哪三处。只有一个数字时，两个人可以都同意"三"而指的是不同的三
应答规则每一行的"该怎么答"，都落在动作权限表允许的动作里三轮实测里，三处硬矛盾全是跨块的：表格要求了权限表里不存在的动作，而没有任何东西会比较这两块
把记录交给一个 agent 之后，它报的"哪几块互相冲突"是空的光是猜测量降到零不算完。跨块冲突不是零就等于没做完——它只会安静地传下去
拒绝清单每一条都有具体输入和一个改做什么拿得出"输入 X → 必须改成 Y"，才可能在验收时变成一条检查
动作清单按"能不能撤销"排，不按重要性中间那档写了数字额度，不是"合理范围内"
把四块交给 agent，它问你的问题在三个以内它猜的每一处都是洞，补完再数一次

这一步用到哪些 skill

  • anb-design — 四问：流程形状、拒绝清单、动作权限、交接契约。设计阶段的方法本身。
  • architecture-decision-records — 难回退的选择写成 ADR，含放弃的选项和代价。
  • domain-modeling — 术语定死，写进 GLOSSARY。
  • codebase-design — 模块边界、接口深浅、seam 位置。
  • spec-driven-development — 把共识固化成可验收的规格。
  • to-spec — 对话已透时直接固化，不再采访。
  • writing-plans — 把 spec 变成别人能执行的步骤。
  • to-tickets — 拆成 tracer-bullet 纵向切片，标阻塞关系。
  • api-and-interface-design — 契约先行、错误语义、分页、幂等。
  • database-schema-designer — 表结构、约束、索引、可回滚迁移。
  • auth-implementation-patterns — session/JWT/OAuth 选型、租户隔离。
