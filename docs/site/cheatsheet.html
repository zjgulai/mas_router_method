总览 / 作战手卡

实战作战手卡 · 36 条

把一组收藏压缩成可执行的工作闭环：先说清场景，再选择方法，最后保留证据。
整理自一线 Agent 工程与大模型产品实战，涵盖 Agent 工程、上下文、Eval 评测、创意流、产品增长与数据研究 6 大主题。

作战原则。 不是把收藏变成口号，而是把它变成下一次可以执行和验证的动作。
每张卡片遵循四段式结构：问题暴露 → TIPS 实操要点 → PROMPT 复制口令 → 验收判定。

01Agent 工程：从会做，到可持续运行

主题聚焦：Harness · 长任务 · 并行 · 路由 · 系统地图 ｜ 关联阶段：开发/设计

01-01 先配问题放回系统 需求

痛点：Agent 直接动手，往往连目标、边界和依赖都没有对齐。

  • 先确认真实目标，再看系统结构：把问题放回它所属的层。
  • 区分用户看见的结果和内部工程对象：先剪错误逻辑，再增加新逻辑。
  • 复杂任务先拆成产物链：intent → spec → tickets → implementation → verification。
PROMPT 复制口令
请先不要改代码：先确认真正目标、扫描系统结构、列出边界与依赖，再给出最小可行执行计划。
验收判定：计划必须指标输入、输出、验收和阻塞回退点。

01-02 模型只是乘数，Harness 才是系统 设计

痛点：模型会更换；真正累积的是工具、技能、上下文、循环和审批。

  • 把 system prompt、tools、agent loop、translation layer 视为最小 Harness。
  • 把高频流程沉淀成 Skill，把长期知识放到可检索的外层。
  • 不要用角色数量替代调度设计：先看上下文、工具边界、任务停止、结果验证。
PROMPT 复制口令
如果模型明年强 10 倍，这个功能还应该留在 Harness 里吗？请按必要性、可替代性、验证成本回答。
验收判定：每个长期机制都要能说清保留理由和删除条件。

01-03 长任务要可观察、可接管 交付

痛点：多个 Agent 并行跑，最怕失忆、卡住、上下文膨胀和没人知道当前状态。

  • 用 goal / issue / ticket 维持任务边界；每个阶段产出可读文件。
  • 把进度在工作、谁卡住、token 消耗、待确认事项放到可见面板。
  • 让 Agent 在关键节点停下来请求人审，而不是无限制重试。
PROMPT 复制口令
把这项长任务拆成可并行的 tickets；为每个 ticket 写输入、输出、停止条件、交接文件和人工审批点。
验收判定：任何分支都能从最近一次产物恢复，不依赖完整聊天记录。

01-04 先路由，再执行 设计

痛点：工具很多，Agent 选错方法时会把时间浪费在无效探索上。

  • 先判断任务类型：代码库、浏览器、数据、研究、视觉内容。
  • 按 scenario skill / tool index 选最短路径，保留 timeline 与证据。
  • 模型负责推理，专用执行器负责高频、低熵动作。
PROMPT 复制口令
Route first, execute second: 先写任务类型、授权 scope、可用工具和退出条件，再开始 ACT。
验收判定：没有授权、scope 或工具前置条件时，不进入执行阶段。

01-05 让 Agent 先看地图再改代码 开发

痛点：一口气动十几个文件，依赖和影响面不可见，合并后才发现牵连别处。

  • 先生成本项目系统地图：模块、调用关系、导入导出、数据流与运行入口。
  • 把本次变更圈在地图上，先说明影响面，再让 Agent 改。
  • 真实入口验证后，把新发现写回地图和交接文档。
PROMPT 复制口令
请先画出本次改动涉及的模块、调用关系和数据流；标出不能碰的边界，再开始实现。
验收判定：变更说明必须能回答：改了哪里、为什么、可能影响谁、如何回滚。

01-06 让环境和 Agent 一起变强 迭代

痛点：静态环境只给结果，不给足够的反馈；Agent 很难知道什么算好。

  • 把业务契约、评测集、失败样本和运行日志纳入环境。
  • 每次执行保留 evidence → finding → path，允许回放和比较。
  • 将高频失败模式写回 Skill、Harness 或测试，而不是只修当前对话。
PROMPT 复制口令
把这项任务改造成可评测环境：定义状态、动作、反馈、成功判定和失败样本。
验收判定：下次执行应能复用上一轮的证据，而不是重新猜。

02Skills 与上下文：少而准，按需加载

主题聚焦：Skills · AGENTS.md · 记忆 · 规则分层 · Context Budget ｜ 关联阶段：开发/设计/运营

02-01 新对话失忆 / 先做记忆分层 迭代

痛点：需求、决策、坑和偏好散在聊天里，换会话就要重新交代。

  • 把 定规则、项目事实、当前任务、历史决策分别存放。
  • 把大段历史压成：关键决策 / 当前状态 / 待解决问题。
  • 记忆必须能被检索、更新、删除，不能只靠一个超长文件。
PROMPT 复制口令
请把本次对话压缩成交接文档：目标、已确认决策、当前状态、未解决问题、下一步验证。
验收判定：交接文档脱离原对话仍能让另一个 Agent 继续。

02-02 AGENTS.md 太重 / 规则要分层 开发

痛点：把代码规范、API 格式、业务逻辑和所有例子全塞根目录，Agent 反而变慢。

  • 根规则只做路由和不可违背的边界；细节放到按需加载的 Skill。
  • 工具参数写进工具说明；任务特例与当前任务包挂钩。
  • 定期删除已经没有收益的旧约束，避免规则冲突。
PROMPT 复制口令
审查当前 AGENTS.md、Skills 和任务提示：哪些规则应保留在根层，哪些应下沉或删除？给出迁移表。
验收判定：每条规则都要有触发场景、适用范围、验证方式和删除条件。

02-03 装了 Skill / 不等于真的会用 验收

痛点：Skill 数量增长很快，但模型、Harness 和任务上下文改变使用效果。

  • 先定义 Skill 的触发条件和完成标准，再讨论安装数量。
  • 用真实任务评测：是否被正确选择、是否完整执行、是否产生副作用。
  • 把优秀做法编译进可执行 Harness，减少靠文字提醒的遗漏。
PROMPT 复制口令
请为这个 Skill 写一个最小评测集：触发样例、反例、完成标准、错误边界和回归任务。
验收判定：没有评测证据时，只能说“已安装”，不能说“已掌握”。

02-04 创建 Skill / 先抽取 定方法 迭代

痛点：把一次对话复制成 Skill，容易把偶然措辞和无效步骤固化。

  • 先观察多次任务中的共同输入、决策、工具和验收。
  • 只保留可迁移的流程、模板、检查项和失败边界。
  • 给 Skill 加版本、示例、反例、回归任务和废弃条件。
PROMPT 复制口令
从这组真实任务中抽取 Skill：先列 定模式，再删除一次性细节，最后给出触发器和回归样例。
验收判定：Skill 必须能被另一个人读懂、运行和验证。

02-05 上下文窗口 / 先做价值排序 设计

痛点：低频 Skill、旧决定和中间噪声驻上下文中，挤掉真正有用的信息。

  • 按当前任务的决策价值排序：目标、约束、接口、失败样本优先。
  • 过期 Read、中间尝试和重复解释进入可丢弃区。
  • 用按需加载、摘要和状态文件维持长任务连续性。
PROMPT 复制口令
请将当前上下文分成：必须保留、可按需加载、可丢弃三层，并说明每项的判断理由。
验收判定：压缩后不能丢失用户目标、关键报错、约束和可复现路径。

02-06 汇报要能让非工程师判断完成度 交付

痛点：一堆 commit hash 和工程术语，无法回答到底完成成了什么。

  • 结论先行：工作状态和验证状态分开。
  • 每个事实给定定位证据；不确定写“未确认”。
  • 待决事项编号化，给出影响和选项，而不是把判断甩回去。
PROMPT 复制口令
先写结论；把工作状态和验证状态分开；每个事实给定定位证据；不确定写“未确认”；需要我决定时列编号选项。
验收判定：读者不打开代码，也能判断范围、原因、证据、验证和待确认项。

03Eval First：从会生成，到值得交付

主题聚焦：评测 · 真实入口 · 验收 · Review · 证据 · 止损 ｜ 关联阶段：验收/开发

03-01 AI 项目 / 先建评测再建功能 验收

痛点：输出不可预测，单元测试通过也不能说明用户结果有效。

  • 先定义成功/失败、边界和质量等级。
  • 用代表性样例集反复回归，记录输入、输出、上下文和工具轨迹。
  • 把评测结果作为产品迭代的眼睛，而不是上线后的补丁。
PROMPT 复制口令
Eval First: 先给出评测集、成功标准、失败类型和基线，再设计实现方案。
验收判定：没有基线和失败样例，不宣称“效果更好”。

03-02 单测通过 / 仍要跑真实业务路径 验收

痛点：局部函数正确，不代表权限、状态、并发、重试和回滚真的成立。

  • 一键启动环境、准备数据、明确账号权限，并支持清理重置。
  • 从浏览器、API 或 CLI 操作真实入口。
  • 用 DB、日志、Trace 和业务断言闭合证据链。
PROMPT 复制口令
请从真实入口跑完整业务路径，并同时给出用户可见结果、工具证据和业务契约对照。
验收判定：从入口跑到底端，并留下可复核证据。

03-03 机制很多 / 用消融实验找贡献 验收

痛点：缓存、队列、锁、Agent、插件一起上线，没人知道真正收益来自哪里。

  • 先建基线，再一次只移除或加入一个机制。
  • 比较质量、延迟、成本、失败率和复杂度变化。
  • 没有贡献或无法验证的机制，删除而不是继续解释。
PROMPT 复制口令
给这三个优化设计消融实验，判断真正的收益来自哪里。
验收判定：每个机制都有对照结果和业务收益。

03-04 Bug 反复改 / 设调试止损线 开发

痛点：改一次、又引出新问题，第三轮已经忘了最初错误，Token 和时间一起烧掉。

  • 先复现，再只改一处，用同一方法验证。
  • 连续两轮没有进展，停止修改，重新诊断根因。
  • 保留失败日志和当前假设，避免下一轮从头猜。
PROMPT 复制口令
先复现问题；每轮只改一处；用同一验收方法验证；连续两轮无进展就停止修改并重新诊断。
验收判定：没有新的证据时，不继续堆 patch。

03-05 Review / 先看业务风险再看代码风格 验收

痛点：Agent 生成速度上去了，人工判断却仍按原节奏，审查变成瓶颈。

  • 先验验收标准，再测试结果；治业务路径查权限、状态、并发和回滚。
  • 小 MR，复核需求拆成可独立验收的 Issue。
  • Review 关注有效问题遗漏和用户风险，不追求评论数量。
PROMPT 复制口令
按业务路径做 Review: 先列高风险假设，再逐项给出证据、影响、修复建议和未确认项。
验收判定：每条评论都必须能改变风险、验收或维护成本。

03-06 工具返回合理 / 不等于业务正确 验收

痛点：DB、日志和 Trace 能说明发生了什么，却不能替业务定义什么是对。

  • 先写业务契约和预期结果，再让工具提供证据。
  • 把事实、推断、未确认分开。
  • 对 Agent 产品，还要评估答案质量、定性和拒答边界。
PROMPT 复制口令
先写业务契约，再让工具证明结果；不要让工具替你定义正确答案。
验收判定：结论必须同时有业务依据和可定位的运行证据。

04Creative Workflow：让 Prompt 可读、可控、可复用

主题聚焦：图像 · 视频 · UI · 设计系统 · 审美参考 · 复刻 ｜ 关联阶段：设计/需求

04-01 Prompt 不用专业 / 要写到自己读得懂 设计

痛点：复杂术语堆在一起，自己都无法检查，模型也难以稳定复现。

  • 先写主体、风格、构图、媒介，再补镜头、光线、材质和约束。
  • 把目标拆成可观察的画面条件，而不是形容词堆叠。
  • 让 AI 帮你看改写，但最终 Prompt 必须能被自己读懂和验收。
PROMPT 复制口令
【主体】x【风格】x【构图】x【媒介】；请把我的想法改写成我能读懂、能逐项检查的 Prompt。
验收判定：每个形容词都要对应可观察的画面证据。

04-02 视频从想法到成片 / 先管前 2 秒和镜头 需求

痛点：旁白塞太满、方向没定、细节越改越重，成片反而失去重点。

  • 先确定钩子、节奏和镜头功能，再写逐拍时间线。
  • 每个镜头只承担一个信息或情绪任务。
  • 用参考图、角色设定和镜头语言保持镜头一致。
PROMPT 复制口令
请先给出前 2 秒钩子、镜头时间线、每镜头的动作与转场，再生成完整视频 Prompt。
验收判定：删掉不能服务主题、节奏或转化的镜头。

04-03 抄参考 / 先提取设计系统 设计

痛点：只看截图容易抄到表面，配色、字体、间距和组件关系仍靠猜。

  • 从真实网站提取颜色、字体、间距、阴影、圆角和状态。
  • 用 Design.md / design system 把审美决策写成可复用约束。
  • 把参考分成灵感、规范、组件和验收，不要混成一张收藏夹。
PROMPT 复制口令
请从这个参考网站提取一份可执行设计系统：色板、字体层级、间距、组件、状态、无障碍和验收清单。
验收判定：输出必须能直接指导实现和 Review，而不是只说“高级、简洁”。

04-04 风格库 / 用编号减少描述成本 设计

痛点：审美词汇不稳定，团队和模型对“手绘、电影感、高级”理解不一致。

  • 把风格做成编号画廊，选择时引用编号而不是重复形容。
  • 为每种风格保存中英描述、适用场景和反例。
  • 风格只是变量，仍要单独定义主体、构图、媒介和约束。
PROMPT 复制口令
浏览风格画廊，选出最适合主题的 1 个风格编号，并说明它与主体、构图和媒介如何组合。
验收判定：风格选择必须能解释为什么适合当前任务。

04-05 复刻 / 先拆结构再换内容 设计

痛点：看到结果就照抄，往往只能复制表面，无法迁移到新主题。

  • 拆出镜头、角色、服装、光影、动作、节奏和负面约束。
  • 先固定结构，再替换主体；每轮只改变一个变量。
  • 用对照图或片段回看判断是哪一层造成差异。
PROMPT 复制口令
请把这个参考拆成结构变量与内容变量；先保持结构不变，只替换主体，并列出每轮对照检查项。
验收判定：复刻结果要能说明差异来自哪个变量。

04-06 UI 不是堆功能 / 是任务与层级 设计

痛点：页面看起来完整，却没有清晰任务路径，AI 带来无意义装饰和默认组件。

  • 先写用户任务、信息层级和状态，再选组件和动作。
  • 用高内聚、低耦合组织页面；动效服务反馈，不服务炫技。
  • 把无障碍、响应式、性能和文案纳入设计验收。
PROMPT 复制口令
请按用户任务重构这个页面：先列层级、关键状态和操作路径，再决定组件、动效和视觉风格。
验收判定：每个视觉元素都要服务理解、操作或反馈。

05Product & Growth：从有人感兴趣，到有人付费

主题聚焦：需求验证 · 竞品 · SEO · 内容增长 · 电商 · 自动化 ｜ 关联阶段：需求/交付/运营

05-01 早期验证 / 不要把兴趣当需求 需求

痛点：点赞、浏览和口头喜欢很容易，真实付出才能接近购买意愿。

  • 按用户付出排序：看过 → 收藏 → 留邮箱 → 回消息 → 试用 → 验收 → 预付 → 续费。
  • 为每一级信号设最小样本和下一步动作。
  • 把“有人感兴趣”与“有人愿买单”分成两个结论。
PROMPT 复制口令
请把这个想法拆成信号阶梯：每一级需要用户付出什么、如何观察、什么结果才允许进入下一步？
验收判定：没有最高成本信号前，不要把曝光写成 PMF。

05-02 竞品调研 / 先找切入口再做功能 需求

痛点：资料很多，但没有形成目标用户、替代方案和可交付缺口。

  • 从真实用户问题出发，再翻译成用户会搜索的关键词。
  • 按场景、价格、分发、交付和留存比较竞品。
  • 把观察写成可验证假设，而不是一份链接堆。
PROMPT 复制口令
请做竞品调研：用户任务 → 搜索词 → 竞品替代 → 未满足需求 → 可测试切入口，并标注证据源。
验收判定：每个结论都要能回到用户行为或公开证据。

05-03 内容增长 / 把一次实践沉淀成方法 迭代

痛点：内容靠灵感重复生产，经验无法复用，热点也难以转变成长期资产。

  • 把一次实践拆成问题、过程、结果、证据和可复用模板。
  • 建立知识库：专题、案例、镜头语言和词库等索引。
  • 用前 5 秒对照实验优化钩子，而不是只看总播放。
PROMPT 复制口令
把这次实践整理成可复用内容资产：问题、受众、过程、结果、证据、模板、下一次实验。
验收判定：内容必须留下下次可以直接执行的动作。

05-04 自动化 / 先拆链路再接工具 开发

痛点：把多个平台和 Agent 串起来很容易，但错误会被自动化放大。

  • 先列输入、转换、审批、输出和回滚；再选择 MCP 或 API。
  • 高风险动作保留人工确认，低风险动作交给专用执行器。
  • 记录每一步的状态、权限、失败重试和来源。
PROMPT 复制口令
请把这条业务链路画成状态机：输入 → 抽取 → 分类 → 生成 → 审批 → 发布 → 复盘，并标注人工门。
验收判定：没有权限、幂等和回滚设计时，不做全自动发布。

05-05 SEO / 从真实站点证据开始 交付

痛点：套模板写 SEO 报告，容易忽略 robots、跳转、死链和 JS 内容。

  • 真实抓取站点、站点地图、canonical、结构化数据和核心网页指标。
  • 每个问题给出 URL、规则、影响和修复建议。
  • 修复后再次跑同一套检查，比较前后结果。
PROMPT 复制口令
请对这个站点做真实审计：抓取 → 规则检查 → 证据 → 影响 → 修复 → 复测；不要只给通用建议。
验收判定：报告必须能定位到页面和规则，不能只写“优化内容”。

05-06 电商 / 让 AI 负责流程，人负责契约 运营

痛点：从选品到上架、文案、出图和投放都自动化，最怕品牌和业务标准失控。

  • 先定义品牌、商品、合规和利润规则，再让 Agent 执行。
  • 把素材、文案、库存、订单和投放拆成可检验步骤。
  • 关键发布、付款和客服升级保留人工审批。
PROMPT 复制口令
请把这条电商流程拆成可独立验收的 Skills，并为每一步写输入、输出和人工审批点。
验收判定：自动化不能绕过合规、价格、库存和品牌边界。

06Data & Research：把资料变成可行动知识

主题聚焦：RAG · 检索 · 数据链路 · 知识图谱 · 学习 ｜ 关联阶段：设计/运营/管理

06-01 资料很多 / 先找来源和证据边界 管理

痛点：AI 总结流畅，但读者分不清哪句来自原文，哪句是模型补全。

  • 保留原始链接、文档版本、抓取时间和可见范围。
  • 把原文事实、作者观点、我的推断分层。
  • 折叠、付费墙、摘要和二手转述都要显式标记。
PROMPT 复制口令
请输出：原文事实 / 作者观点 / 你的推断 / 未确认缺口；每条事实给出定位来源。
验收判定：没有原文证据时，不把推断写成事实。

06-02 RAG / 先问检索结构是否适合任务 设计

痛点：切块、向量和相似度搜索并非所有文档任务的最优解。

  • 对长文档先保留层级、章节、表格和引用关系。
  • 比较向量检索、关键词、树状索引和 Agent 导航。
  • 用代表性问题集测准确、召回、成本和可解释性。
PROMPT 复制口令
请先分析文档结构和问题类型，再比较向量、关键词、树状索引等检索方案，给出基线与评测集。
验收判定：不要因为“大家常用 RAG”跳过任务结构分析。

06-03 数据工程 / 用状态机和 Provenance 管住链路 开发

痛点：数据产生、摄取、存储、处理、发布混在一起，失败后无法定位。

  • 把目标、状态、关系、变换、执行、记录拆开。
  • 用状态机管理生命周期，DAG 管依赖，Provenance 管可信度。
  • 每次转换记录输入、版本、规则、输出和责任边界。
PROMPT 复制口令
请把这个数据流程建模为：状态机 + DAG + I/O + 执行器 + Provenance，并列出每个状态的进入与退出条件。
验收判定：任何结果都能回到源头、变换和版本。

06-04 陌生领域 / 先建地图再深入 需求

痛点：资料散落，概念、人物、项目和来源互相混淆，学习路径不可见。

  • 先建立实体页、概念页、来源页和关系页。
  • 把读过的内容沉淀成问题清单和下一步研究动作。
  • 为每个结论保留来源和时间，定期清理过期信息。
PROMPT 复制口令
请把这些资料整理成知识地图：实体、概念、关系、来源、证据等级和待验证问题。
验收判定：地图要能指导下一次搜索，而不是只做漂亮目录。

06-05 学习材料 / 让 AI 解释但不替你相信 验收

痛点：一本书、PDF 或课程很难系统读完，摘要又可能混入幻觉。

  • 先按章节、概念、例子和练习建立阅读路线。
  • 每个答案同时给出原文摘录、解释、反例和自测题。
  • 对关键结论回到原质核对，记录未读与未验证范围。
PROMPT 复制口令
请把这份材料变成交互式学习路径：章节 → 核心概念 → 原文证据 → 例子 → 自测题 → 待复习。
验收判定：解释必须能回到材料，不能只凭常识补全。

06-06 研究闭环 / 从信息摄取到可执行决策 管理

痛点：收藏、阅读和转发很多，但没有排序、筛选、实验和反馈。

  • 先过滤时效、来源质量和与当前目标的相关性。
  • 再抽取、打标签、聚类、评分，最后只深挖高价值候选。
  • 把研究结果写成决策、行动、验证和复盘，而不是日报堆积。
PROMPT 复制口令
请把这批资料按相关性、具体程度、可信度和时效评分，给出今日优先阅读与下一步实验。
验收判定：每条研究输出至少导向一个可执行动作或明确的“不做”。
