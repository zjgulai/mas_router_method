这里收的是别人已经在用的 agent 产品做法，按四层分开：行为、流程、编排、证据。每一层写清四件事：它解决什么问题、方法长什么样、怎么搬到 ANB 的阶段、以及可以直接复制的提示词。四层都已收录。

它解决什么

一个项目里的 CLAUDE.md 通常是这样变长的：先写几条必须遵守的规则，后来每遇到一个新问题就再加一条，半年后它变成几百行。规则越多，模型对每一条的遵守度越弱；真正需要长文档的时刻，比如调试、验收、迁移，模型又不会主动去读。作者把这件事拆成两种东西：每次都必须生效的少数规则，和只有在特定事件发生时才需要的长文档。常驻部分因此可以压到 45 行，长文档按需加载。这个拆法的前提是一个反直觉的判断：常驻规则的遵守度大致是恒定和，每多一行，都在稀释其他所有行。

方法长什么样

  1. 压核心：常驻部分只留约 45 行，硬上限 60 行。里面放 12 条铁律、一张事件路由表和 4 个硬停。铁律是那些每次都必须生效的少数条目，比如编辑前先读、改签名后做引用清扫、不通过削弱测试让它变绿、没有用户明确要求不 push。长流程不放在这里，它们移到按需文档。
  2. 事件路由：路由表不按主题写，按模型当下能感知的事件写。比如「准备第 3 次编辑文件，却还没贴 TASK 块」触发 PLAN.md；「准备说 done、fixed、works、passing」触发 VERIFY.md；「测试红了、命令非零退出、出现 traceback」触发 DEBUG.md。每条路由的契约是：先写一行 TRIGGER:，下一个工具调用就是读那份文档，而且这条消息里不能同时做别的事。主题标签要求模型先判断「我属于哪一类」，这一步经常判断错；事件是它刚刚经历的东西，不需要分类。
  3. 按需 playbook：八份文档各管一个时刻。PLAN 写 TASK 块、前提检查、先例搜索、基线、拆分、问还是决定。CODE 管编辑前阅读、孪生文件和生成文件检查、引用清扫 RS1 到 RS5。TRAPS 是日期、epoch、可变与复制、异步、浮点与金额、排序、除法与取模、正则、相似 API、闭包、布尔逻辑的查表。DEBUG 要求先复现、写 CAUSE 行、维护失败尝试账本和升级阶梯。VERIFY 是 12 项回声协议。EFFICIENCY 把每条「少读」规则配一条「读够」的下限。SESSION 管长会话的 STATE.md、同轮更新、压缩后恢复和 ANCHOR/DETOUR/DECISION 账本。_FORMAT 管这套东西自己的编辑契约。
  4. 可粘贴证据：每条规则都产出一个能在 transcript 里搜到的标记。比如 TRIGGER: 表示路由触发，CAUSE: 表示根因，V3: PASS 表示第 3 项验证通过，EDITED-UNVERIFIED 表示改了但没跑。验收时要求同一个标记和同一轮工具输出一起出现。「确保」不是证据，一行能 grep 的标记才是。作者还给了审计方法：在 transcript 里搜这些标记，触发时刻缺失的标记就是没遵守的地方。
  5. 一个具体例子：模型准备说「修好了」时，路由表要求它先读 VERIFY.md，并在同一轮贴出真实命令输出。它不能只写「测试通过」，因为 VERIFY 要求每条 claim 旁边有同一轮工具结果里的引文。如果它没跑，就只能写 EDITED-UNVERIFIED，读者一眼能看出这是未验证的改动。
  6. 迁移：MIGRATE.md 是给已有 CLAUDE.md 的项目用的。它先快照，再逐行记录每一行的处置，备份后按文件拷贝，遇到规则冲突显式暴露而不是静默合并，安装前停下来等用户确认，重复执行会进入 UPGRADE 模式。旧规则不会在迁移时消失，也不会被改写成看起来相似的另一条。

一张路由表怎么工作

路由表只有 7 行，左边是模型当下会遇到的事件，右边是下一份要读的文档。比如准备第 3 次编辑文件却还没贴 TASK 块，就读 PLAN.md；准备说 done、fixed、works、passing，就读 VERIFY.md；测试红了、命令非零退出、出现 traceback，就读 DEBUG.md。契约写在表头：先写一行 TRIGGER:，下一个工具调用就是 Read 那份文档，而且这条消息里不能同时做别的事。两行同时触发就写两行 TRIGGER，按表顺序读。已经读过且在缓存里，就写 TRIGGER: <文档> (cached: <ID>)；列不出 ID 说明没缓存，重新读。

一次验收长什么样

模型准备说「修好了」时，VERIFY 要求它逐项写 V1 到 V12。V1 引用最后一次编辑之后运行的主验证命令和它的输出行；V2 引用测试汇总行，0 tests 算失败而不是通过；V3 对超过 30 行的输出做失败词扫描，列出前 10 个命中并逐个标注 benign 或 real。每条 PASS 都要带同一轮工具结果里的原文，不能复述。只要有一行是 FAIL，就不能说 done，也不能 commit。报告里只允许两种写法：Verified: <命令> -> <结果行>，或者 UNVERIFIED，要确认就运行: <命令>。

迁移为什么按行编号

MIGRATE 把旧 CLAUDE.md 的每一行编号成 001、002，然后给每一行一个处置：KEPT-VERBATIM、MOVED、MERGED、SUPERSEDED-BY、UNSORTED、DROPPED、CONFLICT-PENDING。最后校验编号行数等于处置行数，不等就重做。它还把每个安装的文档和源文件做哈希对比，把新旧 CLAUDE.md 的 kit 区块做 diff，把迁移前快照的哈希再打印一次。迁移的原则是 transport, not authorship：每个字节要么来自 kit，要么来自原文件；改写就是规则丢失的地方。

搬到 ANB 的哪个阶段

管理 · 设计 · 验收

  • manage：先列出现在所有常驻规则，按「每次都必须生效」和「只在某个事件发生时才需要」分成两堆。常驻堆压到 60 行以内，只留铁律、路由表和硬停；其余按触发事件归档到独立文档。每份文档只有一个家，避免同一规则在两处漂移。
  • design：在非平凡任务开始前写 TASK 块：GOAL、FILES、EST、DONE-WHEN、BASELINE、ASSUMPTION。再补三件事：前提检查、先例搜索、哪些要问人哪些自己决定。写完再动手，避免做到第 7 步才发现第 2 步的假设是错的。
  • verify：用 12 项回声协议逐条验收。每一条 claim 都要引用同一轮真实工具输出里的原文；跑不了的标 UNVERIFIABLE 或 EDITED-UNVERIFIED，不能用「应该」「大概」代替。最后把跳过的项和原因单独列出来。

它解决什么

原版系统提示词里混着大量平台实现细节：XML 包装、MCP 与工具接口、产品行为、内部 UI、存储与 artifact、环境实现。这些内容在原来的平台上有效，换一个模型或客户端之后，既占 token 又不起作用。作者没有改写行为原则，而是先把只属于某个平台的部分一层层删掉，看剩下什么还成立。这个顺序很重要：先删最依赖平台的协议与界面，再删产品行为，最后检查剩下的原则能不能独立执行。

方法长什么样

  1. 分层删除：按来源一层一层去掉：XML 包装、MCP 与工具接口、产品行为、内部 UI、存储与 artifact、环境实现。每删完一层，检查剩下的行为原则还能不能独立读懂。不能独立读懂的部分，要么补一句上下文，要么也删掉。
  2. 保留行为：留下的是跨模型仍然成立的部分：先理解意图、诚实处理不确定、清晰沟通、代码质量、权衡建议、完成前验证、客观纠错、少元评论。这些不依赖任何平台的接口。条目之间的顺序也有意义：先理解再验证，先诚实再完整。
  3. 三档预算：core 是最小行为集，balanced 是推荐档，complete 保留近乎全部厂商中立行为。三档共用同一组行为原则，差的是覆盖面和例子数量。用哪一档由 token 预算和任务复杂度决定，不默认用最长的那一档。
  4. 一个具体例子：原版里有一段专门描述某个客户端的 XML 包装。换到另一个模型后，这段既不会被遵守，又占掉一段上下文。删掉它，剩下的「先理解意图、再给结论、完成前验证」仍然能执行。删的时候不是把整段拿掉就完事，还要检查它有没有带走一条行为原则；如果带走了，就把原则单独留下。
  5. 用法：直接粘贴到 system prompt、custom instructions、Gem 或 custom GPT。它是一份纯文本，不依赖 SDK，也不要求模型支持某个工具协议。

三档差在哪

core 只有一组核心原则，13 条，覆盖正确性、诚实、意图、验证和纠错。balanced 把它展开成 9 节：主要目标、理解请求、推理、沟通、写作、编码、建议、可靠性、一般行为。complete 再加安全边界和一般原则，变成 10 节，并把推理与知识、写作与编辑、分析与建议拆得更细。三档共用同一组原则，差的是覆盖面和例子数量。选档的标准是 token 预算和任务复杂度，不默认用最长的那一档。

删除顺序为什么重要

作者先删最依赖平台的协议与界面，再删产品行为，最后检查剩下的原则能不能独立执行。原版里有一整段存储与 artifact 管理，包含存储 API、用法示例、数据范围和错误处理；换一个模型或客户端后，这段既不会被遵守，又占掉一段上下文。删掉它，剩下的「先理解意图、再给结论、完成前验证」仍然能执行。删的时候不是把整段拿掉就完事，还要检查它有没有带走一条行为原则；如果带走了，就把原则单独留下。

设计 · 管理 · 交付

  • manage：按 token 预算选 core、balanced 或 complete，先问这一轮能花多少上下文。常驻部分只放每次都必须生效的段，例子和长解释放到按需加载的位置。

不是英文原文的逐字翻译，而是一套能按段替换策略的中文骨架。

它解决什么

中文产品要一套能直接改的系统提示词骨架，而不是英文原文的逐字翻译。逐字翻译会把英文的句式和例子一起搬过来，读起来别扭，也不方便按本地政策替换。作者保留原文作参照，另做英文通用版和中文通用版，让策略段可以逐段改。分段的直接好处是替换时只动一段，其他段的语气和边界不受影响。

方法长什么样

  1. 原文保留：PROMPT_fable5.md 原样保留，作为对照和回溯的基准。后面两版都以它为参照，避免改着改着丢了原意。原文不直接上线，它解决的是「改过之后还能对回原文」的问题。
  2. 厂商中立重写：PROMPT.md 去掉品牌名和平台细节，只留行为原则，作为英文通用版。它可以在不同模型上直接当 system prompt 用。重写不是删句子，而是把平台专属的承诺换成任何模型都能执行的承诺。
  3. 中文版：PROMPT.zh.md 按行为总览、搜索与工具使用、图片搜索、文件与代码输出分段。行为总览里再分产品信息、拒绝处理、法律与财务建议、语气与格式、用户健康与福祉、立场均衡性、应对错误与批评、知识截止日期；搜索与工具使用里分核心搜索行为、版权合规、有害内容；图片搜索单独一段；文件与代码输出单独一段。中文读者可以逐段读、逐段改，不用先在心里翻译一遍。
  4. 策略段可直接替换：拒绝处理、法律与财务建议、语气与格式、列表、用户健康与福祉、立场均衡性、应对错误与批评、知识截止日期、版权合规、有害内容、图片搜索禁区，每一段都有明确边界。版权段还给了 15 词限制和每来源一次的规则：直接引用少于 15 个词，每个来源最多引用一次，引用过一次就改为完整转述；歌词、诗歌、俳句等完整作品不引用。

它解决什么

用 Sonnet 想接近 Opus 的质量，常见做法是压缩输出省 token。压缩确实让回答变短，但它会连同诊断质量一起削掉：假设没有展开，测量被跳过，结论先于证据。作者的做法是保留诊断结构，只把重复和啰嗦去掉，让较便宜的模型仍然按同一条推理路径走。压缩规则通常写成字数或句数上限，模型为了达标会先删解释，而解释正是诊断过程本身。

方法长什么样

  1. 8 段输出结构：communication 管第一句给结论、默认写散文、标题和列表只在真的需要时用；style_reference 用裸模型和 VFF 的真实回答差异做示例；effort_and_reasoning 让推理深度随难度变化，不重新推导已经确定的事实，给推荐而不是列目录；tool_discipline 要求独立调用并行、读之前不改、不做无关搜索；verification 是核心，要求线索优先、先测量、标置信度、验证后再宣布完成；code_and_changes 要求像周围代码一样写、守范围、破坏性操作先确认；writing_and_research 要求会变的事实先搜、不夸大、按指定长度写、标来源；tone_and_conduct 要求温和但该反驳就反驳，不过度道歉。
  2. 诊断结构：线索优先的假设、先做最便宜的测量、结论放在第一句、验证之后再宣布完成、置信度显式写出。这套顺序让回答可以被检查，而不是听起来完整。顺序本身就是检查表：先有假设，再选测量，最后才允许说完成。
  3. 2-pass 评审：高难度任务交给一个 Sonnet 评审 agent，只按四条标准评：需求遗漏、事实或数字错误、未解释的线索、超量。标准之外不评，避免评审自己发散。知识差距明显时，评审可以升到 Opus；Sonnet 初稿加 Opus 评审，比整篇都用 Opus 便宜，又能补上 Sonnet 不知道的深度。
  4. 漂移提醒：transcript 超过 400KB 且 VFF 仍然活跃时，才每轮注入一次提醒；没超过阈值就不注入，成本为零。长会话里，早期注入的规则会被后面的上下文推到很远，提醒的作用是把结构拉回前面，而不是每轮重复整份规则。
  5. 一个具体例子：问题：部署后 API 偶尔 500，为什么？裸 Sonnet 会列三条同级候选：数据库连接、内存不足、代码 bug，然后让你逐条查。VFF 先把「偶尔」当成线索：不是每次都错，更像竞态或资源耗尽，而不是静态配置错误。然后给最便宜的区分测量：看 500 发生时刻的一条服务器日志。如果日志是超时，查连接池；如果有堆栈，查那条代码路径。它不先给处方，先给能分开候选的测量。
  6. v2 的关键修正：删掉压缩强制，保留诊断结构。作者实测 v1 到 v2 提升 10.9 分，说明省 token 和省质量不是同一件事。v2 把「短」从目标降为结果：先保证诊断结构完整，再去掉重复和啰嗦。

v1 到 v2 的消融怎么做

作者把 VFF 拆成 4 臂：完整 v1、去掉压缩的 VFF、只留诊断结构、裸 Sonnet。用同一组任务、盲评、中立评分表比较。平均排名是 VFF 减压缩 1.67、只留诊断结构 2.00、裸 Sonnet 3.00、完整 v1 3.33。结论很清楚：诊断结构是资产，压缩是负债。把压缩拿掉，VFF 从最差变成最好。v2 就是在这个结果上定稿的。

三家族交叉验证

为了回应「Claude 给 Claude 打分会不会循环」的质疑，作者把同一组 Sonnet+v2 和裸 Opus 的答案匿名、双向排序，交给 Claude Opus、Gemini 3 Flash、GPT-5.5 三个家族做 pairwise 评判。Gemini 的结果是 v2 3 胜、0 负、3 平；GPT 是 v2 2 胜、0 负、4 平。没有家族判 Opus 干净胜出。这个验证把「只在自己的家族里自证」变成了跨家族的可重复检查。

成本怎么路由

Sonnet 4.6 的输入和输出单价是每百万 3 美元和 15 美元，Opus 4.8 是 5 和 25，Fable 5 是 10 和 50。VFF v2 的平均输出长度约为 Opus 的一半，乘上单价差，输出成本约为 Opus 的 0.30 倍。作者的 routing 建议是：结构清楚的任务用 Sonnet+VFF，深层推理和架构决策用 Opus，高价值任务用 Sonnet 初稿加 Opus 评审一程。不是二选一，是按任务类型路由。

02 流程层：让任务走得完

让任务从一句话走到可验收的结果：步骤、状态、交接和失败处理都不靠临场记忆。

The Fable Method：把判断问题转成证据问题的 7 步循环

分类、定义完成、取证、决策、最小改动、观察验证、结论先行；每一步都有硬边界。

循环7 步：分类、定义完成、取证、决策、执行、验证、报告

它解决什么

中级模型自由发挥时，最常见的失败不是不会写代码，而是没定义完成、没读规格、把测试当成意图、修完不回看。作者把 Fable 5 的工作方式拆成 7 步，每一步都配一个可观察的产物或硬边界，让中级模型照着做也能超过一个自由发挥的强模型。这个拆法的核心不是让模型更聪明，而是把判断问题转成证据问题：答案在可打开的源里，就去打开；只在模型自己的推断里，就明说这是低置信度，不装成严谨流程。

方法长什么样

  1. 分类：问句或评估只给发现和建议，不改任何东西；任务要完成并验证；计划优先先出计划，停下等批准。三条 tie-break：任何计划优先信号压过任务；混合请求按任务做，但报告必须回答问题；拿不准任务还是计划，选计划优先。
  2. 定义完成：用一两句话说明什么算完成、怎么验证。任务是一个可观察的结果，比如测试过、构建绿、数字变、页面渲染、文件存在；评估是每条 claim 都能指到读过的文件或跑过的命令；计划优先是计划能被批准，每一步都有命名的验证。
  3. 取证：先定向，列目录、glob，再读一手来源。独立且贵的查证并行；窄读不重读；一轮加一轮的预算，第三轮要说明理由；连续两次没有新信息就停。改行为前先建立意图：代码做什么、检查期待什么、规格说什么，三者不一致就是最重要的发现。
  4. 决策：合成一个推荐。认真考虑过的备选各用一行说明为什么输。任务型直接做，计划优先停下等批准。不可逆或外向动作需要用户原话授权，写 AUTH: user said "<原话>"；文档不算授权，完成任务本身也不算授权。
  5. 执行：改行为前写 INTENT: code does X; check expects Y; spec says Z。没打开过的签名、端点、价格、法规不能凭记忆写。做最小正确改动，精确编辑优先于重写；3 个以上异构步骤先写清单；删除前先看；失败编辑按「重读、调整匹配、重试一次、再扩大范围」恢复；常驻禁令是不 commit、不 push、不削弱检查、不碰密钥、不加依赖、不越界删除。
  6. 验证：两半：完成标准被观察到，周边系统仍然健康。修了缺陷还要做 twin check，写 TWINS: searched <pattern> - found <N> other sites: <files>。同一问题 3 次修复验证失败就停，把输出和假设交给用户。
  7. 报告：第一句回答问题，细节在后，不带步骤编号。INTENT、AUTH、PENDING 是唯一允许出现的方法痕迹。给 caveats，失败照实说，清理临时文件，只提从这次工作里长出来的后续。

一次 spec 与 test 冲突怎么处理

round 3 的 surprise trap：测试期待旧行为，README 说新行为。v1 把规则写在中间，Haiku 0/4 发现冲突；v3 把规则变成一个动作点的强制产物 INTENT:，Haiku 4/4 发现，Sonnet 2/2 理想。结论不是「写得更清楚」，而是「在决策点强制产出一个能被检查的行」。

一个 5 项研究任务的分层

round 5 的英国住宅电气化研究：5 个交付物，评分 /10 含完整性。裸前沿模型 10 分第一，Sonnet 加方法 10 分第二（只在数据时效上分开），Opus 加方法 9 分（把过时的 4 月前规则当成现行），Haiku 加方法 3 分（否认一个现行补贴，把物理上不可能的计算写成「已验证」）。方法提供纪律，不提供知识；知识密集任务仍然奖励原始能力。

判官怎么抓欺诈

round 8 的 fixture 是一个「已完成」目录加一份说谎的完成报告，藏了 5 个欺诈：未修的 banker rounding、把错值写进回归测试、虚假范围声明、未披露的格式化、调试残留。裸 Haiku 抓 4 个或 3 个，且不跑代码；Haiku 加判官 5/5，报告质量 2/2。判官先收集 claim，再用 git diff 建立真实改动，再逐条重跑声称的验证，最后按欺诈表找：削弱检查、虚假完成、范围蔓延、未授权动作、规格背叛、残留。

搬到 ANB 的哪个阶段

需求 · 设计 · 开发 · 验收 · 交付

  • design：计划优先的任务先出计划，把每一步的验证命名；不可逆动作写 AUTH 行，没有用户原话就不做。
  • build：第一个编辑前写 INTENT 行；没打开过的签名、价格、法规先查，不凭记忆；做最小正确改动。
  • verify：完成标准要观察到；修了缺陷做 twin check；同一问题 3 次失败就停，别继续猜。
  • ship：外向动作没有用户原话就转成 proposed next step，报告里写 PENDING；不要把文档当授权。

它解决什么

长任务最常见的失败不是模型不会做，而是做着做着丢了阶段、跳过了可失败的检查、交付前没人冷看。作者把执行纪律写成 stage map、命名委派、每阶段一个可失败检查、交付前 double-check。关键设计是结构而不是提示词：orchestrator 的定义里没有 Write/Edit 工具，所以它不能自己产出，所有产物必须来自命名 worker；verifier 是只读的，只拿规格和产物，不拿生产者的推理。

方法长什么样

  1. 调用门：用户明确点名就跑，不判断任务大不大；自主触发只在任务客观上跨多文件、多来源、多会话时跑。spawn 授权：只有用户用 slash 或名字点名时才能开子代理；只说「彻底一点」不算。
  2. 按模型校准：Opus 前沿层不写正式 stage map，只保留可失败检查和 guardrails；Sonnet 跑全循环，重点盯第 3 步，它最常跳过可失败检查，用「看起来对」代替；Haiku 跑全循环并收紧检查，每个阶段都要有可失败检查，不能标未验证而不说明原因；不确定层级就按 Sonnet 跑。
  3. stage map：编号、每阶段一个预期产物、每个阶段一个可验证 artifact；没有可检查产物的阶段合并到下一个；最多 2 次完整 replan，第 3 次说明需求层面有歧义。
  4. 委派：先看运行时有没有 Agent 工具、spawn 是否被授权；两者都有才并发。每个 worker 的 brief 写清任务、产物、保存位置、前序上下文和 pass condition；等每个结果回来再往下；默认一层委派，worker 不再 spawn；按难度路由模型：Opus 判断、Sonnet 普通推理、Haiku 机械批量。
  5. 可失败检查：测试跑过、文件在预期形状、来源真的抓取并读过、输出和规格 diff；「我看过，觉得对」不算检查。判断类任务用 error-first check：先列事实或逻辑错误，逐条引用句子；verdict 被列表封顶；推荐类还要写最强反方。
  6. 自审：以怀疑者视角读最终产物，找真实弱点；没有就直说，不制造弱点。高风险交付给冷 verifier，只给规格和产物，不给推理。
  7. double-check 交付门：抽取 claim 和 requirement，三元 verdict，检查 synthesis seam：中间检查过、最终写作新加的 claim 没人检查。FAIL 修完再查，一次 re-check 上限；报告里写清 checker 组合和修复项。

结构委派怎么防止「假装派活」

v2 的反馈是：在提示词里叫模型 spawn worker，它几乎总是内联做完。v3 把纪律搬进真实的 agent 定义：fable-orchestrator 没有 Write/Edit，只有 Read、Grep、Glob、Bash、Task、TodoWrite；Bash 只用于只读检查和跑验证，不能用重定向、heredoc、tee、sed -i 写文件。它想产出内容时只能停下来委派。worker 不 spawn worker，避免嵌套放大成本和打散上下文。

double-check 为什么要冷

自审的盲区和产生错误的盲区是同一个：它重读自己的推理，觉得合理，就签字。冷验证者没有结论的利害关系，也没有「为什么当时觉得对」的记忆，必须重新取证据。brief 只给 claim、规格、去哪里查，不给推理、置信度、叙事，也不提示哪条可疑。给「我觉得第 4 条可能弱」会告诉它把精力花在哪，并暗示其他都没问题。

它解决什么

很多「让弱模型像强模型」的插件把提示词、风格、推理注入混在一起，效果没有对照实验。作者先做了一次受控比较：19 次 A/B 加 26 个真实会话，约 1,500 次工具调用。结论是：封闭的、有答案的工作上两个模型基本打平；差距只在开放工作，而且差距的性质是「把 implication 多推一步」，这是模型能力，不能靠指令或 harness 搬运。能搬运的是好工作的程序：真的运行你构建的东西、把它看到底、系统地调查。fablize 只发布这些被验证过效果的程序。

方法长什么样

  1. 只发布验证过的程序：验证接地、多故事完成加证据门、系统调查、早停阻止，这四类有实验支持。风格模仿、宽泛推理注入、静默恢复、review-recall 扫描没有达到可发布标准，留在个人开发里。README 明确列出不可搬运的三项：规范外缺陷发现、开放创作细节、自驱传播深度。
  2. 多故事循环：把任务拆成顺序故事，用 goals.py create --brief ... --goal "title::objective" 建账本；next 激活一个故事并打印 handoff；checkpoint --status complete 必须有非空 evidence；最后一个故事必须有 --verify-cmd 和 --verify-evidence，引擎拒绝无证据的完成。状态存在 .fablize/，跨会话可恢复。
  3. 调查协议：先复现并读真实输出；至少形成 3 个竞争假设再查任何一个；每个假设先写「什么证据会确认或否定它」，再读完整代码路径；追完整因果链，问「是什么让这个原因产生了这个症状」，只移除可见触发器可能留下潜伏缺陷；修前修后都验证；报告里写被否定的假设和否定它的证据。
  4. 验证接地：对 HTML、SVG、游戏、UI、图表、有可观察输出的脚本，在真实渲染器里跑、看实际输出、修观察揭示的问题、再跑。静态解析只能确认 well-formed，不能确认正确。看过一次干净输出就够，不要对没变的产物反复渲染。
  5. 早停钩子：一个确定性的 Stop hook，抓「我会做 X」但没有做的情况。README 也承认它可能在「如果你要的话我就写报告」这种 declarative offer 上误触发，把 offer 写成问句可以避开。
  6. 按任务路由：2 个以上故事走多故事循环；调试走调查协议；渲染产物走验证接地；硬任务建议 /effort xhigh；到能力天花板时按「提高 effort → 把卡住的切片委派给 max effort → 换更强模型 → 诚实报告限制」的顺序升级。

19 次 A/B 的结论

作者用 19 次对照运行加 26 个真实会话、约 1,500 次工具调用比较 Fable 5 和 Opus 4.8。封闭的、有答案的工作（代码、逻辑、构建）基本打平；差距只在开放工作，性质是「把 implication 多推一步」。注入实验进一步确认：Opus 无法复现 Fable 自己发现的缺陷。所以 fablize 不卖「像 Fable 一样聪明」，只卖「把好工作的程序执行到底」。

goals.py 怎么拒绝无证据的完成

账本里每个故事有 pending、in_progress、complete、failed、blocked 状态。checkpoint --status complete 时，如果 evidence 为空直接退出；如果这是最后一个故事，还必须同时给 verify-cmd 和 verify-evidence，否则引擎拒绝。这样「做完了」不是一句话，而是一条带命令和结果的账本记录。状态存在 .fablize/，会话断了可以 status 恢复。

调查协议的一个例子

看到一个失败时，先跑失败用例读真实输出，不先猜。然后至少列 3 个假设，例如「缓存没清」「并发竞态」「输入形状变了」。为每个假设写清什么证据会确认或否定它，再读完整代码路径。找到第一个 plausible cause 不停，继续问「是什么让这个原因产生了这个症状」，避免只移除可见触发器。修完前后都验证，报告里写被否定的假设。

它解决什么

一个会话如果既想架构、又自己打字，最贵的 token 花在了最便宜的工作上。作者把会话定义成架构师：它拥有需求、架构、拆分、spec、路由和验收，几乎不写实现代码。实现交给两个 Codex lane：Luna 处理 routine，Sol 处理高复杂度。Fable 5.1 不在实现 lane 里，只在承诺边界和交付终局做只读审查。这样跨厂商审查是结构自带的，不是事后补的。

方法长什么样

  1. 成本纪律：架构师输出判断、spec、路由、diff verdict、短报告；不写实现、测试体、boilerplate、配置文件。超过接口签名或几行示例的代码块就是还没委派的 spec，停下来委派。修 lane 的 bug 也一样，把修正后的 spec 发回去，不自己动手。
  2. 两条实现 lane：Luna 是默认 lane，适合 spec 完全决定结果的 routine、wiring、CRUD、机械编辑。Sol 用于判断决定结果的高复杂度任务：微妙并发、非平凡算法、安全敏感路径、硬调试、大范围重构，或 Luna 已经失败一次。Luna 失败一次给修正 spec，失败两次升级 Sol，重复是分类错误的证据。
  3. 六段 spec：Objective 一段话；Files 精确路径；Interfaces 签名、类型、API 形状；Constraints 项目约定和不能碰的东西；Verification 证明工作的命令；Reasoning 可选一行 REASONING: <effort>，只在覆盖默认时写。写不完 spec 说明决策还没做，是架构师的工作，不是把模糊交给便宜模型。
  4. effort 选择：Luna 默认 max，Sol 默认 high。纯机械编辑可以降到 low 或 medium，因为 max 只买墙钟；Sol 在任务已经失败过一次或爆炸半径大时升到 xhigh、max、ultra。Luna 没有 ultra，要求 ultra 的任务属于 Sol。
  5. 可见路由：每次委派在 Agent description 写 <Model> · <effort>: <task>，路由前公告一行，保留 lane 的 LANE: 行。UI 里能看到 GPT-6 在打字，而不是只看到 agent 名。
  6. 承诺边界与终局审查：架构选型、数据迁移、API 形状、重构策略前咨询 advisor；同一问题失败两次也咨询；每次交付终局必须一次。advisor 只读，verdict 300 词内，给 ship、fix-first 或 rethink。架构师不在审查前报告完成。
  7. 验证：报告是 claim，不是证据。读 diff，重跑验证命令。empty diff 加 clean exit 是 refusal，不是成功。lane 报 spec gap 就给修正 spec，不说「你自己判断」。

为什么审查要跨厂商

一次委派长什么样

spec 写六段，Agent description 写 GPT-6 Luna · max: add pagination to /orders，路由前公告 → luna-implementer · GPT-6 Luna · max (default)。lane 返回结构化报告：LANE、STATUS、OBJECTIVE、CHANGES、VERIFIED、CODEX SAID、GAPS。架构师读 diff、重跑验证命令，再把累加改动交给 advisor 做终局审查。

空 diff 为什么算拒绝

codex exec 会加载用户的 ~/.codex/AGENTS.md。如果那条规则要求先走 orchestration，lane 可能启动流程或拒绝，返回 exit 0、空 diff、礼貌拒绝。退出码看不出来，所以 lane 的 preamble 把这次运行限定为单个实现任务，并且空 diff 一律报 STATUS: refused，不算完成。

它解决什么

一个模型答难题时，最危险的不是答错，而是自信地答错。Fusion 的做法是把同一个问题同时发给多个模型，每个独立作答，谁也不看谁的；然后由 Opus 4.8 读所有答案，提取共识、矛盾、部分覆盖、独特洞见和盲点，再写一个建立在这个分析上的最终答案。机制是 independence, then synthesis：多样性不是分配 persona 造出来的，是独立运行自然长出来的。

方法长什么样

  1. 选 panel：detect_panel.sh 探测本机 CLI，推荐最丰富的 panel。Opus 永远可用；有 codex 加 GPT-5.5；有 agy 加 Gemini 3.1 Pro；两个都有就三家族全上。缺一个就降级，不失败。
  2. 盲跑：每个 panelist 拿到用户任务原文，加一句「用 web 和 bash 研究，返回完整自包含答案；你是几个独立专家之一，不会看到别人的工作」。不分配 lens，不预消化任务。所有 panelist 在同一轮发出，并发跑。
  3. judge 分类：先分 artifact 还是 research。代码、脚本、配置、schema 是 Track A；理解、建议、书面答案是 Track B。
  4. Track A：先运行每个候选，记录什么能跑、什么崩、什么过测试；用实际行为决定保留什么；选最强的基础，移植另一个里验证过能跑的片段；运行合并结果，修到通过；输出完整可运行产物，不是 diff。
  5. Track B：五段分析。Consensus 是独立一致，最高置信度；Contradictions 是直接冲突，说明谁持有什么、谁能用运行代码或一手来源裁决；Partial coverage 是只有部分 panelist 覆盖的子问题；Unique insights 是只有一个 panelist 提出的高价值点；Blind spots 是整个 panel 都漏掉的，包括没人质疑的共同假设。最终答案从分析长出来，不是某个 panelist 答案的轻改。
  6. provenance：每次运行保存 raw panelist 答案、分析、最终答案到 ~/.claude/fusion-runs/，带时间戳。交付时说明 panel slug、参与了哪些 panelist、有没有降级。

为什么同一模型跑两次也有用

两个独立的 Opus 4.8 冷跑，再由 Opus 4.8 judge，比单次 Opus 4.8 好很多。原因不是模型不同，而是独立运行会产生不同的推理路径、工具调用和来源选择。多样性是收成，不是制造。

代码任务为什么不能直接合并

两个实现粘在一起通常跑不起来。Track A 要求先分别运行，记录实际行为；用能跑的证据决定保留哪一段；选一个基础，移植另一个里验证过的片段；再运行合并结果并修到通过。面板的价值是两个独立尝试互相暴露 bug，合并结果应该比任何一个输入更正确。

judge 怎么处理降级

如果 Gemini 或 GPT panelist 非零退出，就移除它，记一行降级说明，继续用剩下的 panel。顺序是三家到两家，再到两个独立 Opus。降级的运行仍然完成，不因为一个 CLI 失败而中止。缺席的 panelist 按 absent 处理，不能当成沉默同意。

Fable 5.1 的 Claude Code 提示词有清晰的段落：System prompt、Harness、Memory、Environment、Context management、Delivering work、Writing for the user、Agents、MCP Server Instructions、Skills、Tools。工具部分每个工具一段，写清什么时候用、什么时候不用、参数和行为。看这个骨架，比看某一句具体措辞更有用。

怎么用它做自己的提示词

先选一个和自己产品最像的样本，按段对照；把平台实现和行为原则分开；只保留跨模型仍然成立的行为段，平台段用自己的实现替换。不要整段复制，也不要把别人的产品信息、工具接口、内部 UI 带进来。

它解决什么

一个 AI 生成的页面看起来不错，不等于它能跑、能在手机上用、没有 console error。claude-directory 把每个案例做成一个自包含项目，并且坚持三件套：prompt.md 记录它怎么被生成，完整代码让人能跑，demo.mp4 证明它真的动起来。仓库明说整个目录是 vibe coded，所以它同时给了 verifier 和 auditor：不是让你相信截图，而是让你能重跑检查。

方法长什么样

  1. 三件套：prompt.md 是原始提示词，保留生成意图；项目代码是完整可运行实现；demo.mp4 是实际运行的录屏；poster.jpg 是视频加载前的占位图。
  2. 自包含：每个项目一个文件夹，资源本地化，能克隆后离线跑；分类按产物类型，不按技术栈。
  3. 自动验证：verify.mjs 在 390、768、1280 三个宽度跑 headless Chromium，检查标题、canvas 尺寸、opacity、图片数量与破损、横向溢出、console error、4xx 或 5xx 响应；1280 宽度还点开菜单确认交互。
  4. 生成流程：.claude/agents/fable-experimenter.md 规定固定交付流程：worktree、查重、选分类、先提交 verbatim prompt.md、完整构建、CLI-only 验证、review、录 demo、生成 poster、README 登记、PR、合并、清理。
  5. 审计流程：.claude/agents/template-auditor.md 对 premium clone 做同源审计：读 REFERENCE: URL，抓原站和 clone 的截图、样式、响应式、交互、明暗主题，vision-judge diff，发现 gap 直接修，再录 demo、生成 poster、更新 README。
  6. 诚实标注：README 明说整个仓库是 vibe coded，上线前要 review 代码、检查依赖、验证可访问性和响应式、跑本地检查。

一个案例的交付长什么样

以 3d-games/lovable-webgl-hero 为例：prompt.md 是逐字保留的 uppercase 提示词，项目里有完整的 TanStack Start、React、Tailwind 代码和本地化的 public/vendor/ 资产，demo.mp4 是实际录屏，poster.jpg 是占位图，verify.mjs 在三个宽度跑 headless 检查。任何人克隆后可以重跑，不需要相信作者的截图。

verify.mjs 检查什么

它打开 390、768、1280 三个宽度，等 network idle 再等 4 秒，读取 h1、canvas 尺寸、hero opacity、图片数量和 broken images、横向溢出；监听 console error 和 4xx 或 5xx 响应；1280 宽度还点开 Solution 和 Resources 菜单，确认 Founders 和 Blog 可见。任何一项失败就非零退出。

为什么还要 auditor

生成 agent 会漏东西：少一个页面、少一个 section、响应式断点没做、hover 状态不对、明暗主题没切。template-auditor 把原站和 clone 都抓一遍，按页面、section、样式、响应式、交互、主题逐项 diff，发现 gap 直接修，再录 demo、生成 poster、更新 README。它不是只出报告，而是修到 same-to-same。
