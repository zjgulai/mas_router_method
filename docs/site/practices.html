实战用法

这里收的是别人已经在用的 agent 产品做法，按四层分开：行为、流程、编排、证据。每一层写清四件事：它解决什么问题、方法长什么样、怎么搬到 ANB 的阶段、以及可以直接复制的提示词。整页分四批上线，当前批次是行为层。

01 行为层：让模型守规矩

让模型在每一轮都守住边界：哪些规则常驻，哪些只在事件触发时读，哪些内容不该进入上下文。

Guardrails Kit：把常驻规则拆成事件触发的 playbook

常驻上下文是恒定和税；核心压到 45 行，长文档只在触发时读。

它解决什么

常驻 CLAUDE.md 越写越长，模型对每条规则的遵守度被稀释；真正需要的长文档又没人读。规则堆在同一个文件里，还会让每一轮上下文都为它们付一次 token。作者把「每次都必须生效的少数规则」和「特定时刻才需要的长文档」拆成两种东西，常驻部分因此可以压到很短。

方法长什么样

  1. 压核心：常驻部分只留约 45 行，硬上限 60 行。里面放 12 条铁律、一张事件路由表和 4 个硬停，其余内容全部移出去。
  2. 事件路由：路由条件写成模型当下能感知的事件，比如测试红了、准备说 done、第 3 次读同一个大文件。不写主题标签，因为主题标签要先判断「我属于哪一类」，这一步经常判断错。
  3. 按需 playbook：PLAN、CODE、TRAPS、DEBUG、VERIFY、EFFICIENCY、SESSION 八份文档放在旁边，只有对应事件触发时才读。平时它们不占上下文。
  4. 可粘贴证据：每条规则都产出一个能在 transcript 里搜到的标记，比如 TRIGGER:、CAUSE:、V3: PASS。验收时要求同一个标记和同一轮工具输出一起出现，规则有没有执行就不用靠感觉。
  5. 迁移：MIGRATE.md 逐行处置旧的 CLAUDE.md：先快照，再备份，遇到冲突显式暴露，最后让用户确认。旧规则不会在迁移时静默消失。

搬到 ANB 的哪个阶段

管理 · 设计 · 验收

  • manage：把规则分成常驻核心和事件触发 playbook。常驻部分只留每次都必须生效的条目，其余按触发事件归档。
  • design：先写 TASK 块，把目标、前提、基线、拆分，以及哪些要问人、哪些自己决定写清楚，再让模型动手。
  • verify：用 12 项回声协议逐条验收。每一条 claim 都必须引用同一轮真实工具输出，不能只复述结论。

可以直接用的提示词

把这段常驻规则压到 60 行以内：只保留 12 条铁律、事件路由表、4 个硬停；其余移到按需文档。每条路由写清触发事件、要读的文件、读完必须产出的标记。

作者报告的效果

作者用 155 条失败模式研究和 193 条对抗评审把规则硬化了一遍。规则以可 grep 的标记出现在 transcript 里，所以能审计哪些触发过、哪些被跳过。作者报告，常驻上下文从一份不断变长的文件，变成 45 行核心加按需文档。

Universal Fable 5：把系统提示词删到只剩行为

把平台细节删到只剩行为原则，按 core、balanced、complete 三档控制预算。

它解决什么

原版系统提示词里混着大量平台实现细节：XML 包装、MCP 与工具接口、产品行为、内部 UI、存储与 artifact、环境实现。这些内容在原来的平台上有效，换一个模型或客户端之后，既占 token 又不起作用。作者没有改写行为原则，而是先把只属于某个平台的部分一层层删掉，看剩下什么还成立。删除顺序也有讲究：先删最依赖平台的协议与界面，再删产品行为，最后检查剩下的原则能不能独立执行。

方法长什么样

  1. 分层删除：按来源一层一层去掉：XML 包装、MCP 与工具接口、产品行为、内部 UI、存储与 artifact、环境实现。每删完一层，检查剩下的行为原则还能不能独立读懂。
  2. 保留行为：留下的是跨模型仍然成立的部分：先理解意图、诚实处理不确定、清晰沟通、代码质量、权衡建议、完成前验证、客观纠错、少元评论。这些不依赖任何平台的接口。条目之间的顺序也有意义：先理解再验证，先诚实再完整。
  3. 三档预算：core 是最小行为集，balanced 是推荐档，complete 保留近乎全部厂商中立行为。用哪一档由 token 预算和任务复杂度决定，不默认用最长的那一档。三档共用同一组行为原则，差的是覆盖面和例子数量。
  4. 用法：直接粘贴到 system prompt、custom instructions、Gem 或 custom GPT。它是一份纯文本，不依赖 SDK，也不要求模型支持某个工具协议。

搬到 ANB 的哪个阶段

设计 · 管理 · 交付

  • design：把产品行为原则写成可迁移的段落，不绑定某一个模型的工具格式。
  • manage：按 token 预算选 core、balanced 或 complete，先问这一轮能花多少上下文。
  • ship：上线前删掉厂商特定内容，避免换模型时整段失效。

可以直接用的提示词

把这份系统提示词里只属于某个平台的部分删掉（XML、工具接口、产品 UI、存储、环境），只保留跨模型仍然成立的行为原则；按 core、balanced、complete 三档输出，并说明每档删了什么。

作者报告的效果

作者报告三档提示词在 Claude、ChatGPT、Gemini、DeepSeek、Qwen、Grok、GLM 等模型上保持兼容。删掉平台细节之后 prompt 更短，context 更省，行为原则仍然能读。换模型时不需要重新审一遍平台耦合，只要按新的预算挑一档。

来源：KinetiNode/claude-fable-5-system-prompt-clean

Fable 5 中文版：一套可以直接改的系统提示词骨架

不是英文原文的逐字翻译，而是一套能按段替换策略的中文骨架。

它解决什么

中文产品要一套能直接改的系统提示词骨架，而不是英文原文的逐字翻译。逐字翻译会把英文的句式和例子一起搬过来，读起来别扭，也不方便按本地政策替换。作者保留原文作参照，另做英文通用版和中文通用版，让策略段可以逐段改。分段的直接好处是替换时只动一段，其他段的语气和边界不受影响。

方法长什么样

  1. 原文保留：PROMPT_fable5.md 原样保留，作为对照和回溯的基准。后面两版都以它为参照，避免改着改着丢了原意。
  2. 厂商中立重写：PROMPT.md 去掉品牌名和平台细节，只留行为原则，作为英文通用版。它可以在不同模型上直接当 system prompt 用。
  3. 中文版：PROMPT.zh.md 按行为总览、搜索与工具、图片搜索、文件与代码输出分段。中文读者可以逐段读、逐段改，不用先在心里翻译一遍。分段名称直接对应读者要改的东西，不需要先理解英文的章节标题。
  4. 策略段可直接替换：拒绝处理、法律财务、语气格式、列表、健康、立场均衡、错误与批评、知识截止、版权、有害内容、图片搜索禁区，每一段都有明确边界。版权段还给了 15 词限制和每来源一次的规则。

搬到 ANB 的哪个阶段

设计 · 交付 · 管理

  • design：把拒绝清单、语气、引用规则写成可逐条对照的策略段，每一段只回答一类问题。
  • ship：上线前替换产品信息、拒绝清单、版权与图片规则，保留分段顺序，方便逐段回归。
  • manage：把策略段作为版本化基线，改一条记一条，避免多处副本各自漂移。

可以直接用的提示词

以这份中文系统提示词为骨架，保留策略分段结构，把产品信息、拒绝清单、引用规则、图片规则改成我们产品的版本；不要改变分段顺序。

作者报告的效果

作者提供原文、英文通用版、中文通用版三份。任何一份都可以直接作为聊天机器人或 agent 的 system prompt 起点。中文版按行为、搜索、图片、文件与代码输出分段，策略段可以整段替换而不动结构。原文保留还让改动有据可查，哪一段换过，可以和原文逐段对照。

来源：moely-ai/claude-fable-5-prompt

Value-for-Fable：用诊断结构而不是压缩去接近 Opus

压缩省下的是 token，削掉的是诊断质量；v2 删掉压缩强制，保留诊断结构。

它解决什么

用 Sonnet 想接近 Opus 的质量，常见做法是压缩输出省 token。压缩确实让回答变短，但它会连同诊断质量一起削掉：假设没有展开，测量被跳过，结论先于证据。作者的做法是保留诊断结构，只把重复和啰嗦去掉，让较便宜的模型仍然按同一条推理路径走。压缩规则通常写成字数或句数上限，模型为了达标会先删解释，而解释正是诊断过程本身。

方法长什么样

  1. 8 段输出结构：communication、style_reference、effort_and_reasoning、tool_discipline、verification、code_and_changes、writing_and_research、tone_and_conduct。每一段只负责一类行为，模型不用在一段里同时满足互相冲突的要求。
  2. 诊断结构：线索优先的假设、先做最便宜的测量、结论放在第一句、验证之后再宣布完成、置信度显式写出。这套顺序让回答可以被检查，而不是听起来完整。顺序本身就是检查表：先有假设，再选测量，最后才允许说完成。
  3. 2-pass 评审：高难度任务交给一个 Sonnet 评审 agent，只按四条标准评：需求遗漏、事实或数字错误、未解释的线索、超量。标准之外不评，避免评审自己发散。
  4. 漂移提醒：transcript 超过 400KB 且 VFF 仍然活跃时，才每轮注入一次提醒；没超过阈值就不注入，成本为零。
  5. v2 的关键修正：删掉压缩强制，保留诊断结构。作者实测 v1 到 v2 提升 10.9 分，说明省 token 和省质量不是同一件事。

搬到 ANB 的哪个阶段

验收 · 迭代 · 管理

  • verify：把诊断结构用作验收回答模板，先给结论，再给假设、测量和置信度。
  • iterate：把「压缩是质量债」做成一次消融实验，去掉压缩规则看分数，再决定要不要保留。
  • manage：长会话只在超过阈值时注入提醒，避免每一轮都付一次 token。

可以直接用的提示词

用 VFF v2 的诊断结构回答：第一句给结论；先找能解释所有线索的假设；处方前先给最便宜的测量；没验证前不说完成；不确定的地方标置信度。不要为了短而删掉解释。

作者报告的效果

作者报告 Sonnet 加 v2 与裸 Opus 在两次重评中的结果为 87.1 对 86.2、84.8 对 89.4，落在噪声内；输出成本约为 Opus 的 0.30 倍。省下来的主要是输出 token，诊断结构仍然保留。这个结果说明，接近更强模型的一条可行路径是改回答的结构，而不是改回答的长度。

来源：itsinseong/value-for-fable
