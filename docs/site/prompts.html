提示词库

可以直接复制的会话提示词。按阶段分类，每条都标明：什么时候用、以及为什么这么写。
更系统的 36 张战斗卡片见 实战作战手卡。

这些提示词的共同点：都在要求一个具体动作，而不是一个结论。 "帮我检查一下"会让它给你一段看起来认真的话；"造一个会让它失败的情况，跑一次，把结果原样贴给我"会让它给你证据。

把 ___ 换成你的内容。带 <b> 的地方是强调，复制时可以去掉。

跨阶段

会话开始

用 todo-ledger 读一下当前状态，确认分支和 worktree，告诉我 Now 和下一件事。
什么时候用每次新会话
为什么这样写凭记忆开工是万恶之源。

会话结束

用 handoff 写交接文档：目标、状态、决策、下一步、待答问题。指向已有产物，不要重复。
什么时候用换人或换 agent 时
为什么这样写交接文档写给下一个 agent 读，不是给你自己看的。

不知道下一步

用 anb 判断我现在卡在哪一步。只问必要的问题，然后只给我那一步要做的事，不要列全流程。
什么时候用任何时候
为什么这样写列表单会让你更迷茫。要一个动作。

诊断卡住

用 diagnosing-bugs 查这个 bug：先建一个能变红的反馈回路，再谈假设。
什么时候用有 bug 但不知道在哪
为什么这样写不能变红的复现不算复现。

需求

把一句话想法问成意图

用 interview-me 采访我：我想做 ___，但还没想清给谁用、成功长什么样。一次只问一个问题，每个问题带上你的推荐答案。
什么时候用只有一句模糊想法时
为什么这样写不要让它替你回答。它替你想的每一句都是猜测，你会在验收时无从判断。

攻击已有草稿

用 grilling 拷问这份方案，按 frontier 分轮提问，每个问题给出你的推荐答案。
什么时候用已经写了一份 PRD 或方案
为什么这样写前提是草稿是你写的。攻击一份它自己写的草稿，只会听到附和。

确定该走哪条车道

用 agent-delivery-router 判断这个需求走哪条车道：incident / exploration / capability / fast。
什么时候用每个任务开始
为什么这样写这一步只要 30 秒，但省掉它你会用错误的节奏做事。

写想法的第五句

帮我写"什么情况说明这个产品不该做"。要求：是一个可以被测量的事件，不是"如果没人用"。
什么时候用你能说清用途但说不清否定条件时
为什么这样写这是整个需求阶段里唯一能后期验证的一句。

判断该不该用 agent

我这个产品要做的是___。先别设计。只用一个问题判断：我能不能把决策树画出来？如果能写出步骤顺序和分支条件，就告诉我该做成固定流程；如果下一步取决于上一步返回什么、我列不出分支，才告诉我需要 agent。给出判断和理由。
什么时候用任何 agent 产品动手前
为什么这样写这是最贵的错误：本可以做成管线，却做成了 agent。管线的顺序确定，所以人力和钱都省一半以上。

设计

第一问：画出流程形状

帮我把这个产品的流程写成编号列表，然后标出哪些步骤每次一样、哪些步骤需要临场判断。最后告诉我判断点一共几处——零到一处说明这是管线，三处以上说明要么它真需要临场判断，要么我还没想清楚。
什么时候用进入设计阶段的第一件事
为什么这样写判断点的数量就是"该不该用 agent"的第二次投票。数量和需求阶段的判断对不上时，先别往下做。

第二问：写拒绝清单

我要一条一条写"它必须拒绝什么"。每条按这个格式：一个具体输入 → 它必须改做什么。先问我一个问题：这个产品最容易被误用成什么样？然后给我三条候选，我来判断。
什么时候用设计阶段的第二件事
为什么这样写写不出具体输入的，是价值观不是拒绝清单。"要诚实"没法测，"问能不能治痘痘 → 改成外观表述"能测。

第三问：动作权限按能不能撤销分

列出这个产品能做的每一个动作，按能不能撤销分三档：可撤销的放行；会被看见或花钱的，放行但要记账并设额度；不可撤销的先问人。不要按重要性排——重要性我会排错。
什么时候用产品能发送/删除/付款/发布时
为什么这样写中间那档最容易被跳过，而真正的损失都在那：不是答错一次，是在有人看之前错了五十次。额度要写数字。

第四问：交接契约写三行

对模型能调用的每一个工具，写三行：做什么、什么时候不该用它、失败时返回什么。第二行是重点——只写"它做什么"等于授权它在任何场景下用。
什么时候用模型会自己决定调哪个工具时
为什么这样写agent 产品最常见的失败不是工具坏了，是工具用在了不该用的地方，而日志里一切正常。

写一条 ADR

用 architecture-decision-records 为 ___ 的选择写一份 ADR，把放弃的选项和各自的代价写进去。
什么时候用做了难回退的选择
为什么这样写没有"放弃的选项"那一节的 ADR 是宣布，不是决策。

定死一个术语

用 domain-modeling 把"___"这个词定死，写进 GLOSSARY。给出它在这里的具体含义，以及一个反例（它不包含什么）。
什么时候用同一个词在两处意思不同时
为什么这样写反例比定义有用。说不清它不包含什么，等于没定义。

契约先行

用 api-and-interface-design 设计 ___ 的接口。先出契约和错误语义，再谈实现。
什么时候用要对接外部或跨模块时
为什么这样写错误语义是重点。只写成功路径的契约会在第一个失败时崩掉。

拆成可验收的票

用 to-tickets 把这份计划拆成纵向切片，每张票切穿所有层、能单独演示，标清阻塞关系。
什么时候用计划已批准
为什么这样写一张票如果跨了多个不相干的能力，继续拆。

设计阶段收尾：数问题

这是四问的答案。你现在只拿这份，不要问我任何问题，直接实现最窄的那条路。做完告诉我：过程中你不得不自己猜的有几处、分别是哪几处。
什么时候用四问写完之后
为什么这样写它猜的每一处都是设计的洞。两轮之内补完是正常的；超过三轮说明是缺了一整块，不是写得不细。

开发

做一条最窄的路

只做一条路径：一个真实输入进去，一个真实结果出来。不要界面，不要配置，不要"以后扩展"。做完让我自己跑一次。
什么时候用开始开发时
为什么这样写它一定想给你搭架子。拒绝。架子不产生任何你能判断的东西。

测试先行

用 tdd 在 ___ 这个 seam 上做：先写会失败的测试，再写最小实现。
什么时候用写新逻辑或修 bug
为什么这样写先跑一次确认它真的红。没红过的测试不是测试。

控制范围

ponytail full：用最小完整改动解决，不要加没人要的抽象。结束时告诉我你跳过了什么、风险在哪。
什么时候用任何编码任务
为什么这样写"跳过了什么"这一项最有价值，它让省略变成决定而不是遗漏。

分析这个模块

用 codebase-design 的词汇分析这个模块：接口是不是太浅，seam 该放哪。
什么时候用要改一块现有代码前
为什么这样写先理解形状，再动。

验收

故意弄坏一次

挑一条检查和一种会让它失败的情况。造出来，跑一次，把结果原样贴给我。必须告诉我它是红了还是绿了。
什么时候用任何检查通过之后
为什么这样写这是全套方法里最重要的一条。没红过的检查是装饰。

断网试

把 ___ 的密钥改成错的（或删掉），再跑一次。我要看到的是"无法判断"，不是"通过"。
什么时候用一切正常得可疑时
为什么这样写它的表现应该是明确报错 + 非零退出码，而不是静默降级。

念给我听

把这次检查结果逐条念：一共几条、跑了几条、过了几条、失败几条、跳过了几条、为什么。不许合并成一句。
什么时候用收到"全部通过"之后
为什么这样写第五节最容易省。省了就是被藏起来了。

把总数加一遍

把总数拆开加一遍：成功的 + 各种失败原因的 = 总数吗？给我算式。然后什么都不做刷新五次，看数字会不会自己动。
什么时候用看到任何仪表盘或计数时
为什么这样写两分钟，只需要计算器。这是唯一能查"记录有洞"的方法。

看三个真实输出

给我看三个真实输入的输出——不是你挑的样例，是我随手找的。然后告诉我：你会把这个交给客户吗？不会的话，哪一行最先出问题？
什么时候用机制全绿但你不确定结果好不好时
为什么这样写这一条抓的是"结果对不对"，前四条抓的是"机制可不可信"。两件事。

读信号：红还是尺子坏了

我认为这条测试红了。先别改代码。告诉我：你认为这是产品错了还是测试错了？理由是什么？
什么时候用检查红了的时候
为什么这样写实测中三条红的，三条全是测试自己写错。直接改代码迁就错的测试 = 测试变绿、产品变坏。

交付

换台设备

给我这个地址，我要在手机上打开。打的开的截图给我。
什么时候用认为做完了的时候
为什么这样写在你机器上能开不叫能开。密钥、数据、权限、地址，四件事在你这里全是配好的。

算一遍配额

这个功能每次使用会消耗多少次外部调用？我们有多少配额？第几个用户会撞墙？
什么时候用上线前
为什么这样写这个算术在写完代码时就能做，不用等到用户撞墙。

找人试

给我一个陌生人第一次使用的说明：他要做什么、可能卡在哪。不要写功能列表。
什么时候用准备给别人用时
为什么这样写写不出"可能卡在哪"，说明你不知道用户是谁。

列一遍密钥与配置

把这个产品跑起来需要的每一样东西列成清单：密钥、环境变量、数据库、外部服务。逐个回答：它从哪来？我是从环境变量读的，还是从某个文件读的？
什么时候用部署之前
为什么这样写四项在你机器上全是配好的：密钥、数据、权限、地址。它们不会在开发时报错，因为开发时本来就没用到未配置的形态。

选一个部署平台

帮我选一个部署平台。不要给我"最好的"，给我最省事的：从零到别人能打开，我需要做几步？哪一步最容易卡住？
什么时候用要给别人用之前
为什么这样写这个阶段的目标不是架构漂亮，是让别人打得开。选完就得做完，中途换平台的成本比选错高。

想好怎么退回去

这个东西如果上线后发现坏了，我怎么退回去？给我具体步骤和大概要多久。
什么时候用上线前
为什么这样写没有回滚方案的部署不是部署，是单向门。写不出步骤说明你还没想清楚它依赖什么。

上线后头 15 分钟看什么

上线之后我该盯着看哪三样东西？分别看到什么数字算正常、什么数字说明要退回去？
什么时候用按下部署之后
为什么这样写这十五分钟里你会紧张，紧张的时候需要的是三个具体数字，不是"再看看"。

运营

补三个数字

这个产品现在能回答：跑了多少次、花了多少、为什么失败？三个都要能打开就看到，不要跑命令。
什么时候用任何"感觉不太对"的时候
为什么这样写缺任何一个，后面所有判断都没有依据。

产品侧观测

除了技术日志，怎么知道"有没有人真的在用"？给出三个可以埋的点：谁、用了哪一步、在哪一步放弃。
什么时候用技术指标正常但不确定产品成不成立时
为什么这样写这是这套方法的边界。技术正常和没人用可以同时成立。

登记产物

这个东西（脚本/开关/面板）登记一下：owner 是谁、什么时候过期、满足什么条件就删。
什么时候用创建任何有持续成本的东西时
为什么这样写没有过期条件的产物会永久留在仓库里。

迭代

复盘

用 retro 复盘这一段：按严重度排序列出环境改进项，每项给 owner 和复查日期。
什么时候用一个周期结束
为什么这样写没有 owner 和日期的改进项等于没有。

该不该抽模板

这个东西要不要抽成模板？先回答两个问题：上个产品用过吗？它的形状会随产品变吗？
什么时候用想抽通用组件时
为什么这样写判据不是"用了几次"。形状会变的，抽出来就是负担。

分诊积压

用 triage 过一遍待处理 issue，先给我需要我注意的三类，其余先不动。
什么时候用issue 堆积时
为什么这样写全量分诊会让真正重要的三条被埋掉。

数据产品

判断这个指标该不该存在

这个指标是「___」。先别帮我算。只回答一个问题：如果这个数错了，哪个决策会怎么错？答不出来就告诉我它不该进产品。然后告诉我它由哪一层的记录加总而来，以及分子和分母是不是同一层——跨层相除得到的是效率，而效率要等传导关系确立之后才有意义。
什么时候用要往看板上加一个数字之前
为什么这样写这一问挡掉的是最贵的一种浪费：一个看起来比任何单个指标都更像洞察、实际没有任何含义的复合数。

把定义写到别人能算出来

把这个指标的可执行定义写出来，要求换一个人不问你能算出同一个数。格式：数据从哪张表哪个字段来、过滤条件是什么、按什么分组、权重是多少、时间按哪个时点归周。写完之后，你自己找一处最容易被误读的地方指出来。
什么时候用定义写完了但还像一段说明
为什么这样写「按情感为正的内容加权求和」不是定义，因为没有权重。定义的长度不是问题，可复现才是。

找出这个指标什么时候骗人

这个指标的已知偏差是什么？给我三档，每档说清一件事：具体哪个环节缺失或口径不一致、数字会往哪个方向偏、会让什么样的结论出错。不要给我「仅供参考」这种免责声明。
什么时候用写「已知偏差」那一栏时
为什么这样写「无偏差」等于「没想过」。说不清方向说明还不了解这个数。

写一条真能拦住它的禁令

这个指标的「什么时候不可用」，要写成一条禁令：当一个检查变红时，这个数不许出现在结论里。帮我把现在的说法改写成这种形状，并指出它对应哪个能触发的检查。改不出来就说明这句话是感慨。
什么时候用写「什么时候不可用」那一栏时
为什么这样写性质（「绝对数无意义」）和禁令（「不与上一期比较」）是两件事，后者才能挂到检查上。

改口径之前先问这三句

我要改这个指标的口径。先别动手。回答三件事：旧数据重算还是不重算（默认不重算，说清理由）、新旧版本要不要并行跑一个周期对比、界面上的版本号怎么显示。然后告诉我：如果不重算，跨期比较时怎么让人分清「口径变了」和「业务变了」。
什么时候用任何口径变更前
为什么这样写重算之后这两件事就永远分不开了，而这是数据产品里最贵的一种错误。

判什么：说出那个人做的判断

这个标签叫「___」。先别写分类规则。只回答：一个人看着一条内容时，脑子里做的那个判断是什么？然后给我三类例子，各一条：典型正例、典型反例、边界例。边界例是唯一有价值的那一条——写不出它，说明定义还没做完。
什么时候用定义一个新标签时
为什么这样写一个只会标 80% 的标签，剩下 20% 全靠猜。而那 20% 里集中了所有真正有趣的帖子。

什么情况算不适用

这个标签有一批内容它判不了。给我三个选项让我挑：加一个 n/a 值（分母变小但可见）、并进已有的一类（分母完整但那类被稀释）、排除整条记录（覆盖率下降要单独统计）。选完之后告诉我：说得出一个具体帖子落在它上面吗？说不出这个值不成立。
什么时候用写完定义之后
为什么这样写「不涉及这个维度」和「涉及但我判不了」必须是两个值，否则你答不出自己的打标覆盖率是多少。

把置信度钉死成可用的东西

这个标签的置信度，逐条钉死三件事：它是逐条的还是逐类的、它校准过没有（说 0.8 的那些真的对了 80% 吗）、按三档分别算准确率（<0.6 / 0.6–0.8 / >0.8）。高的那一档必须比低的那一档准。
什么时候用模型会输出 confidence 时
为什么这样写反过来的置信度是最隐蔽的一种错：所有「只用 >0.8」的规则都反了，而每条规则单独看都合理。

Kappa 低的时候先改定义还是先培训

两个人标同一批 200 条，Kappa 是 ___。先别安排培训。把那几条不一致的拿出来，逐条问：能说清「这条为什么该判 A」而不用「我觉得」吗？说不清的那几条，是定义有歧义，不是标注员不行。给我一份改定义的清单。
什么时候用Kappa < 0.6 时
为什么这样写培训只会让两个人一起错得更一致。

改标签之前先写映射表

我要把「___」这一类拆成两类。先别动代码。给我：显式映射表（旧类 → 新类，不许静默合并）、旧数据怎么查（按版本分组，还是要映射）、新旧并行跑多久。最后告诉我：如果不映射，跨期比较时人会看到什么假象。
什么时候用任何标签改版前
为什么这样写拆开之后悄悄按新体系合并，去年 52 周的数据会在某一点出现台阶，而那个台阶会和真实的市场变化混在一起。

这句话能不能被推翻

这是我的结论：「___」。先别帮我润色。只回答一个问题：构造一个数据，让这句话变错。构造得出来，告诉我那是哪个已注册的证伪条件；构造不出来，说明这句话里没有数字或者没有对象，回去改它。
什么时候用任何结论写完之后
为什么这样写一个不能说错的句子，也不能被检查。这是结论层和「一个 dashboard」之间唯一的分界线。

把点估计换成区间

这条结论现在只有点估计「___」。给我一个 95% 区间，并回答：它跨过 0 吗。跨过的话，这条结论要标成「无结论」而不是「效应弱」——告诉我为什么这两种说法会导致不同的动作。
什么时候用要发布一个数字之前
为什么这样写「弱效应」会被引用进一次预算会；「无结论」不会。而它们来自同一个区间。

决策含义要写成一个动词

这条结论的决策含义我写的是「___」。帮我改成一个动词 + 一个对象 + 一个方向 + 一个时间。改完之后告诉我：星期一的哪件具体事会因此不同？说不出来，这条结论不该写。
什么时候用写决策含义那一栏时
为什么这样写这是六项里最常被写空的，也是唯一能反过来判断这条结论该不该存在的一项。

依据要能走到原始载荷

这条结论的依据是「___」。帮我逐跳列出：结论 → 指标（带版本） → 标注（带 taxonomy_version） → 记录 → 原始载荷。哪一跳断了，就停在那里告诉我缺什么。
什么时候用写依据那一栏时
为什么这样写做不到这点，血缘就只是宣称。「基于大量真实数据」三个问题一个都答不上：多少条、哪个源、哪个版本。

被推翻的时候新增而不是改写

这条结论被证伪了。别改原件。按三句话给我：旧结论主张什么、什么条件触发了、新结论是什么。然后告诉我这张旧卡该标成什么状态。
什么时候用证伪检查报红之后
为什么这样写删掉旧结论会失去「我们曾经相信过什么、为什么信错了」的记录，而那份记录是唯一能让下次判断更快的东西。

实战战斗 Prompt 专区（36 条原则精选）

精选自 6 大实战作战主题。详见 完整作战手卡与验收判定 →

01 Agent 工程：从会做，到可持续运行

01-01 先配问题放回系统

请先不要改代码：先确认真正目标、扫描系统结构、列出边界与依赖，再给出最小可行执行计划。
解决痛点Agent 直接动手，往往连目标、边界和依赖都没有对齐。
验收判定计划必须指标输入、输出、验收和阻塞回退点。

01-02 模型只是乘数，Harness 才是系统

如果模型明年强 10 倍，这个功能还应该留在 Harness 里吗？请按必要性、可替代性、验证成本回答。
解决痛点模型会更换；真正累积的是工具、技能、上下文、循环和审批。
验收判定每个长期机制都要能说清保留理由和删除条件。

01-03 长任务要可观察、可接管

把这项长任务拆成可并行的 tickets；为每个 ticket 写输入、输出、停止条件、交接文件和人工审批点。
解决痛点多个 Agent 并行跑，最怕失忆、卡住、上下文膨胀和没人知道当前状态。
验收判定任何分支都能从最近一次产物恢复，不依赖完整聊天记录。

01-04 先路由，再执行

Route first, execute second: 先写任务类型、授权 scope、可用工具和退出条件，再开始 ACT。
解决痛点工具很多，Agent 选错方法时会把时间浪费在无效探索上。
验收判定没有授权、scope 或工具前置条件时，不进入执行阶段。

01-05 让 Agent 先看地图再改代码

请先画出本次改动涉及的模块、调用关系和数据流；标出不能碰的边界，再开始实现。
解决痛点一口气动十几个文件，依赖和影响面不可见，合并后才发现牵连别处。
验收判定变更说明必须能回答：改了哪里、为什么、可能影响谁、如何回滚。

01-06 让环境和 Agent 一起变强

把这项任务改造成可评测环境：定义状态、动作、反馈、成功判定和失败样本。
解决痛点静态环境只给结果，不给足够的反馈；Agent 很难知道什么算好。
验收判定下次执行应能复用上一轮的证据，而不是重新猜。

02 Skills 与上下文：少而准，按需加载

02-01 新对话失忆 / 先做记忆分层

请把本次对话压缩成交接文档：目标、已确认决策、当前状态、未解决问题、下一步验证。
解决痛点需求、决策、坑和偏好散在聊天里，换会话就要重新交代。
验收判定交接文档脱离原对话仍能让另一个 Agent 继续。

02-02 AGENTS.md 太重 / 规则要分层

审查当前 AGENTS.md、Skills 和任务提示：哪些规则应保留在根层，哪些应下沉或删除？给出迁移表。
解决痛点把代码规范、API 格式、业务逻辑和所有例子全塞根目录，Agent 反而变慢。
验收判定每条规则都要有触发场景、适用范围、验证方式和删除条件。

02-03 装了 Skill / 不等于真的会用

请为这个 Skill 写一个最小评测集：触发样例、反例、完成标准、错误边界和回归任务。
解决痛点Skill 数量增长很快，但模型、Harness 和任务上下文改变使用效果。
验收判定没有评测证据时，只能说“已安装”，不能说“已掌握”。

02-04 创建 Skill / 先抽取 定方法

从这组真实任务中抽取 Skill：先列 定模式，再删除一次性细节，最后给出触发器和回归样例。
解决痛点把一次对话复制成 Skill，容易把偶然措辞和无效步骤固化。
验收判定Skill 必须能被另一个人读懂、运行和验证。

02-05 上下文窗口 / 先做价值排序

请将当前上下文分成：必须保留、可按需加载、可丢弃三层，并说明每项的判断理由。
解决痛点低频 Skill、旧决定和中间噪声驻上下文中，挤掉真正有用的信息。
验收判定压缩后不能丢失用户目标、关键报错、约束和可复现路径。

02-06 汇报要能让非工程师判断完成度

先写结论；把工作状态和验证状态分开；每个事实给定定位证据；不确定写“未确认”；需要我决定时列编号选项。
解决痛点一堆 commit hash 和工程术语，无法回答到底完成成了什么。
验收判定读者不打开代码，也能判断范围、原因、证据、验证和待确认项。

03 Eval First：从会生成，到值得交付

03-01 AI 项目 / 先建评测再建功能

Eval First: 先给出评测集、成功标准、失败类型和基线，再设计实现方案。
解决痛点输出不可预测，单元测试通过也不能说明用户结果有效。
验收判定没有基线和失败样例，不宣称“效果更好”。

03-02 单测通过 / 仍要跑真实业务路径

请从真实入口跑完整业务路径，并同时给出用户可见结果、工具证据和业务契约对照。
解决痛点局部函数正确，不代表权限、状态、并发、重试和回滚真的成立。
验收判定从入口跑到底端，并留下可复核证据。

03-03 机制很多 / 用消融实验找贡献

给这三个优化设计消融实验，判断真正的收益来自哪里。
解决痛点缓存、队列、锁、Agent、插件一起上线，没人知道真正收益来自哪里。
验收判定每个机制都有对照结果和业务收益。

03-04 Bug 反复改 / 设调试止损线

先复现问题；每轮只改一处；用同一验收方法验证；连续两轮无进展就停止修改并重新诊断。
解决痛点改一次、又引出新问题，第三轮已经忘了最初错误，Token 和时间一起烧掉。
验收判定没有新的证据时，不继续堆 patch。

03-05 Review / 先看业务风险再看代码风格

按业务路径做 Review: 先列高风险假设，再逐项给出证据、影响、修复建议和未确认项。
解决痛点Agent 生成速度上去了，人工判断却仍按原节奏，审查变成瓶颈。
验收判定每条评论都必须能改变风险、验收或维护成本。

03-06 工具返回合理 / 不等于业务正确

先写业务契约，再让工具证明结果；不要让工具替你定义正确答案。
解决痛点DB、日志和 Trace 能说明发生了什么，却不能替业务定义什么是对。
验收判定结论必须同时有业务依据和可定位的运行证据。

04 Creative Workflow：让 Prompt 可读、可控、可复用

04-01 Prompt 不用专业 / 要写到自己读得懂

【主体】x【风格】x【构图】x【媒介】；请把我的想法改写成我能读懂、能逐项检查的 Prompt。
解决痛点复杂术语堆在一起，自己都无法检查，模型也难以稳定复现。
验收判定每个形容词都要对应可观察的画面证据。

04-02 视频从想法到成片 / 先管前 2 秒和镜头

请先给出前 2 秒钩子、镜头时间线、每镜头的动作与转场，再生成完整视频 Prompt。
解决痛点旁白塞太满、方向没定、细节越改越重，成片反而失去重点。
验收判定删掉不能服务主题、节奏或转化的镜头。

04-03 抄参考 / 先提取设计系统

请从这个参考网站提取一份可执行设计系统：色板、字体层级、间距、组件、状态、无障碍和验收清单。
解决痛点只看截图容易抄到表面，配色、字体、间距和组件关系仍靠猜。
验收判定输出必须能直接指导实现和 Review，而不是只说“高级、简洁”。

04-04 风格库 / 用编号减少描述成本

浏览风格画廊，选出最适合主题的 1 个风格编号，并说明它与主体、构图和媒介如何组合。
解决痛点审美词汇不稳定，团队和模型对“手绘、电影感、高级”理解不一致。
验收判定风格选择必须能解释为什么适合当前任务。

04-05 复刻 / 先拆结构再换内容

请把这个参考拆成结构变量与内容变量；先保持结构不变，只替换主体，并列出每轮对照检查项。
解决痛点看到结果就照抄，往往只能复制表面，无法迁移到新主题。
验收判定复刻结果要能说明差异来自哪个变量。

04-06 UI 不是堆功能 / 是任务与层级

请按用户任务重构这个页面：先列层级、关键状态和操作路径，再决定组件、动效和视觉风格。
解决痛点页面看起来完整，却没有清晰任务路径，AI 带来无意义装饰和默认组件。
验收判定每个视觉元素都要服务理解、操作或反馈。

05 Product & Growth：从有人感兴趣，到有人付费

05-01 早期验证 / 不要把兴趣当需求

请把这个想法拆成信号阶梯：每一级需要用户付出什么、如何观察、什么结果才允许进入下一步？
解决痛点点赞、浏览和口头喜欢很容易，真实付出才能接近购买意愿。
验收判定没有最高成本信号前，不要把曝光写成 PMF。

05-02 竞品调研 / 先找切入口再做功能

请做竞品调研：用户任务 → 搜索词 → 竞品替代 → 未满足需求 → 可测试切入口，并标注证据源。
解决痛点资料很多，但没有形成目标用户、替代方案和可交付缺口。
验收判定每个结论都要能回到用户行为或公开证据。

05-03 内容增长 / 把一次实践沉淀成方法

把这次实践整理成可复用内容资产：问题、受众、过程、结果、证据、模板、下一次实验。
解决痛点内容靠灵感重复生产，经验无法复用，热点也难以转变成长期资产。
验收判定内容必须留下下次可以直接执行的动作。

05-04 自动化 / 先拆链路再接工具

请把这条业务链路画成状态机：输入 → 抽取 → 分类 → 生成 → 审批 → 发布 → 复盘，并标注人工门。
解决痛点把多个平台和 Agent 串起来很容易，但错误会被自动化放大。
验收判定没有权限、幂等和回滚设计时，不做全自动发布。

05-05 SEO / 从真实站点证据开始

请对这个站点做真实审计：抓取 → 规则检查 → 证据 → 影响 → 修复 → 复测；不要只给通用建议。
解决痛点套模板写 SEO 报告，容易忽略 robots、跳转、死链和 JS 内容。
验收判定报告必须能定位到页面和规则，不能只写“优化内容”。

05-06 电商 / 让 AI 负责流程，人负责契约

请把这条电商流程拆成可独立验收的 Skills，并为每一步写输入、输出和人工审批点。
解决痛点从选品到上架、文案、出图和投放都自动化，最怕品牌和业务标准失控。
验收判定自动化不能绕过合规、价格、库存和品牌边界。

06 Data & Research：把资料变成可行动知识

06-01 资料很多 / 先找来源和证据边界

请输出：原文事实 / 作者观点 / 你的推断 / 未确认缺口；每条事实给出定位来源。
解决痛点AI 总结流畅，但读者分不清哪句来自原文，哪句是模型补全。
验收判定没有原文证据时，不把推断写成事实。

06-02 RAG / 先问检索结构是否适合任务

请先分析文档结构和问题类型，再比较向量、关键词、树状索引等检索方案，给出基线与评测集。
解决痛点切块、向量和相似度搜索并非所有文档任务的最优解。
验收判定不要因为“大家常用 RAG”跳过任务结构分析。

06-03 数据工程 / 用状态机和 Provenance 管住链路

请把这个数据流程建模为：状态机 + DAG + I/O + 执行器 + Provenance，并列出每个状态的进入与退出条件。
解决痛点数据产生、摄取、存储、处理、发布混在一起，失败后无法定位。
验收判定任何结果都能回到源头、变换和版本。

06-04 陌生领域 / 先建地图再深入

请把这些资料整理成知识地图：实体、概念、关系、来源、证据等级和待验证问题。
解决痛点资料散落，概念、人物、项目和来源互相混淆，学习路径不可见。
验收判定地图要能指导下一次搜索，而不是只做漂亮目录。

06-05 学习材料 / 让 AI 解释但不替你相信

请把这份材料变成交互式学习路径：章节 → 核心概念 → 原文证据 → 例子 → 自测题 → 待复习。
解决痛点一本书、PDF 或课程很难系统读完，摘要又可能混入幻觉。
验收判定解释必须能回到材料，不能只凭常识补全。

06-06 研究闭环 / 从信息摄取到可执行决策

请把这批资料按相关性、具体程度、可信度和时效评分，给出今日优先阅读与下一步实验。
解决痛点收藏、阅读和转发很多，但没有排序、筛选、实验和反馈。
验收判定每条研究输出至少导向一个可执行动作或明确的“不做”。
