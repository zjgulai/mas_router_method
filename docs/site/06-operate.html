06运营

看得出它有没有被用、有没有变好、钱花在哪、出事时能不能查。

半个覆盖　ANB 阶段 5 只覆盖了技术侧的观测（跑几次、花多少、为什么失败）。产品侧——有没有人用、用了之后有没有变好——这套方法答不了。

为什么这一步重要：没有这一步，你无法回答"这个产品到底成不成立"。而技术上的"全部正常"和产品上的"没人用"可以同时成立。

什么情况走哪条路

按代价排序，不按发生概率。先做便宜且能推翻结论的。点击跳到对应处理。

如果去为什么
你不知道它跑了多少次、失败多少次b-blind先补三个数字，再谈别的。没有观测就加功能，等于在黑暗里挪。
有记录，但总数和分项对不上b-reconcile记录有洞。每一条其它结论都建立在这上面。
数字正常，但不知道有没有人真的在用b-nouser这是产品侧观测，需要埋点而不是日志。
能回答"谁在用、用了多少次、哪里失败"b-next进入迭代。

不知道它跑了多少次

你缺三个数字：跑了多少次、失败多少次、为什么失败。

先有这三个，再谈别的。没有观测就加功能，等于在黑暗里往前挪——你会一直走到撞墙才知道方向错了。

总数和分项对不上

这说明记录有洞：有请求开了头没结尾，或者被算了两次。

一个更隐蔽的版本：你去看仪表盘的那次请求，自己也被计入了仪表盘。于是每看一次，数字就涨一次，而且只涨不跌。

动作：把总数拆开加一遍。然后什么都不做，刷新五次，看数字会不会自己动。

不知道有没有人真的在用

技术观测答不了这个。日志能告诉你"程序跑了"，不能告诉你"有人需要它"。

这是这套方法的边界：它能让你不骗自己，不能让你不骗市场。要做产品侧观测，得埋点——谁在用、用了几次、在哪一步放弃。

这一步过了

进入下一步。如果这是一个大产品，建议在这里停下来，把这一步的产出写成文件——因为三个月后你会需要它。

谁来验，怎么验

每一行都是一个你能亲手做的动作。做不了就记成未通过，写明缺什么，不要用近似动作代替。

动作通过标准
做三次，历史里有三条做 N 次数 N 条
故意弄坏一次，能在记录里找到它和原因找不到就是记录有洞
知道花了多少这个产品花的是 API 配额，不是 token——两个都要能看清

这一步用到哪些 skill

  • anb-observable — 三个数字：跑几次、花多少、为什么失败。
  • observability-and-instrumentation — 从 on-call 问题倒推日志、指标、追踪、告警。
  • instrument-product-analytics — 事件表、漏斗、留存、身份策略。
  • artifact-registry — 每个有持续成本的东西登记 owner 与过期。
  • tech-debt — 打分排序的债务登记表。
  • deprecation-and-migration — 弃用策略与 expand/contract 迁移。
  • repo-gc — E1–E4 分级的删除计划。
  • ponytail-audit — 全仓审计：什么可以删。
