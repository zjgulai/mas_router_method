04验收

定下「什么算好」，并且让这个标准能自动跑，而且必须亲眼看到它失败过一次。这一阶段的护栏检查来自设计记录：先跑 node scripts/design.mjs refusals，把每一行变成一条检查。

方法论已覆盖　这一步由 anb-judgeable 覆盖，它是整条链路里唯一的硬门。这里不过，不许往下走。

为什么这一步重要：没有这一步，后面每一次改动都是无法测量的。产品会安静地变差，而所有人都以为在变好。

什么情况走哪条路

按代价排序，不按发生概率。先做便宜且能推翻结论的。点击跳到对应处理。

如果去为什么
还没有任何检查一条检查都没有先写五到十条判断标准，再改产品。顺序反了，检查只会描述现状。
有检查，但从来没红过检查从没红过一条从没失败过的检查不是检查。走「故意弄坏」。
检查红了检查红了先问：是产品错了还是尺子错？实测中三条红的，三条全是测试自己写错。
检查全绿，但你不确定结果好不好全绿但结果不好这是另一类问题：机制可信 ≠ 产出可用。
检查全绿，且空跑五次数字不动这一步过了进入交付。

一条检查都没有

现在改产品是没有方向的：你不知道自己在改好还是改坏。

先做的事：写下五到十条"什么样算好、什么样算坏"。每一条都要能变成一次自动检查，要么是能数的，要么是需要读一遍判断的。

关键顺序：先写检查，再改产品。反过来的话，检查会变成"描述产品现在做什么"，那是一种永远不会失败的检查。

检查从没红过

一条从没失败过的检查，只有三种可能：没在跑、没接进判定、写得太松。三种都长得像成功。

动作：故意造一个违反它的结果，看它会不会红。如果还是绿的，这条检查是装饰。

检查红了

先别让它修。先问一句：你认为这是产品错了，还是测试错了？理由是什么？

实测中我遇到三条红的，三条全是测试自己写错：我把字符数算错、把排序预期写反。如果直接改代码去迁就错的测试，测试会变绿，而产品会变坏。

全绿但结果不好

这是两件不同的事：机制可不可信和产出可不可用。一个机制完全可信的工具可以稳定地输出垃圾。

动作：先问"有没有一条检查是关于结果对不对的，还是全是关于程序有没有崩的"。然后让它给你看三个真实输入的输出。

这一步过了

但注意：过了这一步不代表产品好用，只代表你能判断它好不好。

谁来验，怎么验

每一行都是一个你能亲手做的动作。做不了就记成未通过，写明缺什么，不要用近似动作代替。

动作通过标准
你亲眼看到过一条检查变红，并能说出是哪条抓到的不是"应该有"，是"我看到了"
被跳过的检查数为零，或者整体结论是"不完整""跳过"绝不能算通过
成功 + 各种失败原因 = 总数拆开加一遍，两分钟

真实案例

从 2,794 个真实工程会话里挑出来的。案例已去掉业务细节，只用来说明这些误判真的会发生。

对应误判真实案例说明
一条检查都没有自动检查只验文件格式对不对，没测功能、没比页面长得对不对、也没查无障碍。有自动检查 ≠ 有能判断好坏的检查。
检查从没红过新加一条检查后，先拿现有版本跑一遍，确认它真的会报错；否则它可能只是在空转。主动证明检查会红。
检查红了测试报错是预期的：要做的功能还不存在。先确认"红得对"，再动手做。红可能是尺子错，不一定是产品错。
全绿但结果不好在自己电脑上从头到尾跑通，不等于线上每个页面都换了新版本；旧页面照样能打开，看起来像成功。"能打开"是机制可信，"新版本真的上线了"才是产出可用。
检查太松（最常见成因）换系统时，检查只确认"编号存在"，不确认"这个项目是不是已经停用"；上线前只确认"文件夹在"，不确认"谁有权访问"。只检查 X 存在，不检查 X 对不对。

实战避坑守则 (Battle Tips)

归属于验收阶段的实战守则摘要。完整复制口令见 作战手卡全表。

守则与手卡入口典型痛点验收判定
02-03 装了 Skill / 不等于真的会用Skill 数量增长很快，但模型、Harness 和任务上下文改变使用效果。没有评测证据时，只能说“已安装”，不能说“已掌握”。
03-01 AI 项目 / 先建评测再建功能输出不可预测，单元测试通过也不能说明用户结果有效。没有基线和失败样例，不宣称“效果更好”。
03-02 单测通过 / 仍要跑真实业务路径局部函数正确，不代表权限、状态、并发、重试和回滚真的成立。从入口跑到底端，并留下可复核证据。
03-03 机制很多 / 用消融实验找贡献缓存、队列、锁、Agent、插件一起上线，没人知道真正收益来自哪里。每个机制都有对照结果和业务收益。
03-05 Review / 先看业务风险再看代码风格Agent 生成速度上去了，人工判断却仍按原节奏，审查变成瓶颈。每条评论都必须能改变风险、验收或维护成本。
03-06 工具返回合理 / 不等于业务正确DB、日志和 Trace 能说明发生了什么，却不能替业务定义什么是对。结论必须同时有业务依据和可定位的运行证据。
06-05 学习材料 / 让 AI 解释但不替你相信一本书、PDF 或课程很难系统读完，摘要又可能混入幻觉。解释必须能回到材料，不能只凭常识补全。

这一步的实战用法

来自实战项目的做法，按它和本阶段的关系收录。完整案例、方法和提示词见 实战用法。

项目一句话来源
Guardrails Kit：把常驻规则拆成事件触发的 playbook常驻上下文是恒定和税；核心压到 45 行，长文档只在触发时读。TheColliny/FableClaudeMDForOpus
Value-for-Fable：用诊断结构而不是压缩去接近 Opus压缩省下的是 token，削掉的是诊断质量；v2 删掉压缩强制，保留诊断结构。itsinseong/value-for-fable
The Fable Method：把判断问题转成证据问题的 7 步循环分类、定义完成、取证、决策、最小改动、观察验证、结论先行；每一步都有硬边界。Sahir619/fable-method
Fable Mode：把编排做成结构，而不是提示词里的请求stage map、命名委派、可失败的检查、冷验证；orchestrator 没有写权限，worker 才有。mrtooher/fable-mode
fablize：只搬运被实验证明可搬运的程序不提升模型天花板，只让模型走到自己的天花板；只发布验证过效果的程序。fivetaku/fablize
Fable Advisor：架构师不下场打字，按能力分 lane 路由会话当架构师，GPT-6 lane 打字，Fable 在承诺边界和终局做审查。DannyMac180/fable-advisor
Fusion-Fable：独立 panel 加固定 judge，把多个模型合成一个答案同一 prompt 盲跑多个模型，Opus 固定做 judge，输出共识、矛盾、遗漏、盲点。duolahypercho/fusion-fable
Fable Foreman：路由卡是单一事实源，贵的模型要二次批准先证明能用，再按成本/能力选座；lead 亲自验收，贵模型要用户两次确认。olsenbrands/fable-foreman
System Prompts Leaks：把系统提示词当成可对照的工程材料18 个厂商、约 1900 份提示词，按产品和版本归档，能看到行为契约的结构和演变。asgeirtj/system_prompts_leaks
claude-directory：用 prompt、成品和录屏证明一个案例真的能跑541 个项目，每个都带 prompt.md、可运行代码、demo.mp4 和 poster.jpg。pulkitxm/claude-directory

这一步用到哪些 skill

  • anb-judgeable：定什么算好，且检查必须能失败。唯一硬门。
  • anb-check-break：故意弄坏，看检查会不会红。
  • anb-check-offline：断网/密钥错，必须是"无法判断"而非"通过"。
  • anb-check-readback：逐条念结果，含跳过了几条。
  • anb-check-reconcile：把总数拆开加一遍。
  • anb-check-output：看三个真实输出，判断结果对不对。
  • verification-before-completion：证据先于声明：跑命令、读输出、再下结论。
  • llm-evaluation：LLM 评测集设计、judge 偏差控制、回归门。
  • test-suite-health：测试越写越多越慢越脆时体检。
  • code-review：Standards 与 Spec 两条轴分开报告。
  • security-review：高置信度漏洞，含 prompt injection 与租户泄漏。
  • diagnosing-bugs：先建会变红的回路，再谈假设。
  • interrogate：多模型各派一个对抗者；每条 finding 必须附可重跑的命令与真实输出，主 agent 重跑，跑不出来就丢。
  • principle-prove-it-works：声明完成前，对着真实产物验证，而不是"能编译"。
  • principle-explain-the-number：每个数字都要能解释：什么限制了它、噪声底多大、还可能测到了什么。
  • benchmark-checklist：报告任何测量数字前先过这一遍：限制因素、重复次数、是否真干了活。
  • blast-radius：上线前找"diff 之外会被这次改动弄坏的东西"，并真跑代码证明唯一侥幸成立的前提。
  • thermos：并行跑上面两个审查，再合并结论。
