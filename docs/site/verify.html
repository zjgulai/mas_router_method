总览 / 验收

04验收

定下「什么算好」，并且让这个标准能自动跑。而且——必须亲眼看到它失败过一次。这一阶段的护栏检查来自设计记录：先跑 node scripts/design.mjs refusals，把每一行变成一条检查。

方法论已覆盖　这一步由 anb-judgeable 覆盖，它是整条链路里唯一的硬门。这里不过，不许往下走。

为什么这一步重要：没有这一步，后面每一次改动都是无法测量的。产品会安静地变差，而所有人都以为在变好。

实战避坑与作战原则 (Battle Tips)

来自 6 大作战面板中归属于验收阶段的实战守则。详见 作战手卡全表 →

02-03 装了 Skill / 不等于真的会用

痛点：Skill 数量增长很快，但模型、Harness 和任务上下文改变使用效果。

  • 先定义 Skill 的触发条件和完成标准，再讨论安装数量。
  • 用真实任务评测：是否被正确选择、是否完整执行、是否产生副作用。
  • 把优秀做法编译进可执行 Harness，减少靠文字提醒的遗漏。
请为这个 Skill 写一个最小评测集：触发样例、反例、完成标准、错误边界和回归任务。
验收判定：没有评测证据时，只能说“已安装”，不能说“已掌握”。

03-01 AI 项目 / 先建评测再建功能

痛点：输出不可预测，单元测试通过也不能说明用户结果有效。

  • 先定义成功/失败、边界和质量等级。
  • 用代表性样例集反复回归，记录输入、输出、上下文和工具轨迹。
  • 把评测结果作为产品迭代的眼睛，而不是上线后的补丁。
Eval First: 先给出评测集、成功标准、失败类型和基线，再设计实现方案。
验收判定：没有基线和失败样例，不宣称“效果更好”。

03-02 单测通过 / 仍要跑真实业务路径

痛点：局部函数正确，不代表权限、状态、并发、重试和回滚真的成立。

  • 一键启动环境、准备数据、明确账号权限，并支持清理重置。
  • 从浏览器、API 或 CLI 操作真实入口。
  • 用 DB、日志、Trace 和业务断言闭合证据链。
请从真实入口跑完整业务路径，并同时给出用户可见结果、工具证据和业务契约对照。
验收判定：从入口跑到底端，并留下可复核证据。

03-03 机制很多 / 用消融实验找贡献

痛点：缓存、队列、锁、Agent、插件一起上线，没人知道真正收益来自哪里。

  • 先建基线，再一次只移除或加入一个机制。
  • 比较质量、延迟、成本、失败率和复杂度变化。
  • 没有贡献或无法验证的机制，删除而不是继续解释。
给这三个优化设计消融实验，判断真正的收益来自哪里。
验收判定：每个机制都有对照结果和业务收益。

03-05 Review / 先看业务风险再看代码风格

痛点：Agent 生成速度上去了，人工判断却仍按原节奏，审查变成瓶颈。

  • 先验验收标准，再测试结果；治业务路径查权限、状态、并发和回滚。
  • 小 MR，复核需求拆成可独立验收的 Issue。
  • Review 关注有效问题遗漏和用户风险，不追求评论数量。
按业务路径做 Review: 先列高风险假设，再逐项给出证据、影响、修复建议和未确认项。
验收判定：每条评论都必须能改变风险、验收或维护成本。

03-06 工具返回合理 / 不等于业务正确

痛点：DB、日志和 Trace 能说明发生了什么，却不能替业务定义什么是对。

  • 先写业务契约和预期结果，再让工具提供证据。
  • 把事实、推断、未确认分开。
  • 对 Agent 产品，还要评估答案质量、定性和拒答边界。
先写业务契约，再让工具证明结果；不要让工具替你定义正确答案。
验收判定：结论必须同时有业务依据和可定位的运行证据。

06-05 学习材料 / 让 AI 解释但不替你相信

痛点：一本书、PDF 或课程很难系统读完，摘要又可能混入幻觉。

  • 先按章节、概念、例子和练习建立阅读路线。
  • 每个答案同时给出原文摘录、解释、反例和自测题。
  • 对关键结论回到原质核对，记录未读与未验证范围。
请把这份材料变成交互式学习路径：章节 → 核心概念 → 原文证据 → 例子 → 自测题 → 待复习。
验收判定：解释必须能回到材料，不能只凭常识补全。

什么情况走哪条路

按代价排序，不按发生概率。先做便宜且能推翻结论的。点击跳到对应处理。

如果去为什么
还没有任何检查一条检查都没有先写五到十条判断标准，再改产品。顺序反了，检查只会描述现状。
有检查，但从来没红过检查从没红过一条从没失败过的检查不是检查。走「故意弄坏」。
检查红了检查红了先问：是产品错了还是尺子错？实测中三条红的，三条全是测试自己写错。
检查全绿，但你不确定结果好不好全绿但结果不好这是另一类问题：机制可信 ≠ 产出可用。
检查全绿，且空跑五次数字不动这一步过了进入交付。

一条检查都没有

现在改产品是没有方向的：你不知道自己在改好还是改坏。

先做的事：写下五到十条"什么样算好、什么样算坏"。每一条都要能变成一次自动检查——要么是能数的，要么是需要读一遍判断的。

关键顺序：先写检查，再改产品。反过来的话，检查会变成"描述产品现在做什么"，那是一种永远不会失败的检查。

检查从没红过

一条从没失败过的检查，只有三种可能：没在跑、没接进判定、写得太松。三种都长得像成功。

动作：故意造一个违反它的结果，看它会不会红。如果还是绿的，这条检查是装饰。

检查红了

先别让它修。先问一句：你认为这是产品错了，还是测试错了？理由是什么？

实测中我遇到三条红的，三条全是测试自己写错——我把字符数算错、把排序预期写反。如果直接改代码去迁就错的测试，测试会变绿，而产品会变坏。

全绿但结果不好

这是两件不同的事：机制可不可信和产出可不可用。一个机制完全可信的工具可以稳定地输出垃圾。

动作：先问"有没有一条检查是关于结果对不对的，还是全是关于程序有没有崩的"。然后让它给你看三个真实输入的输出。

这一步过了

但注意：过了这一步不代表产品好用，只代表你能判断它好不好。

谁来验，怎么验

每一行都是一个你能亲手做的动作。做不了就记成未通过，写明缺什么，不要用近似动作代替。

动作通过标准
你亲眼看到过一条检查变红，并能说出是哪条抓到的不是"应该有"，是"我看到了"
被跳过的检查数为零，或者整体结论是"不完整""跳过"绝不能算通过
成功 + 各种失败原因 = 总数拆开加一遍，两分钟

这一步用到哪些 skill

  • anb-judgeable — 定什么算好，且检查必须能失败。唯一硬门。
  • anb-check-break — 故意弄坏，看检查会不会红。
  • anb-check-offline — 断网/密钥错，必须是"无法判断"而非"通过"。
  • anb-check-readback — 逐条念结果，含跳过了几条。
  • anb-check-reconcile — 把总数拆开加一遍。
  • anb-check-output — 看三个真实输出，判断结果对不对。
  • verification-before-completion — 证据先于声明：跑命令、读输出、再下结论。
  • llm-evaluation — LLM 评测集设计、judge 偏差控制、回归门。
  • test-suite-health — 测试越写越多越慢越脆时体检。
  • code-review — Standards 与 Spec 两条轴分开报告。
  • security-review — 高置信度漏洞，含 prompt injection 与租户泄漏。
  • diagnosing-bugs — 先建会变红的回路，再谈假设。
