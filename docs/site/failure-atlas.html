架构故障图鉴 · 八个故障

多智能体系统不是从技巧开始坏的，是从结构性故障开始坏的。这一页把八个反复出现的故障、每个的结构修法、以及每条修法的证据强度列在一起——先认故障，再选修法，最后看证据站不站得住。
萃取自一张在 X 上流传的 Agentic 架构故障图（@sermakarevich 汇编转述）；措辞归属原图，不写成本站结论。

为什么按故障排，不按技巧排。 本仓库名为 mas_router_method——多智能体系统的路由方法。图里的故障 04（用实测统计路由，不靠模型自判）与 07（先路由便宜的）正是这个命名的立论来源。诊断顺序也一致：先定位故障层，再动修法（eval → data → tool → prompt），而不是一上来就改提示词。

01早错一步，步步皆错

模型标不出自己写的那段是错的，于是沿着错前提一路往下

P多轮准确率 −39%，不可靠性 +112%；回放摘要救回 15–20%，多数情况得开新对话。
  • D每次尝试都给全新上下文：前置节点写简报，无状态 worker 执行— agents-as-tools / AgentTool / .as_tool()
  • A长任务用重启循环：保留文件与测试结果，每轮丢掉对话记录— 无基准
  • DCheckpoint 后能 rewind：恢复对话加代码，不只是文件；连续两次纠正失败就清空— Claude Code vs Cursor
  • V错误锁在单次尝试里，绝不跨尝试传播；先想后动，减少自我固化— Manus；先想后动 [P]
  • D按步做持久重试— Temporal / DBOS；陷阱：把错误当字符串返回会被当成功重放

02交接丢掉了接收方要的东西

发出方说清了，接收方拿到的不是它需要的那部分

P一次交接后 recall 0.32，单体不交接是 1.00。
  • D用类型化状态而非散文：字段定死，没有字段的事实就会丢— LangGraph / POLARIS
  • P文件化任务包，worker 能反复重读：73.0→75.6、44.4→58.3— arXiv 2603.25723
  • P合并者看完整规格，不看切片：切片团队 58.2% → 88.9%— arXiv 2603.24284
  • P结构化中继而非散文：5 跳后 22.5% → 75.2%；100 token 验证摘要 $0.125 vs $0.399— DELM
  • P按输入重建而非按时效：0/30 过时计划通过 vs 30/30，多约 15% token— Planfence
  • P每个边界都设门：穿越 4 级流水线的错误 58.4% → 16.2%— arXiv 2608.14588

接着查：8+3 层契约实战用法·编排层

03视野塞太满，工具挤掉了任务

工具和 skill 占满上下文，模型顾不上要做的事

PHaiku 4.5：10 工具 91%、15 工具 87%；Sonnet 4 到 30 工具跌破 90%。
  • V渐进式披露：一行索引，正文按需取：77k → 8.7k token，Opus 4 从 49% 到 74%— 惰性加载 47.3k → 2.4k [P]
  • P扁平索引、不嵌套：嵌套后成功率 0.7479 → 0.3890；精简描述 +19.0 vs 详尽 +0.7
  • D每节点一份目录：分流路由把这一轮交给只带本主题工具的节点；路由错不可恢复
  • V遮蔽而非删除：从选项里藏起工具，但留在缓存前缀里— Manus
  • V不到约 10 个工具不值得上多 agent；只有窗口不够才派子 agent— 一个 harness 输给了朴素循环 [P] LOCA-bench

04多个 agent，同一批错

一个模型的副本共享同一套盲区，投票投不出多样性

P独立时错误 ×17.2、集中评审 ×4.4；平均 −3.5%。
  • P先独立后交互：先各自提案，再讨论；一交互多样性就从 1.03 掉到 0.47
  • P审查席换一个模型家族：同族共失把投票/路由封顶在 5.2–7.9%；审计员配同伴 1.00 → 0.23
  • P带全规格的中央评审，而非自由讨论：放大 17.2× → 4.4×— arXiv 2512.08296
  • P固定顺序、固定角色：比协调者 +14%；一文件一写者，worktree 63.3% vs 55.5%
  • P用实测 per-task 统计做路由，不靠模型自判：41.41 → 47.74%；Opus 4.6 零样本路由最差 39.27%
  • P先做等预算对照：同样思考 token 下单 agent 0.418 vs 团队 0.379–0.388— arXiv 2604.02460

05输入比任何窗口都大

要处理的材料超过上下文，硬塞只会稀释

Vorchestrator-workers 比单 Opus 4 高 +90.2%，代价是 15× token；超过约 45% 基线不再涨。
  • Vorchestrator-workers，effort 规则写进简报：token 解释了 80% 的方差— Anthropic
  • P用代码执行替代原始工具输出：43.6k → 27.3k token，+3–5 分；递归读在 132k 处超 GPT-5 >34 分
  • P编码 agent 当读取器、带文件工具：100k → 200k 文档调用翻倍、−13.6 分；harness 让 Opus 4.6 从 93.1% 掉到 76.7%
  • V廉价无状态读取器：读取省约 90% 主模型 token，每次 10–30 秒，漏过一个线程安全 bug— Spotify
  • V文件系统当上下文：worker 写、主管读摘要；Agora 13 worker 刷新 233 项最好成绩、无基线— Manus；Agora [P]

06评审附和作者，读者轻信文档

没有外部信号，就没有自我纠正

P无外部信号时不会自纠。
  • V盲验证者：只给产物加任务、不给作者轨迹：Cloudflare 48,095 个 MR，3 分 39 秒，$0.98，1.2 条发现
  • P换家族评审：56.7% vs 42.7%；同模型换新上下文约值 1 分；更弱的评审会把 91.4 拖到 82.8
  • P作者看不到的隐藏评分：约 56% → 76%；同族评审带 +0.75 偏置— AIRA2
  • V评审由 harness 指派，绝不自己派：Sonnet 5 模型卡里，模型派了子 agent 批准自己
  • P守卫节点放在对话之外：攻击 17.6% → 1.75%，效用 47.7 → 42.7；CaMeL 163/163、2.82× token
  • P从合并轨迹做归因：agent 级 53.5%、step 级 14.2%；过半根因落在模型节点— AgentFail

07时钟与账单

语音要快、节点要慢、成本要省，三者互相拉扯

P语音控制约 320ms；口述工具调用 74.6 vs 文本 80.8；纯语音论证准确率 42.2。
  • P快节点说话、慢节点动手：工具召回 92–97%；tau-Voice 语音 31–51 vs 文本 85— NVIDIA
  • P规划一次、并行执行：ReWOO 5× token 效率、LLMCompiler 3.7× 延迟；仅当执行器更便宜才划算
  • V先路由便宜的：RouteLLM 95% 分数下省 3.66× 成本；单 agent 85% $2.78 胜过先规划后执行 84.6% $3.18— Prewalk
  • V缓存感知前缀：输入:输出约 100:1，命中率才是指标；团队共享前缀 7×— Manus；共享前缀 [P]
  • P睡眠期计算约比测试期少 5×；从日志恢复；按节点设预算（时间、调用、线程）— 预算 [D]

接着查：Agent 图谱·交付车道作战手卡·先路由再执行

08跨会话什么都没学到

记忆产品反而输给朴素的全历史

V记忆产品输给全历史：Mem0 66.88 vs 72.90；CL-Bench 15.1 vs 22.3。
  • P先和全历史对照：CL-Bench 全历史 22.3 > Mem0 15.1 > ACE 4.6 > Notepad 3.5（模型各异）
  • P记忆管理者带 schema 加评审：写入静默失败 18–30%；共享库时植入的记忆会在多 agent 间扩散
  • P血缘追踪：存下条目由什么构成，按输入重建— Planfence
  • P循环紧时用任务专属记忆：JITMEM Qwen3-8B ALFWorld 61.2 → 77.4；ACE agent +10.6%
