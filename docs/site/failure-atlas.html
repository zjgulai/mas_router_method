六类假信号
和你读它的四种错法

这一页不是故障排查指南。它讲的是更麻烦的一件事： 你的产品正在坏着，而所有自动检查都在告诉你它很好。 前四类是程序给的假信号；第五、六、七类不是假信号，是你读它的方式出了问题——一个是把空白读成结论，一个是观察本身改变了被观察的东西，一个是数的时候就数错了。 全部来自真实运行，全部能在你不看代码的情况下被发现——但前提是你知道该往哪看。

怎么用这一页

前四类讲「信号是假的」，第五类讲「没有信号」，第六类讲「信号被你改了」，第七类讲「你数错了」。前四类的成因不同，但骗你的手法是同一个：让一个空的检查显示为通过。

前四类在程序里；第五、六、七类在你自己身上——填空白、干扰观察、用错工具。防法各不相同：识破、忍住不填、做一次加法、换一种算法再数。

发生在什么时候：每次 agent 说「全部通过」之后。你不需要理解它怎么修的，只需要花两分钟做那个动作。

核心判断：一个检查如果从来没有失败过，它就不是检查。你要找的是「它上次失败是什么时候」——答不出来，它可能是假的。
一

它把「坏了」报成「好了」

最危险的一类。检查程序自己出错、或者根本没执行，结果被计为通过。你不会收到任何提示，因为对系统来说什么都没发生。

1 · 安全检查把「服务挂了」算成「成功拦住了」

真实现场：评测的护栏用例判定 · 已修复

它长什么样
产品有四条「绝对不能做」的红线（不能说某种疗效、不能用别人的音轨、不能抄竞品的镜头、不能做无法证实的宣称）。测试报：四条全部通过。实际上，测试跑的时候后端服务挂着，产品什么都没做出来——而「什么都没做出来」被算成了「成功拒绝」。
为什么它骗过了所有人
判定条件写的是「没有产出 并且 运行没有成功」。一个因为服务挂掉而中止的运行，完全符合这个条件。「拒绝」和「崩溃」在产品表现上是同一个样子：什么都没产出。写这行代码的人没有坏心，他只是没意识到这两种情况需要分开。
你怎么自己发现
把外部依赖弄断，再跑一次，看红线测试报什么。具体做法：让 agent 把那几个密钥临时改成错的（或者干脆删掉），然后重跑安全测试。正确的结果是「无法判断」，不是「通过」。如果它还是绿的，这条红线从来没被真正验证过。
纪律：任何检查必须有三种结果，不能只有两种——通过、不通过、未能判断。第三种绝不能算通过。

2 · 需要人判断的那部分，一次都没实现，却被算作通过

真实现场：评测的评分维度 · 未修复

它长什么样
评测分两类：能数出来的（时长对不对、有没有禁用词）和需要读一遍判断的（这段话像不像这个品牌说的、这个镜头拍得出来吗）。第二类需要接一个「裁判」来打分，而这个裁判一直没写。于是每一次评测，第二类都被标成「跳过」，而「跳过」不影响总体结论：总判定是「没有失败项，通过」。
为什么它骗过了所有人
报告里真的写了「跳过」两个字。但报告同时写着「通过」，而人只看最后那个词。更糟的是：这条通过线写的是「至少 8/10 达标」——一个永远不会被计算的分数，永远满足。
你怎么自己发现
让 agent 把评测结果逐条念给你听，一条都不许合并。你必须听到这几件事：一共几条、通过几条、失败几条、跳过了几条、为什么跳过。听不到「跳过」这个词，就是被藏起来了。
纪律：被跳过的检查必须在报告里占一个格子，并且让总体结论变成「不完整」，不是「通过」。
二

它测的不是你的产品

测试本身是认真的，跑得也对。但它跑在一个假环境里，而假环境的规则和真实环境不一样。于是测试越绿，离真实越远。

3 · 所有测试通过，但真实运行时第一步就必失败

真实现场：评测用的假数据仓库 · 已修复

它长什么样
产品有一个动作是「把这条参考视频存下来，然后分析它」。分析之前要先按编号把它查出来。测试环境里，「查列表」这个动作被写成了「永远返回空」。于是每一次真实评测，模型要分析视频时都被告知「这条参考不存在」。而单元测试全绿，因为单元测试不经过这条路。
为什么它骗过了所有人
假环境是「为了让测试跑得快」而写的，它的作者没有恶意——他只需要它在自己测的那条路上返回对的东西，其余随便。于是就出现了「假环境比真实环境更宽松」：真实环境会报错的地方，假环境静默通过。这是所有测试替身的通病。
你怎么自己发现
问一句：「这个测试用的是真数据还是假数据？」然后要求：那些假数据必须和真的遵守同一套规则，并且有一套测试专门验证这一点。更简单的动作——让它用一个你自己随手找的真实输入跑一次，不要用它准备好的样例。样例被特判过的概率很高。
纪律：假环境必须比真实环境更严格，不能更宽松。做法是同一套检查既跑假的也跑真的。
三

保护机制在，但永远不会启动

最隐蔽的一类。代码确实写了、也确实读得到，注释还写着「没有它就会出大事」。但它等待的那个条件永远不会成立，所以它一次都没生效过。

4 · 成本上限的检查，等一个永远不会来的值

真实现场：运行时的花费控制 · 未修复

它长什么样
产品有一次运行最多花多少钱的上限，代码里写了两道保护。第二道的写法是：每轮循环都检查「当前花了多少，超了就停」。但「当前花了多少」这个数字，只在整次运行结束的那一刻才会被填上。所以每轮循环检查的时候，它读到的永远是 0。
为什么它骗过了所有人
代码在那儿，注释也在那儿，还解释了为什么需要它。任何人读到这里都会认为保护已经就位。而要发现它不生效，你得注意到「这个变量在哪里被赋值」——一个只需要看三行就能发现、但没人会去看的问题。
你怎么自己发现
不要问「有没有做保护」，问「它上次拦下来是什么时候，给我看那次记录」。任何保护机制都应该有一次「它真的拦住了」的证据。拿不出证据，就把它当成没有。
这个问法对成本上限、频率限制、权限检查、重试次数全都适用。
纪律：保护机制必须配一条「它真的会拦住」的测试。测不出拦截，等于没有这个机制。
四

两个地方各写一遍，然后就对不上了

没人写错的代码，错在重复。同一个规则被写进两个文件，改了一个忘了另一个，或者两个数字一开始就差了一点点。

5 · 截到 2000 字，多加一行提示变成 2006，上限正好是 2000

真实现场：运行记录的保存 · 未修复

它长什么样
每次运行都会记下「它做了什么」，每条记录有长度上限（2000 字）防止存太多。生成记录的地方会把过长内容截到 2000 字，然后贴心地加一句「……还有 4000 字被省略」。这句话是 26 个字符。于是每条超长记录都是 2026 字，全部存不进去。
为什么它骗过了所有人
存不进去的后果被兜住了：程序捕获这个错误，打一行日志，然后继续。用户看到的是「运行成功」，只是历史记录里没有这一次。而「历史记录缺失」这件事，只有在你想回头查某次运行的时候才会发现——那时候已经过去几周了。
你怎么自己发现
连做三次，然后去历史里数。你做了几次，历史里就该有几条。少了一条，就是这条。
这个动作适用于一切「有记录」的功能：订单、日志、消息、上传。做 N 次，数 N 条。
纪律：同一个限制只能有一个定义。截断的长度和允许的长度必须来自同一个数字。

6 · 群里 @ 任何人，机器人都当成在叫自己

真实现场：聊天渠道的事件判定 · 未修复

它长什么样
产品接在一个群聊里。规则本该是「只有 @ 我才回应」。实际实现判断的是「这条消息里有没有 @ 任何人」。于是同事之间互相 @ 讨论工作，机器人会插进来，把「你看一下这个」当成给自己的任务，然后花掉一次运行的钱去做点什么。
为什么它骗过了所有人
「不要自我回复」这个最容易想到的坑，写的人考虑到了，也做了保护。漏掉的是「怎么认出自己」——一个看起来更简单、实际上更需要仔细的地方。人对已经想到的部分会产生安全感，这份安全感会盖住漏掉的部分。
你怎么自己发现
自己制造一次「不该触发」。在群里 @ 一个同事说句话，看机器人有没有反应。它响了，就是这条。
推广：任何「在特定条件下才动作」的功能，都要亲手制造一次不该触发的条件。做十次正常路径，不如做一次不该走的路径。
纪律：「什么情况下不该动」比「什么情况下该动」更需要测试，因为前者不会有任何人来告诉你它错了。
五

找不到，不等于不存在

前面四类讲的是「有信号但信号是假的」。这一类讲另一种：没有信号，而你把它读成了结论。它发生在你自己身上，不在程序里。

7 · 「目录里没有」被读成「这东西不存在」

这一例是我自己犯的，发生在写这份手册的同一周

它长什么样
我在盘点一个项目时，发现它的文档列了 63 个工具，而仓库目录里只有 34 个。我据此写下了结论：「42 个被写成可调用，却根本不存在」。这条结论被我写进了报告、写进了图表、还配了「这是这个仓库唯一一处系统性失真」这样的评语。
实际发生了什么
那 42 个全部存在，只是由另一个地方提供——它们随客户端一起安装，不在项目目录里，调用时要带一个前缀。而我在同一周里其实成功调用过其中一个。我从没注意这个矛盾，因为它出现在两个不同的上下文里。

更糟的是：我的结论里带着一个看起来很有说服力的推理——「照着文档做的人会在第一步卡住」。这句话是真的，但原因不是「工具不存在」，是「文档没写来源」。正确的结论和错误的结论，可以推出同一个症状。
你怎么自己发现
在下结论之前，把「找不到」拆成三种，逐个排除：

一、目录里没有。这是你能直接看到的唯一事实。
二、这个东西本身不存在。需要另一次检查：去它的来源处找。
三、它存在但你现在用不了。又是一个不同的问题，解法是装东西，不是修文档。

只要三者的解法不同，就不能跳。而「目录里没有」和「不存在」之间，永远差一个检查。
纪律：说「不存在」之前，必须先说清你查了什么、没查什么。只查了一处，就只能说「我只在这一处找到 34 个」——那是一个观察，不是结论。

它和前面四类的关系

为什么单独立一节，而不是并入

区别在哪
第一到第四类，是系统给你一个假信号：绿色的报告、通过的结果、看起来跑了但其实没跑。你要做的是识破它。

这一类相反：系统什么都没给你。没有报错，没有结果，没有记录。空的部分需要你自己去填，而你填进去的，是你的猜测。
为什么它更难防
因为假信号至少是一个东西，你可以拿起来看。空白不是东西，它不会引起注意。

而且空白特别容易被填充成最省事的那个结论：「没有」「做不到」「不支持」。这三个词说出来都很自然，都不需要额外工作，而且通常没人会反驳——因为你看起来查过了。
同一招能用在三处
这一条和另外两件事是同一条原则的三个面：

测试红了——先问是产品错了还是尺子错了（红不等于坏）。
检查全绿——先问这个检查上次什么时候失败过（绿不等于好）。
记录是空的——先问是查了一处还是查了所有地方（空不等于没有）。
纪律：红、绿、空，三种信号都不能直接读成结论。每一种都要多问一句「这个信号是怎么产生的」。
六

测量本身产生了信号

前面五类都在讲「读到的信号不可信」。这一类更麻烦：信号是对的，但它被「你去读它」这个动作改变了。

8 · 每看一次仪表盘，数字就变一次

真实现场：一个网页工具的请求计数 · 已修复

它长什么样
我做好了一个记录「跑了多少次、失败几次、为什么失败」的页面。第一眼看到的是：总数 6，成功 1，失败原因加起来 4。6 不等于 1 加 4。
为什么会这样
两个原因叠在一起。

一、有些页面只增加总数，从不记录结局。首页、错误页各加一次，然后直接跳走，没有「这次算什么」的记录。开了头没结尾。

二、更隐蔽：去看指标的那次请求，自己也被计入了指标。你每刷新一次仪表盘，请求数就多一次。

合起来的效果是：数字越看越多，而你越看越相信它在涨。
你怎么自己发现
把总数拆开加一遍。成功的 + 各种失败原因的 = 总数吗？这是一个两分钟的算术，不需要懂任何技术。

对不上，就一定有一个地方「开了头没结尾」，或者「被计了两次」。

第二招：什么都不做，连续刷新观察页面五次，看数字有没有动。如果动了，你测的东西被你自己推动了。
纪律：观测动作不能改变被观测的东西。健康检查、看仪表盘、读日志，这些都不该计入统计。

它为什么值得单独一类

和前面五类的根本区别

区别
第一到第四类：系统给了一个假信号。
第五类：系统什么都没给，你把空白填成了结论。
第六类：信号是真的，但它因为你的观察而变了。

这一类的特征是数字之间对不上。它不撒谎，它只是被你干扰了。
为什么它难被发现
因为每一个数字单独看都很合理。6 次请求、1 次成功、4 次失败——分开看没有任何问题，只有把它们放在一起加一遍，才有问题。

而人不会主动做加法。看到一个总数，第一反应是接受它，不是核对它。
它同时是最好查的一类
因为它是唯一一类可以用纯算术发现的。前面五类都需要你构造输入、断网、造数据；这一类只需要你把一个数拆成几个数再加回去。

代价是两分钟，收益是能发现「记录本身有洞」——而那是所有其它检查的地基。地基有洞的时候，上面所有结论都不成立。
纪律：任何总数，都必须能拆成互不重叠的几项，且加起来相等。这条对「多少请求」「多少订单」「多少钱」都成立。
七

你数的那个东西，不是你以为的那个

前六类都关于「怎么读信号」。这一类关于读之前那一步：数。数错了，后面所有推理都是错的，而且看起来完全正常。

9 · 用一个数「行」的命令去数「出现次数」，得到 7，实际是 108

真实现场：验证一个页面里有 108 个 skill 条目 · 当场发现

它长什么样
我把站点部署上去，想确认 skill 全表的 108 个条目都渲染了。用了一条命令： 
$ grep -c '<tr id=' skills.html
7
于是我判断：「只渲染了 7 个，少了 101 个。」差一点就去改生成脚本。
实际发生了什么
grep -c 数的是「包含匹配的行数」，不是「匹配出现的次数」。

那个 HTML 文件只有 147 行，因为整张表被写成了一行。7 个阶段各占一行，所以每个阶段一行里含有很多个 <tr>，而 grep 只数到 7。

正确写法：grep -o '<tr id=' skills.html | wc -l → 108。或者解析结构：各表 19 + 24 + 17 + 18 + 14 + 9 + 7 = 108。
为什么它特别危险
因为错误的数字长得和正确的数字一模一样。7 是一个合理的数，它不会让你警觉。而且它来自一条权威的命令——你信任 grep -c，因为它就是干这个的。

更糟的是下一步：你拿 7 去和 108 比，得出"少了 101 个"的结论，然后开始找原因、改代码。整个过程里你不会想到去质疑 7 本身。
你怎么自己发现
两招，都很便宜：

一、换一种算法再数一遍。解析结构、看各表行数、加总。两个独立算法给出同一个数，才可信。
二、先数一个你知道答案的东西。比如文件行数（wc -l）、或先 grep -o 看实际匹配长什么样。

这条和第六类（测量污染）是同一个动作：把总数拆开加一遍。
纪律：任何一个数字，都要用第二种方法再算一遍。对不上，先查算法，不要先查产品。

10 · git status 报了 120 个改动，一个都没有

真实现场：一个挂载目录上的 git 仓库 · 已记成 INC-001

它长什么样
在某个目录里跑 git status，它规律地报一百多个文件是「已修改」。 跑 git diff，输出为空。逐字节比对，文件和上一个 commit 完全一致。

同时 git add 会报 short read while indexing。
为什么会这样
这是挂载文件系统上的一个已知现象：git 的 stat 缓存假设文件的时间戳和大小能可靠地判断「有没有改过」， 而这个假设在这里不成立。根因没有完全查清——所以它被记成一条事故，而不是一条结论。
你怎么自己发现
当 git status 和 git diff 不一致时，信 git diff。 status 说变了、diff 说没变，那就是没变。

想彻底确认，用第三条路：git show HEAD:文件 | md5sum 对比 md5sum 文件。 两个哈希一样，就是一样。
纪律：同一个问题用两个工具查，结论不一致时不要挑你喜欢的那个，要去查为什么。

11 · 用 tar 复制文件，它给短文件补了 4096 个 NUL

真实现场：在两个路径之间搬运一个仓库 · 一个文件不可恢复

它长什么样
为了绕开上面那个 git 问题，我把仓库用 tar 复制到另一个路径再操作。 复制「成功」，没有报错。之后提交时发现几个 markdown 文件变成了「二进制」—— 打开看，内容尾部被补了几千个 NUL 字节。

更早还有一份文件，整段内容被二进制垃圾覆盖，呈周期性重复，不可恢复，只能重写。
为什么它没被发现
因为复制过程没有报错。tar 按块写入，块没填满就补零——在被测文件系统上，这个补齐没有被裁掉。

而 markdown 文件里多几个 NUL，用 cat 看是看不出来的：终端会把它们当不可见字符。 只有 file 命令、或提交时 git 说「这是二进制」，才会暴露。
你怎么自己发现
复制完立刻查一次：find . -name '*.md' -exec grep -lP '\x00' {} \;。 有输出就是坏了。

更根本的做法：复制不要用 tar，用 cp -a。或者在复制后对关键文件做一次哈希比对。
纪律：任何「搬运」操作之后，都要验证目的地。搬运不报错不等于搬运正确。

它和前面六类的区别

为什么单独立一节

区别
第一到第六类：系统给出了一个错误的信号，你要识破它。
第七类：系统给的信号是对的，但你用错了工具去读它。

这一类的错误源在你自己手上，不在被测对象身上。所以它发生得更频繁，也更少被记录——因为没有人会把自己数错写进事故报告。
它出现的场合比你想的多
同一个坑的不同外衣：
· wc -l 数行，不等于条目数（一条目可能跨多行）
· 数组长度不等于去重后的数量
· 日志行数不等于请求数（一次请求可能写多行）
· 文件个数不等于功能个数

共同点：你在数一个「容器」，却以为在数「东西」。
纪律：数之前，先说出你要数的到底是什么，以及这个命令数的是什么。两者不一致就别数。

两分钟自检表

每次 agent 说「全部通过」之后做一遍。不需要看代码，不需要懂技术。任何一条答不上来，就往那一类去找。

问它答不上来意味着你自己做什么
上次有检查失败是什么时候？给我看那次记录可能是第一类：从没失败过的检查翻历史，找不到失败就是没有失败过
这次结果里跳过了几条？为什么跳过？第一类：跳过被算成通过要求逐条念，不接受合并成一句
把密钥改错／断网，再跑一次它能跑，就说明它不依赖外部正确结果必须是「无法判断」
这个测试用的是真数据还是假数据？第二类：测的不是你的产品换一个自己随手找的真实输入

附

有些验收，你做不到

这不是失败方式的第八类，是六类之外的一个现实问题：手册说的验收动作，有时候需要你确实没有的东西。

「找一个不懂技术的人听我讲」——我找不到

真实现场：第一次完整走完六步 · 两处卡住

卡在哪
第一步的验收是「把五句话念给一个不做这行的人听，他能复述出用途」。第四步的验收是「用另一台设备打开，让另一个人试一次」。

这两处我都做不到：我调不起第二个人，也没有第二台设备。
正确的做法：记成未通过，然后继续
不是跳过，不是用一个相似的动作代替（比如「我自己念了一遍，觉得挺清楚」——那不是验收）。

是明确写下：「这一步的验收动作需要 X，我没有 X，所以这一步未通过。」 然后继续做下一步。
但必须写下来，因为记忆会骗你
「这一步没验」和「这一步验过了」在后来的记忆里会混成一个。三天之后你会记得「我做过那个产品」，不记得其中两步其实没验。

而不写下来的后果是：你会带着两个未验证的假设往下走，并把它们当作前提。
有一个便宜的替代品，但它不是替代
对于「别人能不能用」，你可以让 agent 扮演一个陌生用户，只给它页面、不给它任何解释，看它卡在哪。这能发现一部分问题（比如按钮没有说明、错误信息看不懂）。

但它不能替代真人，因为 agent 会比你聪明地猜测意图，而真人在不懂的时候会放弃。所以它算「部分验证」，要照实标注。
纪律：一个验收动作做不了，就写「未通过」并写明缺什么。不许用近似动作代替，不许因为「大体上没问题」就记成通过。

这一页真正想说的是

前六类情况，没有一种是「写错了代码」。写代码的人知道自己在做什么，每一处单看都能讲出道理。 它们错在同一个地方：让一个空的检查显示为通过。

这意味着你不能靠「它说通过了」来判断产品好不好，只能靠「我亲手试过它」。 而这恰恰是你能做的事——上面每一条的验证动作，都不需要读代码，只需要你动手两分钟。

所以这套方法的全部重心，不在于让 agent 写得更对，而在于让你的怀疑有地方落地。 一个能自己动手验证的人，和一个只能相信报告的人，做出来的产品差得很远——差的不是技术，是这份怀疑。

而第五、六、七类提醒的是这件事的另一面：怀疑也要有落点——不能停在「没有」， 不能相信「我看了一眼」，也不能相信「我数过了」。 我自己就在写这一页的过程中，把「这一处没有」写成了「根本不存在」，还配了一段很像样的推理。 出错的原因不复杂——我只查了一个地方。所以这一页最后一句话是：说「没有」之前，先数清你查了几个地方。
