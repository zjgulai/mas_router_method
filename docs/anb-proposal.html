方案 v02026-10-24状态：待你定方向读者：不会写代码的产品开发者

Agent Native Builder
让不会写代码的人，能判断自己做的东西是真的能用

这不是一套"教你写代码"的方案。代码由 agent 写。 这套方案要解决的是另一件事：当你看不懂代码时，你怎么知道自己做出来的东西是真的能跑，而不是看起来能跑。 全部内容围绕这一个问题组织。

问题说准了，方案才对得上

先纠正一个我自己的误判：我上一轮是在为工程师设计流程。对不会写代码的人，那套东西的每一处假设都错。

01

他们不缺代码，缺判断力

agent 能把代码写出来，而且写得比他们自己学三年还好。真正卡住他们的是：面对一段正在运行的程序，不知道哪里会坏、坏了看不出来、好了也不确定。

02

他们最大的风险是「假绿色」

测试全过、没有报错、界面能点——这三件事同时成立，产品仍然可能完全不能用。能读代码的人能发现，他们不能。所以他们会带着一个坏产品继续往前走。

03

他们要的不是流程，是「能亲手检验的一下」

十二个阶段的 SOP 他们记不住也不会遵守。但如果每个阶段都以「你现在可以自己点一下这个」结束，他们会做完——因为那一下给的是确定感。

五条设计原则，每条都挂着一个真实事故

这不是从方法论推出来的原则，是从我上一轮在这个仓库里实际挖出来的缺陷倒推出来的。每条后面的事件都真实发生过，可以查。

一、每个自动信号必须声明它能证明什么、不能证明什么

事故：护栏把服务 502 记成「成功拒绝」。四条安全用例全部变绿，实际一条都没被验证。原因只有一行判定条件写错了。

二、「测试通过」和「能用」是两件事，必须分开报

事故：所有单测通过，但第一次真实分析必然失败。测试用的假环境返回空列表，而那条路径只在真实运行时才走到。

三、任何保护机制，都要有证据证明它真的会触发

事故：成本上限的检查永远不触发。它读的那个数字只在运行结束时才有值，所以条件恒假。注释写着"没有它就会超支"，代码里它什么也没做。

四、同一个数字不许在两个地方各写一遍

事故：截断到 2000 字符，加个尾巴变成 2006，而上限正好是 2000。于是每次运行记录写入都失败，用户看到的是"运行成功"。

五、没验证过的东西必须写「未验证」，不许留白

事故：五份评测记录成本全是 0，一次真实评测都没跑过，但目录看起来像有历史。空白会被读成「正常」。

闭环长什么样

六步，不是十二步。每一步的出口都是一次「你自己能动手的检验」，不是一个文档。测试不过不往前走——这是唯一一条硬规矩。

为什么是这六步，而不是更多

因为我按「哪一步能拦下一个会毁掉整个产品的错误」来切的。多出来的步骤是给团队协作和长期维护的——你现在的规模用不上，加进去只会让流程被放弃。第三步（能判断）之所以被单独立出来而不是塞进「能跑」，是因为不会写代码的人最容易跳过它：东西跑起来了，看着挺好，就继续做下一件事了。而所有「做了三个月发现方向错了」的项目，都是在这一步没停下来。

六个阶段，每个阶段四栏

「你在做什么」是给你的；「它会假装成什么样」是我今天实际挖出来的坑；「你可以自己验」是你亲手能做的动作，不需要看懂代码。

1

想法

目标：把「我想做个 X」变成一句话，能判断做完了没有
你在做什么
回答四个问题，每个用一句话：谁在什么情况下用它、他为什么现在没有更好的办法、做完之后他具体能做什么以前做不到的事、什么情况说明这事不该做。第四个问题最重要，它决定你要不要开始。
它会假装成什么样
agent 会很热心地替你补全答案，写出一份看起来完整的方案。而那份方案的每一条都是它的猜测，不是你的判断。这就是为什么第一步必须你自己说完，agent 只负责提问、不负责回答。
你可以自己验
把那一页念给一个不懂技术的人听。如果他听完能说出「所以你是在帮谁解决什么」，这一步过了。如果他要问「这是什么意思」，重写。
反模式
写功能清单（"要有登录、要有导出、要有后台"）。功能清单不是想法，它是想法的替代品，而且它让你在第三步无从判断好坏。
2

能跑

目标：一条真实输入，从头走到尾，出一个真实结果
你在做什么
不做功能，只做一条最窄的路：一个真实输入进去，一个真实结果出来。不要样例数据，不要「先做个界面」，不要「以后再接真实数据」。这条路要能重复跑第二次。
它会假装成什么样
这是最容易骗人的一步。agent 给你的东西会有界面、有按钮、点下去有反应——但背后用的是假数据。你以为跑通了，其实只跑通了界面。我上一轮那个仓库就是这样：所有单测通过，第一次真实分析必然失败，因为测试用的假环境返回空。
你可以自己验
给它一个你自己随手找的真实输入（一个真链接、一份真文件、一句真需求），看它给出什么。然后换一个你说不上来的输入再试一次。第二次才是真的测——第一次可能是被特判过的。
反模式
「先把架子搭好，功能后面填」。对不会写代码的人，架子没有任何价值，因为它不产生任何你能判断的东西。先做那条最窄的、能出结果的、丑的路。
3

能判断

目标：定下「什么算好」，并且这个标准能自动跑
你在做什么
写下 5 到 10 条「什么样算好、什么样算坏」。每条都要能变成一次自动检查：要么是能数的（时长在 15 到 45 秒之间、必须包含某个字段），要么是需要人读一遍判断的（这段话像不像这个品牌说的）。然后先写检查，再让它改产品。
它会假装成什么样
三种，全都见过：
一、把崩溃当通过——检查程序自己出错时，报「通过」。于是我这边四条安全用例全绿，实际一条没验。
二、检查项永远跳过——需要人判断的那部分没实现，每次都记为「跳过」，而「跳过」被算成通过。
三、规则写了但没接上——代码里有这条检查，用例里没引用它，等于不存在。
你可以自己验
三重验证，缺一不可：
一、故意做坏一次：让它产出一个明确违反某条标准的东西，看检查会不会红。如果还是绿的，这条检查是假的。
二、故意断网或删掉密钥，再跑一次。这时候应该是「无法判断」，不能是「通过」。
三、让它把检查结果逐条念给你听，你要听到「跳过了几条、为什么」。没听到，就是被藏起来了。
反模式
只测「正常情况」。十条全测正常路径，等于零条。真正会毁掉产品的是那些「不该发生却发生了」的情况——说错话、超支、把 A 用户的数据给了 B。
4

能交付

目标：别人拿到一个链接就能用，不需要你在旁边
你在做什么
让它能被人打开。这一步不是为了「上线」，是为了让你第一次从使用者的位置看它。你在自己电脑上跑，永远看不到别人会遇到什么。
它会假装成什么样
「本地能跑」被说成「可以用了」。区别在于：环境变量、密钥、域名、权限，这四件事在你自己电脑上全都是配好的，在别人那里全都是缺的。另外它可能给你一个只在你电脑上开着的地址，你发给别人，别人打不开。
你可以自己验
用另一台设备（手机）打开它，用你之外的一个人试一次。如果他卡在某一步，那一步就是你接下来要做的全部工作。
反模式
在这一步补功能。能交付的意思是「现有的东西能被用」，不是「再加三个功能就更好了」。
5

能观测

目标：出事的时候，你不问人也能看出是哪一层出了问题
你在做什么
只要三条信号：它一共跑了多少次、每次花了多少钱、失败的都是什么原因。三条都必须是你能打开就看到的，不是要跑命令才看得到的。
它会假装成什么样
日志里全是技术细节，但你想要的三个数字一个都找不到。或者更糟：成本显示为 0，因为根本没记。我见过五份运行记录成本全是 0，一眼看不出那是「没记」还是「很便宜」。
你可以自己验
故意弄坏一次（用掉一个不存在的输入），然后在记录里找不找得到这一次失败、以及失败原因说得清不清楚。找不到，或者原因写的是「出错了」，这一步没过。
反模式
先做漂亮的仪表盘。你要的是「出事能查」，不是「平时好看」。三条数字够了。
6

能复用

目标：下一个产品不用从零开始，但也不要背上一堆用不上的东西
你在做什么
把这一次里你真的用过三次以上的部分抽出来，做成下一个产品的起点。其余全部丢掉。
它会假装成什么样
「通用框架」的诱惑。agent 很擅长给你造一个灵活的、可配置的、能支持各种情况的底座——而这个底座本身会变成下一个项目最大的负担。判断标准很简单：这个东西上个产品用过吗？没有就别抽。
你可以自己验
用抽出来的模板开第二个产品，计时：多久能跑出第一个真实结果？如果比第一个产品更慢，模板是负担，不是资产。
反模式
为了复用而复用。第二次做同类产品时你会知道该抽什么；第一次就想抽，抽出来的全是猜的。

三件套各管一件事

你选了这个形态。它们的分工不是按内容分的，是按「什么时候用得上」分的——这决定了它们不会互相重复。

Skill

你坐在 agent 面前工作时用。它是给 agent 的指令，不是给你读的。

  • 六个阶段技能，每个包含：提问清单（一次只问一个、带推荐答案）、产出物模板、自检项、以及「这一步最容易假装成功的地方」。
  • 四个检查技能：故意做坏、断网试、念给我听、第二台设备。这四个是可执行的动作，不是建议。
  • 一个路由：你只要说「我不知道下一步做什么」，它判断你在哪一步，然后只拉起那一个阶段技能。不给你看全流程。
  • 关键设计：每个技能在动手前先问「这一步的验收是什么」，答不出来就不许往下——这是唯一硬规矩的落地点。

文档

你不在 agent 面前时用。它要在没有对话上下文的情况下也能读懂。

  • 一页决策树：我现在该做什么？回答三个问题就能定位到阶段。
  • 一页术语表：每个技术词配一句「用人话说」+「它坏了会怎样」。后一半是给非工程师的，一般文档没有。
  • 一页失败图鉴：今天挖出来的六个事故，每个写清「它长什么样」「你怎么自己发现」。这一页是整套东西里最值钱的。
  • 不写：架构原理、设计模式、技术选型对比。这些对你没有决策价值，而且会稀释前面三页。

模板仓库

新项目从它起步。它必须是能跑通的，不能是骨架。

  • 只放被验证过的部分：一个 agent 循环、一套数据形状、一个评测跑法、一条成本上限、三条观测信号。就这些。
  • 自带一个能跑通的例子，不是一个空架子。空架子会被误认为「已经搭好了」。
  • 自带六个已知坑的防护：每个坑对应一段代码 + 一条会红的测试。这是模板最大的价值——它把踩过的坑固化成默认行为。
  • 刻意不做的事：不做多租户、不做权限体系、不做多平台。这些是这个仓库上一个版本最大的时间黑洞，而且它们不影响第一个产品能不能用。

和现有东西的关系

这个仓库里已经有 34 个 skill 和一堆流程文档。直接叠上去只会让它更重。

现有的怎么处理为什么
42 个被引用但不存在的 skill 从目录里删掉，不要装 十一个流程阶段依赖它们，照着走的人会在第五步卡住。这是最快让人放弃流程的方式。
十二阶段 SOP（S0–S15） 压缩成六步 它的每一段都写得对，但它是给有工程团队的人写的。对一个人做产品，阶段数比阶段质量更致命。
六阶段路由 native-agent-dev 保留骨架，换掉内核 「按你说的阻塞点路由」这个设计是对的。要换的是每个阶段的内容：从「写给工程师的纪律」换成「给非工程师的判断动作」。
九个 ADR 与决策清单 保留，但对非工程师隐藏 它们是给下一个 agent 读的，不是给你的。你不需要读，但需要它们在——否则下次改动会推翻上次的判断而没人知道。
评测设计与用例 保留并前置到第二步 这是这个仓库写得最好的东西，也是唯一能替非工程师兜住质量的机制。它现在排在很后面，要挪到「能跑」之前。

这次明确不做的

每一条都有理由，不是偷懒。

不做「从零教你理解代码」

那是一条三年的路，而且学完了 agent 又会往前跑一代。你要的是能判断，不是能写。

不做多产品矩阵、增长、投放

那是产品做出来之后的问题。现在做，等于在还不知道能不能做出来的东西上分配注意力。

不做团队协作流程

票据、交接、评审委员会，这些在有第二个人之前全是负担。整个方案默认读者是一个人。

不做技术选型建议

选什么模型、什么数据库，这个问题对最终结果的影响，远小于「有没有做第三步」。

我不知道的部分

这套方案里有一半是我能证明的（六个事故、五条原则、六步的切法），另一半是判断，得说出来让你知道边界在哪。

  • 我不知道非工程师实际会卡在哪一步。我推的是「判断力」是瓶颈，依据是那些事故的形状。但真实的卡点可能是别的——比如耐心，比如不知道自己做的东西值不值得做。这个只能靠你试一轮才知道。
  • 六步是不是够了，我不敢确定。它是我按「能拦下什么错误」切的，不是按真实使用数据切的。有可能第五步（观测）对你其实是多余的，也有可能漏了你真正需要的一步。
  • 「故意做坏一次」这个办法我没在非工程师身上验证过。它在工程上成立（能变红的测试才算测试），但让人手动去弄坏自己的东西，心理上是有阻力的。可能需要在 skill 里做成「一键弄坏」。
  • 模板仓库我还没做。它必须从一个真实跑通的产品里长出来。这个仓库现在还没有一次真实的端到端运行成功——所以现在做模板，做出来的是骨架，而骨架最危险，因为看起来像成品。

下一步，两件事需要你定一件事

第一，先做哪个。我建议先做「文档里的失败图鉴」那一页——六个事故我已经有了，一页纸，半天的量，而且它是唯一能立刻改变你判断力的东西。Skill 和模板仓库都依赖它先把语言定下来。

第二，这个仓库怎么处理。它现在是个半成品，修好了六个缺陷但没有一次真实运行。要么我们花一天把它跑通（需要你有模型和视频分析的密钥），让它成为模板仓库的源头；要么把它当成纯证据存档，模板仓库以后另起。前者能让这套方案有实证，后者更快但会缺一块。

方案基于对该仓库的实测：6 个包 typecheck 通过、80 个测试通过（core 31 / evals 30 / feishu 19）、6 个缺陷中 4 个已修复并有测试、2 个（截断超限、预算检查）已定位未修。文中所有「事故」均可在 packages/ 与 docs/evals/recipe-quality.md 中查证。生成于 2026-10-24。
