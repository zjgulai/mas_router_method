# 打标层：一个判断的定义

**开场先问：「这个标签判错的时候，下游哪个数会错，错多少？」**

答得出来，这个标签值得标。答不出来，它会安静地变成一个维度——而维度会进指标，指标会进结论。

打标层是数据产品里**唯一一层衡量标准本身就是推断出来的**。采集错了能看到空值，指标错了能对账，分析错了区间会变宽。打标错了：**准确率这个数字本身也可能是错的**，而它看上去像一把尺子。

## 这一层最容易死的地方

一个情感标签，七类，准确率 0.91。看起来可以用了。

但金标准集里 **88% 是正面**。所以一个把所有帖子都判成正面的模型，准确率也是 88%——它什么都没学到，而 0.91 比 88% 只高三个点。

这三个点里还有一个问题：**Kappa 可能是 0.2**。意思是「比瞎猜好一点」，而 0.91 那个数字让人以为已经在用了。

这不是算错，是**准确率在没有类别平衡的情况下不测技能**。所以这一层的第一条纪律：

> **准确率必须和类别分布一起读。单独一个准确率是分布的形状，不是模型的能力。**

`label-audit.mjs` 会同时给出 Kappa 和类别分布，并把「多数类基线」印出来——**如果一个数不比「永远答最常见的那类」高多少，它测的是数据，不是标注。**

## 五个问题，一份体系

一问一答，答案落进 `work/labels/<dimension>.md`。前两问定「这个标签是什么」，后三问定「它什么时候骗你」。

先给推荐答案，让他同意或纠正。

| 问题 | 定的是什么 | 什么时候问 |
| --- | --- | --- |
| 1. 这个标签判的是什么判断？ | 定义 + 边界 | 总是 |
| 2. 什么情况算「不适用」？ | 第四值 | 总是 |
| 3. 置信度是什么意思？ | 置信度口径 | 总是 |
| 4. 两个人标同一批会不会一致？ | 金标准集 + Kappa | 总是 |
| 5. 改标签的时候旧数据怎么办？ | 版本策略 | 改一次问一次 |

## 问题 1 — 这个标签判的是什么判断？

**推荐答案先给：用一句话说出「一个人在看着一条内容时，脑子里做的那个判断」。**

不是分类边界，是那个判断本身。

- 差：「情感极性」——这是标签名，不是判断
- 好：「这条内容在说这个产品好，还是在说它不好」——这是一个人做的判断

**然后必须给三类例子，一类一个：**

| 类型 | 作用 | 例子 |
| --- | --- | --- |
| **典型正例** | 说明它判什么 | 「用了三个月没漏，值」 |
| **典型反例** | 说明它不判什么 | 「还没收到，等到了再说」——这是未收到，不是中立 |
| **边界例** | 说明最难的那条线在哪 | 「用了三个月没漏，但是我朋友说漏了」——混合，不是正面 |

**边界例是唯一有价值的那一条。** 写不出边界例，说明这个标签的定义还没做完——你会有一个能标 80% 的标签，和 20% 全靠猜的部分，而那 20% 里集中了所有真正有趣的帖子。

判据：**把这个边界例拿给第二个人看，他和你判成同一类吗？** 不一致，定义还没定完，去改定义，别去改标注员。

## 问题 2 — 什么情况算「不适用」？

**这一问没有「不适用很少」。** 每个标签都有一批内容它判不了，区别只在于你有没有给它一个位置。

三个现成的选项，让他挑：

| 处理 | 什么时候用 | 后果 |
| --- | --- | --- |
| **加一个 `n/a` 值** | 这类内容在分母里会污染指标 | 分母变小，但那部分可见 |
| **并进已有的一类** | 这类内容与某一类在决策上无差别 | 分母完整，但该类被稀释 |
| **排除整条记录** | 这类内容根本不属于这个维度 | 覆盖率下降，要单独统计 |

**默认推荐第三个，并单独统计覆盖率。** 因为前两个都会让一个看不见的东西进分母。

对照的是区域归属那四值命名空间的教训：`insufficient`（没线索）和 `unattributable`（线索冲突）处置相同、成因相反，合成一类就再也分不清「算法不行」还是「内容真没线索」。标签层的 `n/a` 同理：**「这条内容不涉及这个维度」和「这条内容涉及但我判不了」必须是两个值**，否则你无法回答「我的打标覆盖率是多少」。

判据：**说得出一个具体的帖子，它落在这个值上。** 说不出，这个值不成立。

## 问题 3 — 置信度是什么意思？

**推荐答案先给：它是这一条判断的可信程度，而不是这一类的可信程度。**

三件必须钉死的事：

**一、它是逐条的还是逐类的。** 「模型对这个标签的置信度是 0.8」是类的；「这一条是 0.83」是条的。只有逐条的置信度才能做敏感性分析——而敏感性分析是判断「结论稳不稳」的唯一手段。

**二、它是不是校准过。** 说 0.8 的那些，真的对了 80% 吗？**没校准的置信度只能排序，不能当概率用。** 排序已经够用了（取前 30% 做敏感性分析），但如果有人拿它当「80% 正确率」引用，那是错的。

**三、它能不能是反的。** 这是最隐蔽的一种：**高置信度那一档的准确率比低置信度那一档低。**

后果很具体：所有「只用 >0.8 的数据」的规则都反了，而每一条规则单独看都合理。

`label-audit.mjs` 会按三档（<0.6 / 0.6–0.8 / >0.8）分别算准确率，高的一档更差就判失败。这条检查存在的理由就是它**不可能靠看总数发现**——总准确率 0.76、Kappa 0.52 的时候，高置信度那一档只有 0.44。

判据：**分档算一遍，高的必须比低的高。** 不满足就先别用置信度做任何筛选。

## 问题 4 — 两个人标同一批会不会一致？

**推荐答案先给：不是「会不会一致」，是「不一致时该改定义还是改人」。**

三个数字，用途不同：

| 数字 | 回答什么 | 门槛 |
| --- | --- | --- |
| **准确率** | 模型对不对 | ≥ 0.7，否则该维度不可用 |
| **Kappa** | 比瞎猜好多少 | ≥ 0.6，否则定义有歧义 |
| **分档准确率** | 置信度是不是正的 | 高的必须比低的高 |

**Kappa 低于 0.6 时，问题在定义，不在标注员。** 这是最容易被搞反的一件事：两个人不一致，第一反应是「培训一下」，实际是标签边界没定死——培训只会让两个人一起错得更一致。

**金标准集必须是人工标的，而且不能由做模型的人标。** 理由不是道德，是可比性：自己标的人会不自觉地按模型的方式理解边界，那个集合就不再是尺子，而是模型的复印件。

规模：**每个标签 200–300 条**。低于 30 条 `label-audit` 会判「无法判断」——三十条上算出的两位小数是噪音。

判据：**两个人工标同一批 200 条，Kappa ≥ 0.6 之后再去测模型。** 人不一致的标签，模型没法被公平评价。

## 问题 5 — 改标签的时候旧数据怎么办？

**推荐答案：旧数据不重写，新数据带新版本，查询时要么按版本分组、要么显式映射。**

改标签有三种情况，动作不同：

| 改什么 | 动作 | 旧数据 |
| --- | --- | --- |
| 拆分类（一类拆成两类） | 版本 +1，写**显式映射表** | 不重写；查询时映射或不映射，两种都要能选 |
| 合并类（两类并成一类） | 版本 +1，映射表 + 保留原始类 | 不重写 |
| 改边界（同一类判得更严） | 版本 +1，**新旧并行跑一个周期**对比 | 不重写 |

**「不静默合并」是这一层的核心纪律。** 一个拆开的标签，如果查询时悄悄按新体系合并，去年 52 周的数据会在某一点出现台阶——而那个台阶会和真实的市场变化混在一起，事后分不开。

判据：**说得出「v2 到 v3 改了什么、旧数据怎么映射」。** 说不出来，等于改的时候没有留痕。

## 检查器管什么，你管什么

```bash
node scripts/label-audit.mjs gold.csv        # 准确率、Kappa、分档准确率、类别分布
node scripts/label-audit.mjs --demo          # 三种错同时出现的样子
node --test scripts/label-audit.test.mjs
```

输入是 `id,gold,predicted,confidence` 四列。

| 它**能**判 | 它**判不了** |
| --- | --- |
| 准确率、Kappa 有没有过门槛 | 标签定义有没有歧义（只能事后从 Kappa 反推） |
| 置信度是不是反的 | 置信度有没有校准 |
| 金标准集够不够大、是不是只有一类 | 金标准集是不是同一个人标的 |
| 多数类基线（准确率要跟它比） | 边界例写得对不对 |
| 数据格式错（置信度不是 0–1） | 版本映射表准不准 |

**实测过一条**：240 行的 demo 里，准确率 **75.8% 过了 0.7 的门槛**，Kappa **0.515 没过**，高置信度那一档准确率只有 **43.6%**（低置信度那档 84.4%）。
所以「准确率达标」这一条本身可以是真的，而这一层依然不能用。**门槛是三个，不是两个。**

## 这个层怎么假装成功

**把准确率当结论。** 0.91，看起来很好，而多数类基线是 0.88。判据：跟基线比过了吗，Kappa 是多少。

**Kappa 低就培训标注员。** 两个人不一致通常是定义有歧义。判据：把不一致的那几条拿出来，能不能说清「这条为什么该判 A」而不用「我觉得」。

**置信度没人验。** 分档算一遍才发现高的一档最差。判据：高的比低的高吗。

**金标准集自己标。** 做模型的人标金标准，等于让模型给自己出题。判据：标金标准的人碰过模型吗。

**改标签时「顺手统一了旧数据」。** 最省事的做法，也是最贵的：台阶从此和业务变化分不开。判据：旧数据被重写了吗。

## 和 8+3 其他层的接口

打标层在中间，两边各有一处不明显的约束：

- **上游（存储 → 打标）**：每条标注要带 `taxonomy_version`。缺了它，跨期比较里「标签改了」和「市场变了」分不开。`collect-store.mjs` 会拒绝没有版本字段的记录。
- **下游（打标 → 指标）**：读到的 `taxonomy_version` 不等于指标卡声明的版本时，**报警，不许猜**。这是 `metric-card` 的「口径版本」与这里的「标签版本」必须分开记的原因——它们各自会变，变的时间点不同。
- **一处反向耦合**：打标结果会反过来影响区域归属。一条被标为「抱怨物流」的帖子，大概率提到本地物流商——那是区域线索。所以不能「先归属再打标」，至少跑两轮：粗归属 → 打标 → 用本地化线索修正归属。

## 退出条件

**两个人工标同一批 200 条，Kappa ≥ 0.6；然后模型在这批上的准确率 ≥ 0.7，且高置信度那档比低置信度那档准。**

三个条件都要，因为它们是三件不同的事：人能不能一致（定义清不清楚）、模型对不对（能不能用）、置信度有没有方向（能不能拿它做筛选）。

任何一项不过：**说清是哪一项不过，以及它对应的动作**——第一项改定义，第二项换模型或降级，第三项别用置信度做筛选。三者的动作完全不同，混成一句「打标效果不好」等于什么都没说。

## 落盘

```bash
mkdir -p work/labels
$EDITOR work/labels/sentiment.md
node scripts/label-audit.mjs work/labels/sentiment-gold.csv
```

体系落在 `work/labels/`，和指标卡同级的理由：它也是**会长期存在、会被改版、会并存多个版本**的定义，不是一个阶段的产出。它不进 `work/designs/`——设计记录是四问一次就完的对话落盘。

文件形状：

```
## 一、判的是什么判断
## 二、什么情况算不适用
## 三、置信度是什么意思
## 四、人和人一致吗
## 五、改版怎么改
## 版本记录
| 版本 | 什么时候 | 改了什么 | 旧数据怎么映射 |
```

`work check` 目前不校验这个目录——**这是已知缺口**，记在 `docs/product/data-product-layers.md` §五。
