02设计

定下那些「以后很难改」的东西：接口契约、数据形状、模块边界、权限模型，以及为什么这样选。

方法论未覆盖　这一步在 ANB 里是空的：ANB 从「想法」直接跳到「能跑」。这是它的一个真实缺口。

为什么这一步重要：设计阶段的错误不会立刻显现，它会以"后面每改一次都很痛"的形式慢慢出现。ADR 存在的意义就是让三个月后的你能看懂当时的取舍。

什么情况走哪条路

按代价排序，不按发生概率。先做便宜且能推翻结论的。点击跳到对应处理。

如果去为什么
这是一个会长期演进的产品，不是一次性脚本b-adr难回退的选择必须写 ADR，含放弃的选项和代价。
有两个方案都合理，选不出来b-tie不要随机选。写 ADR 记录取舍，把决定权和理由一起留下。
你在改一个已有的系统b-existing先理解现状，再动。
只有一个用户、只跑一次b-skip可以跳过设计，但要写下"我跳过了，因为…"。

写 ADR，含放弃的选项

ADR 的价值不在于记录你选了什么，在于记录你放弃了什么，以及为什么。没有放弃选项的 ADR 是一份宣布，不是一份决策。

每条 ADR 至少要有：背景、考虑过的选项、决定、代价、什么情况下该重议。

两个方案都合理时

这是最容易犯错的位置：随手选一个，然后在实现时才发现不合适，于是用补丁掩盖，最后没人记得为什么是这样。

怎么改：写 ADR，把两个方案各自"什么时候会赢"写清楚。如果实在分不出来，选更容易撤销的那个。

改已有系统之前

先理解现在的形状。不是读代码，是问：这个东西现在怎么工作、谁在用、哪部分改动会伤到人。

不做这一步的典型后果：改了一处，另一处坏了，而你不知道它们连着。

可以跳过，但要写下来

一次性脚本、只给自己用的工具，不需要完整设计。

但必须写下"我跳过了设计，因为 X"。因为三个月后你会把它当正式项目维护，那时候没有人知道当初为什么没有 ADR。

谁来验，怎么验

每一行都是一个你能亲手做的动作。做不了就记成未通过，写明缺什么，不要用近似动作代替。

动作通过标准
一个没参与讨论的工程师能只读这些文件就开始实现读 ADR + schema + 接口定义，不需要问人
每个难回退的选择都有一条记录包括"我们决定不做 X"这种反向决策
术语表里每个词只有一个意思同一个词在两个地方定义 = 迟早对不上

这一步用到哪些 skill

  • architecture-decision-records — 难回退的选择写成 ADR，含放弃的选项和代价。
  • domain-modeling — 术语定死，写进 GLOSSARY。
  • codebase-design — 模块边界、接口深浅、seam 位置。
  • spec-driven-development — 把共识固化成可验收的规格。
  • to-spec — 对话已透时直接固化，不再采访。
  • writing-plans — 把 spec 变成别人能执行的步骤。
  • to-tickets — 拆成 tracer-bullet 纵向切片，标阻塞关系。
  • api-and-interface-design — 契约先行、错误语义、分页、幂等。
  • database-schema-designer — 表结构、约束、索引、可回滚迁移。
  • auth-implementation-patterns — session/JWT/OAuth 选型、租户隔离。
