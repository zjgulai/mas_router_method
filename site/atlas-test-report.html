七个问句，漏了一整类

失败图鉴里那七个问句，我拿一个刚做完的小工具逐条试了一遍。 机制层面它们全过了：31 个测试、全部保护机制可验证、假数据不比真数据宽松。 但这个工具在真实网页上产出的摘要基本不可用，而七个问句里没有一条能发现它。

结论

七个问句回答的是同一个问题：「这个机制的证据可信吗」。它们能抓出四类假信号，因为它们本身就是针对假信号设计的。

但它们完全回答不了另一个问题：「这个东西做出来的结果，好用吗」。这两件事之间没有自动联系——一个机制完全可信的工具，可以稳定地输出垃圾。

7问句里能发现「产出质量」问题的
31通过的测试数，全部关于机制
3真实网站里，3 个摘要都不可用
1我的测试自身写错、被误判为代码错的次数

逐条结果

每一条我都真的做了动作，不是判断「应该会过」。结果分成：通过、有缺口、失败。

1

上次有检查失败是什么时候？给我看那次记录

通过

建的过程中确实红过：truncate 在 cap 小于标记长度时会超限。我把它改回去再跑，测试立刻红。

故意改坏后：
30/31 checks passed
FAIL [limits.test.js] truncate never returns more than the cap
     cap 0: got 12 chars

这条问句有效，而且是我建的过程中唯一主动发现的机制 bug。

2

这次结果里跳过了几条？为什么跳过？

有缺口

工具报「31/31 通过」，没有跳过。但追问下去发现：这套测试根本没有「跳过」这个概念。

这意味着这条问句只能用于「已经有了跳过机制」的系统。如果 agent 从一开始就没实现跳过，你问它「跳过了几条」，它会答「零」——一个听起来很好、实际毫无信息的答案。问句需要改：不是问跳过了几条，是问「你这套检查一共能得出几种结果」。
3

把密钥改错／断网，再跑一次

通过

断网后报的是「无法判断」，退出码 1，而且这次失败也被写进了日志：

Could not make a digest: Could not fetch no-such-domain...: fetch failed
exit code = 1

这条问句在一个小工具上就能用，不需要专业知识。它的价值是被低估的——它同时验了三件事：错误可见、退出码正确、失败被记录。

4

这个测试用的是真数据还是假数据？

通过

假的是网络层。我验证了假网络也遵守真实的大小上限：

假 fetch + 真实限制 -> bytes: 1000  truncated: true  html.len: 1000
和真实路径一致吗？ YES

这条问句的价值在于它逼出一个具体检查：假的那一层，会不会让真实的规则失效。这是第二类事故（测的不是你的产品）的唯一抓手。

5

成本上限上次拦住是什么时候？

通过

这个工具不调模型，没有成本。但同类的保护（响应大小上限）能拿到拦截证据：

拦截证据: bytes=500  truncated=true

这条问句的措辞需要改：不该只问成本。任何「有上限的东西」都适用——请求大小、重试次数、并发数、文件个数。问题是「上次拦住是什么时候」，不是「成本」。

6

同一条规则在几个地方各写了一遍？

通过

把所有限制集中到一个文件，然后搜硬编码数字：

grep 2000|10000|2000000|5000 在 src/ 下（排除 limits.js）：
（空 —— 没有第二处）

这条问句有效且便宜。它的做法（把所有限制放一处，然后搜重复）是可以机械执行的，不需要判断力。

7

做三次，历史里有几条？

通过

3 次成功 + 3 次尝试（2 次失败），日志 6 条，一条不少，失败的也在里面。

1. succeeded  https://example.com
2. succeeded  https://example.com
3. succeeded  https://example.com
4. failed     not a url
5. failed     https://no-such-xyz-123.invalid
6. succeeded  https://text.npr.org/

这条最好用：不需要任何解释，做一个数一个就行。而且它对「静默丢记录」这一类问题是最直接的探测。

七个问句漏掉的那一类

31 个测试全绿，产品仍然是坏的

我拿三个真实网站试了。维基百科的「Coffee」页面，摘要第一条是：

Coffee - Wikipedia Jump to content Main menu Main menu move to sidebar hide
Navigation Main page Contents Current events Random article About Wikipedia Contact us
Contribute Help Learn to edit Community portal Recent changes Upload file Special pages
Search Search Appearance Donate Create account Log in Personal tools ... 210 languages
Afrikaans Alemannisch አማርኛ Aragonés Ænglisc Obolo ...

后面还有原样未解析的维基模板代码（<ref name="ukers">{{Cite book...}}）。NPR 的首页摘要则是一整段头条标题串在一起。

这不是机制问题。所有保护机制都工作正常，测试全绿，日志完整。是产出质量本身不成立。而七个问句全部通过了，因为它们问的都是「证据可不可信」，没有一条问「结果能不能用」。

要补的不是第八个问句，是另一类问题

我原本想说「加一条就够」，但试下来发现加一条不够——这是一个独立维度，需要一组。它们和原有的七条性质不同：原来七条验的是可信度，新的这组验的是可用度。

  1. 给我看三个真实输入的输出。不是它挑的样例，是你随手找的。三个都要看，因为第一个可能是特判的。
  2. 这个输出你会拿给客户看吗？如果不会，差在哪一步？这个问题逼出一个具体位置，而不是「整体不够好」。
  3. 有没有一条检查是关于「结果对不对」的？还是全都是关于「程序有没有崩」？大多数项目在这一步会发现：全部是后者。这就是我这次的发现。
  4. 最差的那种输入，会发生什么？不是最难的，是最常见的——真实世界里最多的那种页面，通常是最脏的那种。

补上这四条之后，手册的结构会变成两半：「四类假信号」管可信度，「四条质量问句」管可用度。前者能防止你被误导，后者能防止你做出一个诚实但没用的东西。

还有一个发现：我的测试自己也错过

这件事对手册的意义，比工具本身的 bug 更大。

写完第一轮测试，跑出来 3 条失败。我逐条查了：三条全部是我的测试写错了，不是代码错了。

测试说实际为什么会错
导航词混进了摘要代码对，是我的输入构造方式不对我以为「Home 后面接正文」是两句话，实际没有句号，合成了一句
阈值判断差一代码对，是我算错了字符数我把「长度 ≥ 30」和「30 个字符加句号」搞混了
排序不符合预期代码对，是我写的预期顺序错了我以为同分按字母序，实际代码是按次数降序——代码更合理

这意味着：「测试红了」不等于「产品坏了」，也可能是尺子坏了。而不会写代码的人看到红色的第一反应会是「又出问题了，让 agent 修」——如果 agent 直接去改代码迁就错的测试，测试会变绿而产品会变坏。

所以手册里需要加一条，它属于「怎么读信号」而不是「怎么测」：测试红了，先问「是产品错了还是测试错了」，不要直接让它修。这个判断你自己做不了，但你可以要求 agent 明确回答「我认为是哪一边错了，理由是什么」——如果它答不上来，它就是在猜。

这次实测改变了什么

原本我以为这套手册的核心是「假信号清单 + 七个问句」。实测之后它变成了三块（后来又补了第四块，见页尾）：

  • 四类假信号（不变）——抓可信度问题，仍然有效，其中三条在这次实测里直接起了作用。
  • 四条质量问句（新增）——抓可用度问题。这是原来完全缺失的一整类，也是这次最重要的发现。
  • 一条读信号规则（新增）——测试红了先判断是产品错还是尺子错。没有这条，前面所有准备都会在一次误判里被毁掉。

还有一件事值得记下来：我是在知道图鉴里那几类坑的情况下建这个工具的，仍然踩到了新的一种。这说明手册的价值不在于让人不犯错，而在于让人犯的错有一个名字，因而能被指出来。我这次能发现它，是因为我在写手册；别人发现不了，是因为没人把这件事说破。

实测之后又补的第四块：找不到 ≠ 不存在

这份实测报告写完的同一周，我在清理另一个任务的文档时犯了第七种错误：看到目录里少了 42 个工具，就写下「它们根本不存在」，还配了一段听起来很有说服力的推理。

实际上它们全部存在，只是由别处提供、调用要带前缀。而我在同一周里已经成功调用过其中一个，却从没把这个矛盾跟当时的结论对上。

它和前面几类的区别：前面那些是系统给了你一个假信号；这一种是系统什么都没给，而你把空白填成了结论。防法也不同——前者要识破，这一种要忍住不填。
