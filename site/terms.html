这些词它在说什么
坏了会怎样

你不写代码，但你要读它给你的报告、要判断它说的「做好了」是不是真的。 所以每个词给你三栏：它指的是什么、这个词相关的环节坏掉时你会看到什么、你怎么一眼看出来。 第三栏才是你真正要用的。

怎么用

不用背。你在它的话里看到一个不认识的词，回来查一次；查三次之后就不需要再查了。

先看第二栏。如果那个「坏了会怎样」的场景你听着耳熟，直接看第三栏的动作——比理解这个词本身有用得多。

判断标准：一个词如果你只知道意思、不知道它坏了是什么样，那你还是不能用它做判断。这一页就是为了补后面那一半。
一

它说「做完了」时用的词

这一组是你最常遇到的，也是最容易被糊弄的一组。

跑通it runs

它在说什么
程序从头到尾执行了一遍，没有中途崩掉。仅此而已——它不代表结果是对的、有用的、或者是你想要的。
坏了会怎样
最常见的坏法不是崩，是跑通了但跑的是假的：界面能用、按钮有反应，背后是准备好的样例数据。你以为通了，实际只通了外壳。这次实测里我就见过：31 个检查全过，第一次真实运行必失败。
你怎么一眼看出来
问一句「用的是真数据还是假数据」。然后自己随手找一个输入给它，不要用它给的样例。换第二个说不上来的输入再试一次——第一个可能是特判的。

测试通过tests passing

它在说什么
事先写好的一批自动检查都过了。它证明的是「在你测的那些情况里它没出错」，不证明「它在别的情况下也不会出错」，更不证明「它做出来的东西好用」。
坏了会怎样
三种假的通过：检查程序自己出错时记成通过；该检查的部分没实现，记成「跳过」而跳过算通过；检查写好了但没接进最终判定，等于不存在。三种都让报告显示全绿。
你怎么一眼看出来
问两个问题：「这次有几条跳过了，为什么」和「上次有检查失败是什么时候，给我看那次记录」。一条从没失败过的检查，很可能不是检查。

完成done

它在说什么
它认为这件事达到它理解的目标了。而「它理解的目标」和你想要的经常不是一回事——尤其是你只说了功能没说用途的时候。
坏了会怎样
你会收到一份看起来完整的交付，做的是它猜的那个目标。而「猜错方向」比「没做完」更难发现，因为它有产出，你会倾向于接受它。
你怎么一眼看出来
问「用什么动作能证明它完成了」。如果答案是「看代码」「应该没问题」「测试过了」，那不算——必须是一个你能亲手做的动作。
二

它说「花了多少钱」时的词

做 AI 产品和做别的产品最大的不同：每次运行都在花钱。所以这一组你必须能看懂。

Tokentoken

它在说什么
模型按「块」算钱和算容量，一块就是一小段文字（大致是一个词或半个词）。中文一个字大约 1–2 块，英文一个词大约 1 块多。你输入的和它输出的都要算。
坏了会怎样
真正的坑不是贵，是看不见：你让它记住一整份长文档，之后每问一次都要把那份文档重新算一遍钱。用久了成本会自己胀上去，而单次看每次都「不贵」。
你怎么一眼看出来
问「这次用掉多少，其中多少是我贴进去的内容，多少是它自己说的话」。如果它答不上这两个数的区别，它就没在记。

成本上限budget / max cost

它在说什么
一次运行最多花多少，超了就停。这是唯一能防止「一晚上跑掉一个月的钱」的东西。
坏了会怎样
最常见的是上限设了但从不触发：代码在那儿，注释还写着「没有它就会超支」，但检查的那个数字只在结束时才有值，条件永远不成立。这次实测里就有一个这样的，至今没修。
你怎么一眼看出来
不要问「有没有上限」，问「它上次拦住是什么时候，给我看那次记录」。拿不出证据，就当它不存在。同一个问法适用于任何「有上限的东西」：重试次数、请求大小、并发数。

上下文窗口context window

它在说什么
模型一次能「同时看见」的内容总量有上限。超出就得丢掉一些——丢什么由程序决定，不由你决定。
坏了会怎样
聊到很长之后，它开始忘记前面的约定、重复问已经回答过的事、或者忘掉你给过的限制。你以为是它变笨了，其实是你要它记住的东西被挤出去了。
你怎么一眼看出来
让它忽然复述一条很早之前给过它的限制（比如「我说过不能提什么」）。它复述不出来，就是被挤掉了。这时候该做的不是重说一遍，是把那条限制写进「永远不许丢」的地方。
三

它说「我改好了」时的词

这一组最危险，因为改动本身看不出来，只有后果能看出来。

提示词 / 系统提示prompt / system prompt

它在说什么
你（或者它）写给模型的那段长期指令：你是谁、怎么做事、不许做什么。它不是代码，改一个字行为就可能变。
坏了会怎样
改提示词是最容易的改动，所以会被用来解决一切问题——包括那些其实应该改代码的问题。改完「感觉好点了」，但没有测量，你无法知道它是不是在别处变差了。
你怎么一眼看出来
问「这次改的是提示词还是代码，为什么是这一边」。如果每次出问题它都改提示词，说明它没有别的办法——那说明缺的是机制，不是措辞。

回归regression

它在说什么
原本好的东西被改坏了。它和「没做好」不同：回归是「以前能用的现在不能用了」。
坏了会怎样
没有留存旧结果，就永远发现不了回归。你会一直以为产品在变好，直到某个客户告诉你三个月前那个功能不能用了。
你怎么一眼看出来
问「改之前的结果还留着吗，能拿来对比吗」。留不下来，就没有回归这个概念——只能说「这次看起来还行」。

把坏的当成好的false positive

它在说什么
检查报「通过」，实际是坏的。这是这套方法里反复出现的假信号的共同形状，也是对你伤害最大的一种错误。
坏了会怎样
你会带着一个坏产品往前走，而且每一步都在它上面加东西。发现得越晚，返工越贵。比这更糟的是：你会因为「一直很顺」而对它产生信任，之后连怀疑都不会有了。
你怎么一眼看出来
这一页的第三栏全部是为这个准备的。最通用的一招：想办法让它失败一次，看它会不会告诉你。不会告诉你的，就是假的。
四

它说「接好了」时的词

这一组关系到「别人能不能用上」。

接口 / APIAPI

它在说什么
两个程序之间说话的约定：你给我什么、我还你什么。说「接好了接口」的意思是「两个程序能互相说话了」，不代表说对了话。
坏了会怎样
能连上但内容对不上——比如对方给的是「元」，你当成「分」；对方偶尔返回空，你没处理，于是页面空白。这类错误不会报错，只会产出错的东西。
你怎么一眼看出来
问「如果对方返回空，会发生什么」加上「如果我故意传一个错的值，会发生什么」。这两个都是「不该发生」的情况，而真实世界里最常见的就是它们。

密钥 / 环境变量API key / env var

它在说什么
那些不能写进代码里的密码（访问别家服务的凭证）。通常放在一个配置文件里，程序启动时读进来。
坏了会怎样
两个方向都坏：泄露（被写进代码提交出去，任何人都能用你的账号花钱）或者缺失（在你电脑上配好了，别人那里没有，于是别人一用就崩）。
你怎么一眼看出来
问「这个密钥在几个地方能读到」和「别人拿到这个项目，需要自己做哪几步才能跑起来」。后一个问题的答案就是「交付需要补的洞」。

部署 / 上线deploy

它在说什么
把它从「你的电脑上能跑」变成「一个地址，谁都能打开」。
坏了会怎样
最常见的是「本地能跑」被说成「可以用了」。区别在于：密钥、域名、权限、数据这四件事在你电脑上全都是配好的，在别人那里全都是缺的。
你怎么一眼看出来
用手机打开那个地址。打得开，才算部署了。打不开，前面做的一切都还没交付。
五

它说「有记录」时的词

这一组决定「出事时你能不能查」。写得少，但缺了就很难补。

日志log

它在说什么
程序自己记下的流水账：什么时候发生了什么。
坏了会怎样
三种：只记成功不记失败（于是你永远不知道失败多少次）；记了但丢了（内容太长存不进去，而错误被吞掉，你看到的是「成功」）；记的全是技术细节（你要的三个数字一个都找不到）。
你怎么一眼看出来
做三次，去历史里数几条。做 N 次数 N 条就对了。再故意弄坏一次，看那次失败在不在里面。

超时timeout

它在说什么
等一个操作最多等多久，超过就放弃。没有超时的程序会无限等下去，看起来像「卡住了」。
坏了会怎样
设得太长，用户体验是「点了没反应」；设了但没处理失败，超时之后程序继续用一个空结果往下走，产出错的东西而你不知道。
你怎么一眼看出来
问「超时之后会发生什么」。正确回答是「告诉用户失败了」；如果回答是「继续」或者「重试」，追问「重试几次，几次之后放弃」。

这一页真正的用法

你不该把这一页当词典读。它是一份提问脚本——每个词的第三栏，都是你在那个时刻应该问它的一句话。

词会变。模型换代、工具换名、框架换掉，这些词两三年就会换一批。但第三栏那个结构不会变：任何自动化的东西，你都要能自己想办法让它失败一次，并且它必须告诉你。

记住这一条，这一页剩下的内容都可以忘。
