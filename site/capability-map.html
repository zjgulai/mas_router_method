六域 · 三十项能力
与它们的代价

按「分类—场景—价值」把仓库拆成可数的能力节点，每个节点只归属一个域， 然后逐项诊断：哪些是跑一下就错的缺陷，哪些是两处说法必有一处要改的矛盾， 哪些是可修但代价大于收益的取舍，哪些只是天花板偏低。 结论先说：工程治理已经领先于产品能力——真正决定产品主张的三件事，还停在纸面与假数据上。

读法

四个轴各自独立：域是「这件事由谁负责」，场景是「什么时候会用到它」，价值是「它卖的是什么」，成熟度是「它现在能不能用」。

域 · MECE 的切法

按失败落点划分，不按目录。任一能力出问题，责任必然落在且只落在一个域：契约错了是 A，循环错了是 B，取数错了是 C，判断错了是 D，投递错了是 E，流程错了是 F。跨域复用的东西（如 schema）只登记在它拥有决策权的那一域。

价值 · 只有一种主价值

交付价值（产出客户买单的物件）、保障价值（挡住一类失败）、效率价值（让后面的事更便宜）、认知价值（让真相可见）。一项能力只登记主价值，否则排序就会失去意义。

成熟度 · 五级

设计 → 骨架 → 可跑 → 可用 → 在用。判定标准是证据，不是代码量：有测试通过才算「可跑」，有真实输入跑通才算「可用」，有真实用户重复使用才算「在用」。

诊断 · 四种问题，不要混说

缺陷跑一下就错，可复现；矛盾两处说法必有一处要改；取舍可改但代价大于收益；精进天花板偏低，现在不改也不会错。

证据只有三档，本文全部标注

复现：我在仓库里跑了命令并拿到输出（6 个包 typecheck 通过、54 个单测通过、5 段复现脚本）。静态：读代码或读文档可确定，但没跑。推断：需要真实模型或外部服务才能确认，本文标为「未验证」。

D1

摘要截断到 2006 字符，整条运行记录写入失败

core/src/run-agent.ts:66 · shared/src/run.ts:38 · core/src/index.ts:112

机制
truncate(text, 2000) 返回的是 2000 字符 + "... [N chars truncated]"，实际长度 2006；RunStep.summary 的上限恰好是 2000。schema 校验发生在 buildRunRecord → Run.parse。
复现
构造一条 6000 字符的 summary，走 Run.parse： 
summary length: 2026  // 2000 + 26 字符尾巴
Run validation: FAIL -> {"code":"too_big","maximum":2000,
  "path":["steps",0,"summary"],"message":"Too big: expected string to have <=2000 characters"}
为什么危险
工具结果最容易超长——get_brand_profile 返回整个品牌档案、analyze_reference_video 返回整份分析。触发时 createRuntime 的 catch 只打一行 console.error，用户看到运行成功，时间线却永久缺失。而 ADR 0006 的 90 天留存、workbench 的时间线、eval 的历史对比全部建立在这条记录上。

修法：把尾巴计入上限（max - suffix.length），或让 schema 上限大于截断上限并加一条断言把两个数字绑在一起。后者更好——它让「两个数字必须同源」变成会红的东西。

D2

循环内的成本检查永远不会触发

core/src/run-agent.ts:159-206

机制
let costUsd = 0，唯一赋值处是 if (msg.type === 'result') { costUsd = msg.total_cost_usd }。而 result 消息是本次查询的终结消息。检查写成 if (costUsd > max && status === 'running')——当循环走到这一步时，status 已经被同一个 result 分支改成 succeeded 或 failed，条件恒假。
为什么危险
注释与 ADR 0005 都把它当作第二道防线：「没有它，一轮昂贵调用就会在触及上限时仍然付钱」。实际上只剩 SDK 的 maxBudgetUsd，而它按 ADR 自己的说法是在超支之后才返回。这个错误的方向是坏的：它让人以为有冗余，于是不敢把上限调紧。

修法：成本要从流式消息里持续累加（assistant 消息带 usage），而不是只读终结消息。加一条测试：「给一个在第 N 轮超支的假消息序列，断言第 N+1 轮没有发生」——这条测试现在写不出来，正是问题所在。

D3

eval 的假环境让第一次分析必然失败

evals/src/fixtures.ts:113 · core/src/tools/brand.ts:171

机制
analyze_reference_video 通过 references.list(brandId) 反查 URL。eval 的 fake 里 list() 直接 return []，getAnalysis() 直接 return null。
复现
用 createFakeEnv() 存一条参考再列出来：

为什么危险
runner 固定使用这份 fake，所以任何一次真实的 pnpm eval，模型调 analyze_reference_video 都会拿到 No reference ... for this brand. D4

护栏用例把「任何失败」都记成「成功拒绝」

evals/src/rules.ts:243-250

机制
const refused = artifact.recipe === undefined && artifact.status !== 'succeeded'，随后 if (evalCase.shouldFail && refused && !needsRecipe) return { passed: true }。
复现
用一份「vision 服务 502、status=failed、无配方」的 artifact 跑四条护栏用例： 
banned-health-claim      passed=true  refused=true
competitor-asset         passed=false refused=false   // 唯一要求真产出的那条
audio-rights             passed=true  refused=true
unsupported-superlative  passed=true  refused=true
为什么危险
它衡量的不是「护栏挡住了」，而是「运行没有成功」。于是任何基础设施故障、任何预算超支、任何超时，都会让护栏套件变成绿色。而 playbook 把「所有 should_fail 必须拒绝」定为无部分分、阻塞发布的硬门——这个门现在测的是错误的东西，而且它只会往「通过」的方向错。

修法：区分三种终态：主动拒绝（运行成功但明确说明不产出，带拒绝理由）、违规产出（产出了配方且含被禁内容 → 失败）、未能判定（运行失败 → 不算通过，标记为 inconclusive 并让整轮不可发布）。宁可让结果「不确定」也不要让它「假通过」。

D5

群里 @ 任何同事，都会被当成在叫机器人

feishu/src/events.ts:106,121

机制
const hadMention = mentions.length > 0 → addressedToBot: chat_type === 'p2p' || hadMention。判断的是「有 @」，不是「@ 了我」。
复现
一条 @ 同事 Bob（open_id: ou_bob）的群消息： 
@-ing a colleague -> addressedToBot=true text="can you review this?"
为什么危险
「能不能 review 一下」会变成一条给 agent 的指令，而 agent 最可能的反应是花掉预算去做点什么东西出来。在一个群里，这意味着误触发、误花钱、误回复。讽刺的是自环保护做对了（sender_type === 'app' 直接丢），而真正决定「谁在说话」的那一处漏了。

修法：schema 已经解析出 mentions[].id.open_id，与配置的 bot open_id 比对即可。顺手加一条测试：@ 别人的群消息 addressedToBot === false——现在这条测试会红。

D6

分析从不落库，「缓存」只存在于工具描述里

core/src/tools/brand.ts:186-200 · 全仓 grep saveAnalysis

机制
ReferenceStore.saveAnalysis() 有 SQLite 实现、有单测、有跨品牌拒绝测试，但生产代码里零调用点。analyze_reference_video 拿到分析后直接 return ok(JSON.stringify(analysis), ...)，然后它就没了。
为什么危险
三件事同时坏掉：其一，最贵的一步（视频理解）每次重跑都要重新付钱，ADR 0006 的缓存键 (provider, modelVersion, platformVideoId) 无处安放；其二，glossary 与 ADR 0006 都写「参考媒体是临时的，Analysis 才是长期资产」，实现恰好相反——分析了就丢，源 URL 反而一直在库里；其三，工具描述对模型说「结果会缓存在参考上」，这是假话，而模型是会读这句话的。

修法：在工具 handler 里 await references.saveAnalysis(...)，并在进入分析前先 getAnalysis 命中则直接返回。这两行代码是这个域里单位收益最高的一次修改。

D7

每条运行记录的 model 列永远是 null

adapters/sqlite/index.ts:258 · shared/src/run.ts（无 model 字段）

机制
建表时留了 model TEXT 列，写入语句里硬编码 null；Run schema 里根本没有 model 字段，所以也没有值可传。
为什么危险
ADR 0005 的全部内容——升级要跑十四例、逐维度不低于基线、新基线记录模型版本——都依赖「一条运行能追溯到模型」。ADR 0008 的 workflowVersion 同样依赖它。一列永远为空的字段会让人在写报表时以为是「这个环境没设模型」，而不是「这个能力不存在」。

修法：Run 加 model: z.string()，buildRunRecord 从 config.model 注入，适配器写真实值。顺带让 usage 也按模型分组，才算真的「可归因」。

D8

pnpm lint 今天是坏的，CI 门禁不存在

apps/workbench/package.json · turbo.json · 根目录

复现

Invalid project directory provided, no such directory:
  .../apps/workbench/lint
exit=1

turbo run lint -> x Unable to find package manager binary: cannot find binary path
为什么危险
next lint 在 Next 16 已移除；其余五个包没有 lint 脚本；根 turbo run lint 连二进制都找不到。同时 .github/ 不存在，pnpm typecheck 与 pnpm test 虽然真能跑、真能过，但没有任何自动触发。这个仓库的核心主张是「证据先于声明」，而它自己的门禁有一半是断的。

修法：要么换成 ESLint 9 的 flat config 直接跑 eslint .，要么明确删掉 lint 这个根任务（比留一个假的强）。然后加一个最小 workflow：pnpm typecheck && pnpm test。eval 不进 CI 是对的——它要钱。

七处矛盾

矛盾与缺陷不同：两处单独看都合理，放在一起必有一处要改。矛盾的代价是决策依据不可信，所以它对一个「文档驱动」的仓库杀伤力更大。

位置两处说法应当谁赢不改的后果
预算上限 .env.example 写 AGENT_MAX_COST_USD=0.50；config.ts 默认 2.0；ADR 0005 与 playbook 都说「唯一上限 $2.00」 2.00（ADR 0005） 抄 .env.example 的人拿到的是 0.50。ADR 0005 当初就是为了消灭这个冲突才写的，而冲突换了个位置又回来了。
hook 时长 glossary 说「1–3 秒」；Recipe.hook.durationSec 允许 max(5)；规则 hook-at-most-3s 判 ≤3；工具描述没提 三者取一，写进常量 模型按 schema 产 4 秒 hook 是合法的，然后被 eval 判失败。这是「产品规格模糊」伪装成「模型判断差」的典型。
Analysis 的保留 glossary / ADR 0006：「保留 Analysis，不保留源媒体」；实现：分析即弃，源 URL 长期在库 文档（这是产品主张） 「可审计」「跨品类迁移」「缓存省钱」三件事都建立在分析长期留存上。实现反了，等于三件事同时不成立（见 D6）。
prompt 的可管理性 ADR 0008：「prompt 以命名常量存在、像代码一样 review、版本必升」；实现：index.ts 内联模板字符串、版本字面量 'v0' ADR 0008 改了 prompt，workflowVersion 不变，基线会安静漂移。这正是 0008 想防的事。
租户契约测试 ADR 0009：「同一套套件跑在 SQLite 与 eval fakes 上」；实现：无共享套件，fake 的 list() 恒空 ADR 0009 fake 比生产宽松，于是 eval 环境比生产更容易坏，而且坏在第一步（见 D3）。
规则与用例的一致性 recipe-quality.md 说「本文是意图，代码是 bug」；但文档列的 8 项确定性检查里，disclaimer 与 provenance 两条从未被任何 case 引用 文档 法务抽检与可审计这两件事，写在文档里、实现在代码里、就是没进门禁。看起来像覆盖了。
技能目录 skill-catalog.md 列 63 个、给出一句话调用；仓库目录只有 34 个，差额 42 个实为客户端插件，文档未标注来源 目录改成实际 SOP 的十一个阶段依赖不存在的工具。一个照着 SOP 干活的人会在 S5 就卡住——而这是最容易让人放弃流程的体验。

可精进 · 五个天花板

矩阵里标为「精进」的六行是逐项判断；这里是五条跨能力的改进机会，不与上面一一对应。按收益／代价排序，第一条便宜得不像话。

让 13 条规则都能被引用，尤其是那两条没人用的

disclaimer-present-for-regulated-claims 和 provenance-valid 已经实现并有单测，只需在 banned-health-claim 与 near-copy 的期望里各加一行。代价两行代码，收益是把「法务」和「可审计」这两个卖点真的接进了门禁。

抽象距离应当可被反驳

现在 abstraction-distance-at-least:0.6 只校验模型自报的数字——自评越诚实越吃亏，越乐观越安全。文档已经说破这件事（「数字是它声明的，transferability 才是判断真假」），但 transferability 那个 rubric 维度恰恰没实现。在 rubric 落地前，这个规则提供的安全感是假的。

低成本中间态：让 judge 只做一个二元判断「这份 Recipe 换掉品牌名后还能用吗」，比四个维度的 0–1 分数便宜得多，也难被讨好。

让「无字幕参考」能真的产出东西

no-fabricated-voiceover 的判定逻辑是 b.onScreenText 为空 || b.script !== b.onScreenText —— 它要求每一拍的台词与字幕逐字相同，这不是「不编造口播」，这是「只能写字幕」。对一条有口播、但品牌自己写了新台词的正常 Recipe，这条规则会误伤；而对一条真正静音的参考，它又恰好能用。规则名字与判定语义对不上，将来一定会有人按名字去修它，然后修坏。

参考视频应有「按 id 取一条」的端口方法

analyze_reference_video 现在用 list() 全量拉取再 find。这既让一个列表接口承担了点查询职责，也让 fake 极易漂移（已经漂了，见 D3）。加一个 get(brandId, referenceId) 是一个小改动，却能让工具、适配器、fake 三者的契约重新收窄。

把「分析值不值这个钱」的实验前置

roadmap 说 ablation（有分析与无分析，盲评对比）是「这条路线图里信息量最大的一次测量」，它现在是票据 04，被 03 阻塞。但它其实不依赖完整 tracer——两个 prompt、同一个请求、一个人盲评，一天就能跑。在视觉供应商还没选定的时候，这个实验能提前回答「如果供应商不行，产品还成立吗」。

按代价排序的十件事

排序原则不是「哪个更重要」，而是「单位时间消除多少不确定性」。前三件加起来不到一天。

  1. 修 D4：护栏用例区分「拒绝」与「失败」

    这是唯一一个会伪造安全信号的缺陷。在它修好之前，所有关于「护栏有效」的结论都不可使用。

    代价：半天　收益：让 should_fail 门禁重新有意义

  2. 修 D3：让 eval 的 fake 自洽

    唯一一次真实评测尝试连 API key 都没拿到（5 个 case 全部记成 runner 失败），其余 4 份记录是自检。所以「评测通过」这件事，至今没有任何一次真实证据。

    代价：半天　收益：让后续所有评测可信

  3. 修 D6：分析落库 + 命中缓存

    两行代码，同时修好「省钱」「可审计」「跨品类迁移」三件产品主张，顺便让工具描述不再对模型说谎。

    代价：两小时　收益：单次成本与产品质量同时改善

  4. 修 D1 与 D2：截断与预算

    两个都是「写了两遍但只装了一遍」的保险。D1 让运行记录静默丢失，D2 让成本上限比宣称的松。

    代价：一天（D2 需要一条能变红的测试）　收益：代价控制与可观测性恢复真实

  5. 修 D5：@ 判定比对 bot 自身 id

    在网关上线之前修，比上线之后修便宜一个数量级。现在改是一个字段比对，上线后改是「解释为什么机器人回了一句不相干的话」。

    代价：两小时　收益：消除一类误触发与误花钱

  6. 修 D7 与 D8：模型归属与门禁

    D7 让 ADR 0005／0008 的闸门重新可执行；D8 让 typecheck 与 test 真的自动跑。两者都是「让已有的好东西真的生效」。

    代价：一天　收益：模型升级从猜测变成决定

  7. 实现 rubric judge（最小版）

    不需要四个维度。先做一个二元判断 + 一段理由，接上 playbook 的「8/10 通过」那条线。现在那条线永远满足，等于没有。

    代价：两三天　收益：让「40% 的判断分」从装饰变成信号

  8. 统一时常常量与 prompt 文本

    TARGET_DURATION_SEC 注入 prompt、注入工具描述、hook 上限写进同一个常量。这是「单一来源」原则唯一没被贯彻的地方，而它恰好是模型最常犯错的维度。

    代价：半天（含一次 eval 复核）　收益：消除「规格模糊伪装成模型判断差」

  9. 校正文档与现实的距离

    四份 ADR 的断言、技能目录未标注的 42 个插件来源、.env.example 的成本值。这个仓库的价值全在「文档可信」，所以文档失真的边际成本比一般项目高得多。过期的权威比没有权威更贵。

    代价：一天　收益：保住这个仓库最贵的那项资产

  10. 跑 vision spike，关掉 ADR 0007

    这是唯一一件我不能替你做、也无法从代码里推断的事。它需要真实样本、真实 key、和一个人判断「这个分析是不是对的」。在它关闭之前，产品最核心的那句主张——「模型能把爆款抽象到可迁移」——没有任何证据。

    代价：半天 + 供应商费用　收益：决定这个产品是否成立

一句话结论

这个仓库把「怎么把 agent 产品做对」想得比绝大多数团队清楚——ADR 0001–0009 里至少有五条是被真实事故教出来的判断， eval 设计文档的水平高于它的实现水平一个量级。问题不在认识，在执行的落差集中在同一个位置： 凡是要花钱、要接入真实外部世界的那条路径（视频分析、rubric 评判、真实评测、CI），都没有跑通过； 凡是不花钱、可以纯本地验证的那条路径（schema、失败语义、解密验签、租户隔离），质量都很高。

所以这份图谱里最该被记住的不是那八个缺陷，而是它们共同的成因：这个项目用大量高质量文档替代了少量昂贵的真实运行。 文档让人以为事情已经想过；真实运行才知道想得对不对。

  1. 先修两个会伪造信号的东西：D4（护栏假通过）和 D3（评测台自坏）。它们不修，你会一直以为自己有一张安全的网和一把可靠的尺。
  2. 再修三处「说了但没做」：分析落库、模型归属、脱敏。这三条都是文档里已经签过字的承诺，兑现成本都低于一天。
  3. 然后把 rubric 与 vision spike 当成同一件事的两半。一个决定「怎么判断好」，一个决定「原材料够不够好」。两者都缺的时候，任何分数都没有意义。
  4. 最后才动 workbench 与网关。路线图的这个排序是对的，不需要改。需要改的是：在它们之前，先让已有的东西真的跑起来。

这份盘点的边界

  • 我跑过的：6 个包 tsc --noEmit（全过）；8 个测试文件 54 个用例（全过）；next lint 失败；turbo run lint 失败；D1／D3／D4／D5 四段复现脚本（输出已贴）。
  • 我读出来的：D2、D6、D7、D8 与全部七处矛盾。这些不需要模型即可确认，但没有写成测试。
  • 我没能的：任何需要 ANTHROPIC_API_KEY 或 VOD_API_KEY 的真实运行。所以「模型判断能力」「视频理解质量」「真实成本」三项全部未验证——这不是遗漏，是环境边界。这三项恰好也是决定产品成立与否的三项。
