# 阶段 3：什么算好

## 判断标准（先写，后改产品）

七条。每条都能自动跑。**A 组测「机制可信」，B 组测「结果对不对」——上次实验缺的就是 B 组。**

| # | 组 | 标准 | 凭什么这么定 |
|---|---|---|---|
| 1 | A | 每个数字都带来源 URL，且该 URL 真能打开 | 产品的全部主张是「可审计」。没有来源就只是另一个数字罗列器 |
| 2 | A | 取数失败时明确报「无法判断」，不出结论 | 拿不到数据却给分数，是这份方法里第一类事故的样子 |
| 3 | A | 结论文本里的每个数字都能在信号表里找到 | 防止「结论说了 42 个贡献者，而表里是 unknown」 |
| 4 | B | **对已知的坏样本，必须给出坏结论** | 这是核心：如果它对一个明确不该用的库说「looks solid」，产品不成立 |
| 5 | B | 对已知的好样本，必须给出好结论 | 防止矫枉过正，把所有东西都判成有风险 |
| 6 | B | 每个信号必须带「盲区」说明，且不能为空 | 判不出「完成」和「废弃」的区别，就必须说出来 |
| 7 | A | 同一个输入两次运行，结论必须一致 | 判断是纯函数，不是模型。不一致说明有隐藏状态 |

## 第 4 条为什么是核心

阶段 2 的验收里，`moment/moment` 得到了 "looks solid"。而它是官方已宣布进入维护、建议新项目换用的库。

**这是产品的否定条件在提前显形**：五个 GitHub 指标拼出来的结论，和资深开发者的判断不一致。

如果这条修不好，产品就该按阶段 1 第五句停掉。所以第 4 条不是「质量检查」，它是这个产品是否存在的检查。

## 已知的坏样本（用于第 4 条）

| 样本 | 为什么算坏 | 现有工具怎么说 |
|---|---|---|
| `moment/moment` | 官方进入维护，README 建议勿用 | **looks solid** ← 错 |
| `request/request` | 已废弃 | usable with caveats（勉强对） |
| `jquery/jquery` | 仍在维护，不算坏——用来防止误杀 | looks solid（对） |

## 我要怎么修第 4 条

工具现在只看 GitHub 元数据，看不到 README 里那句「deprecated」。修法有三种，代价不同：

1. **读 README 首屏，找废弃声明。** 便宜，能覆盖 moment 这类。误报风险低。
2. **看是否 archived。** moment 没有 archived，所以这条不解决。
3. **看 npm 的 deprecated 标记。** 最准，但多一个外部依赖。

先做 1，因为它只依赖已经有的 API（README 内容），且直接针对失败样本。
