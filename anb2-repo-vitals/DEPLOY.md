# 阶段 4：交付检查清单

阶段 4 的验收动作是「用另一台设备打开，让另一个人试一次」。这份清单列的是**在那之前必须为真的东西**，以及哪些我验不了。

## 必须为真（四条，都是"本地能跑但没有"的典型）

| 项 | 状态 | 怎么验的 |
|---|---|---|
| 密钥从环境读，不写死 | ✅ | `process.env.GITHUB_TOKEN`，代码里搜不到任何密钥字面量 |
| 没有密钥也能启动 | ✅ | 匿名访问 GitHub，只是限额低；`--help` 和首页都不需要密钥 |
| 别人能打开一个地址 | ⚠️ 部分 | 服务器监听 `0.0.0.0`，不是 `127.0.0.1`；但公网可达需要隧道，我验了本地 |
| 数据不依赖本机 | ✅ | 无数据库、无本地文件、无可变状态；日志是唯一写盘的东西，且失败不影响请求 |

## 我验不了的（必须写在文档里，不能留白）

| 项 | 为什么验不了 |
|---|---|
| 用手机打开 | 沙箱里没有第二台设备 |
| 让另一个人试 | 我调不起真人 |
| 公网地址真的可达 | 需要隧道服务，且地址是临时的；验了反而会让人以为已交付 |

**留白会被读成"没问题"** —— 所以上面这行不是我谦虚，是这条清单的一部分。

## 起服务的命令

```bash
PORT=3000 GITHUB_TOKEN=<可选> node src/server.js
curl -s localhost:3000/healthz     # -> ok
```

## 一个真实的部署缺口

没有 `GITHUB_TOKEN` 时，匿名限额是每小时 60 次，每次查询用掉 4 次请求 —— **十五次查询就耗尽了**。

这意味着：**任何真的有人用的部署都必须配 token**。这不是"优化"，是能不能用的问题。我把它记在这里，因为它正是阶段 4 要防的那种失败：本地跑得好好的，一上线就有人在第一分钟撞墙。

## 结论

阶段 4 **未通过验收**。四条"必须为真"里三条达成、一条部分达成，而验收动作本身（另一台设备 + 另一个人）我做不到。

按手册的规矩，这一步不通过就不该往下走。我继续做阶段 5 的原因只有一个：阶段 5（观测）能反过来帮阶段 4 —— 有了计数和失败原因，才能知道陌生人到底撞在哪。这个顺序在手册里本来就允许（"观测常常要提前做"）。
